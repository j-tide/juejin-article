## 1. 本地 Agent 真正危险的不是会写文件：它能碰到哪些凭证？

### 热点是什么

GitHub 于 2026 年 9 月 23 日为 Copilot app 发布本地沙箱预览。用户可以按项目配置三类边界：文件系统的额外读写目录、只读目录和拒绝目录；网络的外网与本地网络访问；以及 Git HTTPS 凭证和 GitHub CLI 凭证。应用启动沙箱会话时请求这套策略，企业管理设置可以进一步收紧；如果操作系统无法实际执行请求的策略，shell 会直接失败，而不是降级成无沙箱运行。该能力默认关闭，只作用于新的本地会话，与云端沙箱、远程主机和 Copilot CLI 的配置相互独立，当前仍是 public preview。

原始资料：

- [GitHub Changelog：Local sandboxing in the GitHub Copilot app（2026-09-23）](https://github.blog/changelog/2026-09-23-local-sandboxing-in-the-github-copilot-app/)

### 为什么值得写

很多 Agent 安全讨论停在“不要让模型执行危险命令”，但真正的边界是宿主机能否强制限制文件、网络和凭证，而且策略失败时系统要选择拒绝还是放行。GitHub 这次更新把策略声明、操作系统执行、企业覆盖、会话生命周期和凭证范围放在一个具体产品里，适合写成一次权限链拆解。文章可以用本地脚本模拟读取被拒绝目录、访问内网和调用 GitHub CLI 三种动作，比较仅靠提示词、应用层拦截和 OS 沙箱的差异。重点是“请求的策略”和“生效的策略”并不相同，以及新会话边界如何影响长期 Agent。

### 建议标题

**本地 Agent 真正危险的不是会写文件：它能碰到哪些凭证？**

### 文章梗概

一个编码 Agent 被要求修复项目测试，顺手读取了用户目录里的 SSH 配置，还把命令输出发到了外部服务。把“不要这样做”写进 system prompt 没有解决权限问题，真正要问的是：文件、网络和凭证由谁在什么层面拦截？GitHub Copilot app 的本地沙箱预览给出了一个可拆的策略模型：按项目声明边界，由操作系统执行，企业设置可以收紧，无法执行时直接失败。文章先画出策略请求到 shell 启动的时序，再做三组动作测试：读取拒绝目录、访问本地网络、使用 GitHub CLI 凭证。最后讨论沙箱默认关闭、新会话才生效、CLI 与云端隔离，以及为什么“沙箱已开启”不能等同于“Agent 已安全”。

### 结构提纲

1. **提示词为什么不是权限边界**：用读取、联网和凭证调用三个例子区分模型意愿与操作系统能力。
2. **本地沙箱策略怎样进入执行链**：把项目设置、企业覆盖、shell 启动和 OS 强制执行串成状态图。
3. **文件、网络和凭证是三套不同边界**：分析目录白名单、本地网络、Git HTTPS 与 GitHub CLI 凭证的组合风险。
4. **策略无法执行时应该怎样失败**：对比 fail-open 和 fail-closed，说明降级行为为什么必须可观测。
5. **会话生命周期会改变安全结论**：测试默认关闭、新会话生效、重启生效以及本地/云端/远程配置分离。
6. **构造一个最小威胁测试集**：用合成项目验证越权读取、内网探测、凭证使用和策略变更的回归结果。

### 写作所需证据

- **已有资料**：GitHub Changelog 明确列出文件、网络、凭证三类设置、企业收紧策略、OS 无法执行时的失败行为和会话作用范围。
- **需要补做**：在本地准备一个无敏感数据的测试仓库，分别配置允许/只读/拒绝目录、外网/本地网访问和虚拟 Git 凭证；记录命令退出码、审计日志和重启前后状态。没有对应操作系统或产品会话时，只写策略模拟，不声称复现了 GitHub 的实现。
- **适合配图**：项目策略—企业覆盖—OS 沙箱—Agent shell 的架构图；一次命令从模型提出到系统拒绝的时序图；三类资源的权限矩阵。
- **关键未验证点**：不同操作系统的强制机制、企业策略覆盖优先级、凭证是否以代理方式注入、网络规则的默认值以及 public preview 的限制。

## 2. 800,000 行 Rust 是 Agent 写出来的，真正难的是谁来验收？

### 热点是什么

GitHub 工程师 Stephen Toub 的文章最初发表于 2026 年 9 月 16 日，并在 9 月 23 日更新，详细记录 GitHub Copilot CLI、Copilot app 和 SDK 共用的 Agent runtime 从 TypeScript/Node.js/V8 迁移到 Rust 的过程。文章称迁移最终达到 832,378 行生产 Rust、468,689 行 Rust 单元测试和 174,675 行端到端 TypeScript 测试，128 个迁移 PR 分批进入主分支，AI Agent 编写了大部分代码。文章还公开了 96.22% 的 prompt-cache 命中率、5,116 次上下文压缩，以及状态/生命周期、行为契约、宿主边界和错误测试 oracle 等回归类型。作者明确说这不是一句“把整个仓库交给 Agent”就能完成的工作，核心仍是拆分、测试、审查和持续回放。

原始资料：

- [GitHub Blog：Migrating the GitHub Copilot runtime to Rust, using Copilot（2026-09-16，2026-09-23 更新）](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/)
- [GitHub Copilot SDK](https://github.com/github/copilot-sdk)

### 为什么值得写

这篇工程复盘把“AI 写了很多代码”拆成了可以检查的生产流程：先把纯逻辑叶子节点迁移，再处理状态、工具、MCP 和编排；暂时用互操作层维持两种语言，按小 PR 发布，在预发布中观察回归；把 Agent session log 转成评测，持续修正提示词和测试。它还能和用户已有的 Harness、状态恢复、上下文压缩主题形成新的实证材料。文章真正值得讨论的是监督单位：单个 PR、一个迁移波次、一个 Agent session，还是一次完整发布？以及 96% 的缓存命中和数千次压缩怎样影响长期任务的成本与可靠性。

### 建议标题

**800,000 行 Rust 是 Agent 写出来的，真正难的是谁来验收？**

### 文章梗概

把一个生产 Agent runtime 从 TypeScript 改写成 Rust，最容易被记住的是“800,000 行代码主要由 Agent 写成”；真正决定项目能否上线的，却是每个迁移波次如何被限制、测试和回滚。GitHub 的复盘给出了完整线索：从无 I/O 的纯函数开始，逐步经过状态、工具、MCP 和 session orchestration，保留临时互操作层，128 个 PR 分批发布，并把回归和 session log 变成后续评测。文章按这条执行链分析 Agent 参与大型重写的监督单位，解释 prompt cache、compaction、subagent 和 worktree 如何支撑长任务，再用一个小型 TypeScript→Rust 模块迁移实验记录错误 oracle、接口漂移和回滚成本。结论会落在“如何验收”，而不是“Agent 能写多少行”。

### 结构提纲

1. **为什么不能一次性让 Agent 重写整个 runtime**：从状态、I/O、宿主边界和共享依赖说明不可逆风险。
2. **从叶子函数向编排层推进**：还原 GitHub 的迁移顺序、互操作层和 128 个 PR 的分批发布策略。
3. **测试 oracle 比生成代码更重要**：拆解行为契约、生命周期、host boundary 和错误测试本身失真的回归类型。
4. **长任务靠什么不丢上下文**：解释 96.22% prompt-cache、5,116 次 compaction、subagent 和独立 worktree 的配合。
5. **Agent merge 怎样把反馈送回系统**：分析 review、CI、冲突、session log 和提示词更新如何形成闭环。
6. **用小型迁移验证监督单位**：设计一个可回放的模块迁移，比较单 PR、迁移波次和发布级验收的证据差异。

### 写作所需证据

- **已有资料**：GitHub 工程文章公开迁移时间线、代码和测试规模、分层顺序、缓存/压缩统计、Agent fleet、回归分类和发布方式。
- **需要补做**：选一个带接口和测试的 TypeScript 小模块，先迁移纯逻辑，再迁移有状态部分；固定测试 oracle，注入一次行为契约错误，记录 Agent 修复、人工审查和回滚过程。
- **适合配图**：从纯函数到 session orchestration 的迁移阶梯；TypeScript/Rust 互操作层的生命周期图；Agent session—缓存—compaction—测试—PR 的闭环图。
- **关键未验证点**：文章中的“性能提升数量级”没有统一公开基准，缓存命中率依赖该项目的提示词与调用结构，回归数量也不等于全部缺陷；复现实验只能验证流程，不应复述其生产数字。

## 3. 一百万行 PR 也要能评审：动态评论怎样和虚拟列表共存

### 热点是什么

GitHub 于 2026 年 9 月 23 日发布 Copilot app 的前端工程复盘，说明如何让一个包含 2,200 个文件、超过一百万行变更和 400 多条行内评论的 Pull Request 仍能打开、滚动和回复。纯代码 diff 可以利用固定行高和虚拟列表，但 Markdown 评论、展开区域、回复框、图片和 suggested change 的高度只有渲染后才能知道。GitHub 因此把确定性的代码几何和动态评论几何拆开：代码行用前缀和保持精确，评论以稳定 key 锚定文件/行/侧边，按指纹和宽度缓存测量结果，滚动停止后只测视口附近的 block，并用身份锚定修正滚动位置。文章还公开了结构优先流式加载、主线程外高亮、最近 diff 缓存和自动化测量回归的方法。

原始资料：

- [GitHub Engineering：Rendering huge pull requests in the GitHub Copilot app（2026-09-23）](https://github.blog/engineering/user-experience/rendering-huge-pull-requests-in-the-github-copilot-app/)

### 为什么值得写

这是一篇前端性能文章，但它和 AI Agent 的关系很直接：Agent 生成的变更越大，审查评论、建议修改和会话状态越多，代码评审界面就越像一个带动态数据的长任务工作台。简单套虚拟列表会在评论高度变化时产生跳动、空白和重复测量。GitHub 的做法把可预测和不可预测部分拆成两个几何域，再用指纹、视口调度和用户锚点维护体验，适合用一个开源 diff 页面做对照实现。文章可以讨论 Agent UI 的性能指标为什么不能只看首屏时间，还要看滚动稳定性、评论 hydration、缓存复用和“用户主动展开”与后台重排之间的优先级。

### 建议标题

**一百万行 PR 也要能评审：动态评论怎样和虚拟列表共存**

### 文章梗概

代码行的高度可以提前算，评论却不行：Markdown 会换行，回复框会展开，图片可能晚到，Agent 还会不断追加建议修改。把所有内容塞进同一套虚拟列表，滚动时就会出现跳跃、空白和不断重排。GitHub 为 Copilot app 重做超大 PR 视图时，把代码几何和动态 block 几何分开，评论用稳定身份锚定到文件和行，测量只在滚动停止后、视口附近进行，修正时保持用户正在看的 anchor 不动。文章先用一个百万行规模的模拟 diff 解释问题，再实现固定行高 + 动态评论的最小版本，比较单一高度表与双几何模型的滚动和内存表现，最后把这些方法连接到 Agent 生成代码后的审查、评论 hydration 和增量更新。

### 结构提纲

1. **为什么普通虚拟列表遇到评论就失效**：从固定行高、动态 Markdown 和展开交互说明测量契约被打破。
2. **双几何模型如何拆开问题**：解释确定性代码高度、动态 block 高度、稳定 key 和宽度指纹。
3. **测量调度怎样避开滚动热路径**：分析 idle/scroll-gated pass、视口范围、单次 reflow 和 ResizeObserver 的职责。
4. **滚动锚定为什么要按身份而非像素**：展示评论高度变化、窗口重排和用户主动操作下的修正规则。
5. **数据管道如何支撑 Agent 评审界面**：讨论结构优先流式加载、后台高亮、建议修改和最近 diff 缓存。
6. **用最小 diff surface 做压力实验**：测量首屏、滚动帧、评论 hydration、内存和大批量 Agent 评论的退化曲线。

### 写作所需证据

- **已有资料**：GitHub 文章给出极端 PR 规模、双几何公式、测量调度、滚动锚定、数据流和自动化找 bug 的具体设计。
- **需要补做**：用 React 或原生 DOM 做一个可生成大 diff 的测试页，分别实现单一高度表和双几何模型；注入动态评论、图片延迟和展开回复，采集滚动帧率、布局次数和内存。
- **适合配图**：代码行与评论 block 的双几何架构图；滚动—测量—修正时序图；Agent 连续追加评论时的数据流和缓存图。
- **关键未验证点**：文章没有公开完整的生产性能基线、浏览器/硬件矩阵和极端并发评论数据；本地压力测试只能说明设计趋势，不能宣称达到 Copilot app 的指标。

## 4. Qwen Code 0.24.4 开始记录计划漂移，Coding Agent 为什么需要“计划证据”？

### 热点是什么

Qwen Code 于 2026 年 9 月 22 日发布 v0.24.4。这个开源 coding agent 版本加入了 monitor tool 的系统提示引导、批量 workspace session catalog、记录计划由什么输入计算并报告 drift、托管工具执行状态、SSH workspace、加密隔离连接配置、managed runtime attestation，以及把 bubblewrap 沙箱移到工具执行层等能力。发布页标明没有已知 breaking changes，但这些功能涉及会话、计划、工具执行、远程工作区和沙箱多个边界，不能只当作零散 feature list。仓库同时公开完整变更清单，适合从计划版本、工具状态和运行时证明之间的关系做源码阅读。

原始资料：

- [Qwen Code：Release v0.24.4（2026-09-22）](https://github.com/QwenLM/qwen-code/releases/tag/v0.24.4)
- [QwenLM/qwen-code 仓库](https://github.com/QwenLM/qwen-code)

### 为什么值得写

Coding Agent 经常先生成一个计划，再执行文件修改、命令和测试；真正棘手的是计划之后仓库、工具权限或用户目标发生变化，系统却继续沿用旧计划。Qwen Code 把“计划由什么计算出来”和“计划是否漂移”做成显式记录，说明 Agent 的长期可靠性需要计划证据，而不只是最终 diff。托管工具执行、runtime attestation 和沙箱边界又把计划和运行环境连接起来。文章可以实现一个最小计划哈希与工具状态机，模拟用户修改需求、切换工作区、工具执行重试和远程会话恢复，讨论什么时候应该重算计划、暂停任务或要求人工确认。

### 建议标题

**Qwen Code 0.24.4 开始记录计划漂移，Coding Agent 为什么需要“计划证据”？**

### 文章梗概

Agent 上午计划“把支付模块拆成三个服务”，下午用户已经改了接口、切换了 workspace，系统却继续执行早上的文件列表。最终代码可能能编译，但过程已经偏离目标。Qwen Code 0.24.4 新增“计划由什么输入计算”和 drift 报告，同时把托管工具执行、SSH workspace、runtime attestation 与沙箱下沉到工具执行层。文章先把计划、工作区快照、工具权限和执行状态画成状态机，再做一个最小实现：为计划保存输入摘要和哈希，执行每个工具前检查漂移，遇到冲突时选择重算、暂停或人工确认。最后分析计划证据和最终 diff 的关系，说明它解决的是可追责与恢复问题，不是保证模型一定做对。

### 结构提纲

1. **计划为什么会过期**：列出用户目标、仓库内容、工具清单、权限和外部依赖五种漂移来源。
2. **计划证据应记录什么**：设计输入摘要、版本、哈希、生成模型、工具集合和确认点的最小 schema。
3. **工具执行状态如何与计划关联**：区分待执行、运行中、成功、失败、重试和人工确认，避免只保存最终 diff。
4. **沙箱、SSH 和 attestation 改变了什么**：讨论本地/远程工作区、工具级隔离和运行时证明如何影响恢复。
5. **重算、暂停还是继续**：用目标变化、文件冲突、权限变化和测试失败四类事件定义决策矩阵。
6. **用回放测试验证计划漂移**：构造连续会话，比较没有计划证据、只比对文件、带状态机三种实现的错误传播。

### 写作所需证据

- **已有资料**：Qwen Code v0.24.4 release 公开列出 monitor guidance、workspace catalog、plan drift、managed tool execution、runtime attestation、SSH workspace 和工具级沙箱变化。
- **需要补做**：阅读 release 对应的 PR 和测试；实现一个独立的计划哈希/漂移检测器，注入目标修改、分支切换、工具权限变化和远程连接中断，保存状态转移与人工介入点。
- **适合配图**：计划输入—工具执行—状态快照—漂移检测—重算/暂停的状态图；本地与 SSH workspace 的权限边界图；attestation 与工具回执的时序图。
- **关键未验证点**：release 页面没有给出 drift 判定算法、attestation 的可信根、工具状态持久化格式和不同 workspace 组合的失败行为；需以源码和测试为准。

## 今天最值得优先写

推荐先写第 2 题：**《800,000 行 Rust 是 Agent 写出来的，真正难的是谁来验收？》**。

这篇材料在 9 月 23 日刚更新，而且不是简单发布说明，而是完整的生产工程复盘：迁移拆分、互操作、回归分类、prompt cache、compaction、subagent、worktree、Agent merge 和发布节奏都有具体证据。它既能写出架构图和流程图，也能在本地用小型 TypeScript/Rust 模块做可复现实验。更重要的是，文章天然把“Agent 能不能写代码”转成“如何让人审得过、测得出、出错能回滚”，和读者正在面对的真实工程问题直接相关。

## 暂不建议追的方向

- **只把本地沙箱写成产品开关介绍**：真正值得写的是策略声明、OS 强制和失败语义；具体实现仍需要操作系统和产品版本复核。
- **把 Copilot runtime 的 800,000 行当成 Agent 自动编程能力证明**：数字来自 GitHub 工程复盘，项目依赖成熟测试、架构负责人和持续发布，不能外推到任意代码库。
- **把 Qwen Code 的 plan drift 当成已经验证的可靠性提升**：当前只有 release 功能清单，漂移算法和回放效果需读源码、跑测试后再下结论。
- **把超大 PR 的前端方案直接当成通用 benchmark**：文章公开了设计原则，但没有完整硬件和浏览器基线，复现实验应报告自己的环境和指标。
