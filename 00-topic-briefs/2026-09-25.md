## 1. Google PageBreak：Agent 找到漏洞以后，怎样证明它真的能被利用？

### 热点是什么

Google 于 2026 年 9 月 24 日公开介绍内部 Product Security Agent「PageBreak」。它的重点不是让模型多报候选漏洞，而是让候选进入专门的、非 AI 编写的验证器：XSS 通过真实渲染环境执行 JavaScript，SQL 注入检查查询结果或时间变化，路径穿越尝试读取新文件，RCE 和 SSRF 则观察可验证的副作用。Google 称 PageBreak 通过确定性验证把误报压到接近零，并在其一方 Web 应用中发现了 500 多个 XSS；同时保留非确定性候选作为后续验证器开发的种子，不把未验证结果直接交给产品团队。文章还提到它利用单一代码库、流量安全信号和既有扫描基础设施把请求路径连到源码。

原始资料：

- [Google Security Blog：Agentic Hacks, Real Proofs: Inside Google's PageBreak Project（2026-09-24）](https://blog.google/security/agentic-hacks-real-proofs-inside-googles-pagebreak-project/)
- [Google Bug Hunters：PageBreak 配套漏洞深挖](https://bughunters.google.com/)

### 为什么值得写

事实层面，PageBreak 给出了“模型提出假设—专用验证器执行—高置信结果入队—低置信结果反馈”的完整闭环；Google 还明确承认验证器覆盖不足会带来漏报。判断层面，这比“让 LLM 扫代码”更适合讨论安全 Agent 的验收标准：模型负责搜索空间和攻击路径，确定性工具负责把结论落到可观测副作用。文章可以把它和普通静态扫描、只依赖模型判断的 Agent 做对照，说明为什么验证器接口、隔离环境和证据留存比提示词更决定最终噪声。Google 的大单体仓库和内部流量信号是特殊条件，不能直接外推到小团队。

### 建议标题

**漏洞 Agent 找到的只是线索：Google PageBreak 怎样把猜测变成可验证证据？**

### 文章梗概

安全团队最怕的不是少报一个候选，而是收到一堆无法复现的漏洞报告。Google 的 PageBreak 把 Agent 的职责压缩到提出假设和选择攻击路径，把是否成立交给确定性验证器：真实渲染、查询响应、文件副作用和出网信号都要留下可回放证据。文章先画候选到验证的执行链，再用三类验证器解释接口设计，最后在本地靶场比较纯模型、规则和运行时验证，说明“近零误报”仍是发布方口径。
### 结构提纲

1. **从“发现”到“证明”**：区分漏洞假设、可利用性和产品团队可以行动的证据。
2. **PageBreak 的候选生成链**：还原代码路径、HTTP 流量信号、扫描器和 Agent 之间如何交换上下文。
3. **验证器为什么必须是确定性的**：用 XSS、SQL 注入、路径穿越、RCE、SSRF 对照各自的可观测副作用。
4. **漏报如何回到系统改进**：解释非确定性发现的种子、缺失能力反馈和验证器开发队列。
5. **哪些条件不能照搬 Google**：分析大单体仓库、认证扫描基础设施、内部数据和固定随机种子带来的优势。
6. **搭一个最小运行时验证实验**：在隔离靶场上记录候选、payload、环境、结果和复现脚本，比较三种 Agent 方案。

### 写作所需证据

- **已有资料**：Google 文章给出 PageBreak 的目标、启动时间、验证器类别、非确定性反馈、500+ XSS 的发布方统计，以及单体仓库、流量信号和既有扫描器的上下文。
- **需要补做**：阅读 Google 配套漏洞案例，搭建只含 XSS、路径穿越和 SSRF 的本地靶场；让模型只能提交结构化漏洞假设，由固定验证器执行，并记录可复现 payload、HTTP 响应和副作用。
- **适合配图**：Agent 候选生成—验证器—证据存档—人工确认的架构图；三类验证器的时序图；确定性结果与非确定性种子的反馈回路图。
- **关键未验证点**：Google 没有公开 PageBreak 的完整模型提示、验证器实现、样本分母和误报计算方法；“近零误报”和 500+ XSS 都不能写成独立实测结论。

## 2. GitHub Security Lab 的 Fuzzing Taskflow：Agent 怎样接管模糊测试的人工循环？

### 热点是什么

GitHub Security Lab 于 2026 年 9 月 24 日公开介绍基于 Taskflow Agent 的 C/C++ 模糊测试流水线。给它一个 GitHub 仓库后，任务流会识别入口、分析构建系统、生成 fuzz harness、运行 AFL++、读取覆盖率、改进 harness、归并 crash，并为每个唯一问题生成带可利用性判断、建议补丁和回归测试草稿的报告。仓库把 shell 驱动、YAML taskflow 和 MCP 工具分成三层，Agent 负责“下一步做什么”，工具负责编译、运行 AFL、读覆盖率和写数据库；状态落在 SQLite 中，AFL 二进制与 coverage 二进制分别构建。覆盖率预算从 30 秒逐轮翻倍，连续两轮增益低于 1% 时停止。

原始资料：

- [GitHub Blog：AI-powered fuzzing with the GitHub Security Lab Taskflow Agent（2026-09-24）](https://github.blog/security/application-security/ai-powered-fuzzing-with-the-github-security-lab-taskflow-agent/)
- [GitHubSecurityLab/seclab-taskflows-fuzzing](https://github.com/GitHubSecurityLab/seclab-taskflows-fuzzing)
- [GitHubSecurityLab/seclab-taskflow-agent](https://github.com/GitHubSecurityLab/seclab-taskflow-agent)

### 为什么值得写

这条热点的价值在于它公开了一个可读、可运行的 Agent 工程，而不是只展示扫描结果。事实是，Taskflow 把“写 harness—跑一轮—看覆盖率—补种子或改 harness”显式建模为可恢复的任务流，并让 MCP 工具掌管副作用；仓库还说明默认直接在宿主机运行 AFL、clang 和任意构建命令，提示注入可能获得用户权限。判断是：这里最值得拆的不是 Agent 是否替代安全研究员，而是如何把一个会产生副作用的循环变成可暂停、可重跑、可审计的状态机。它和前几天的“权限边界”主题不同，切口在执行编排、反馈信号和失败恢复。

### 建议标题

**让 Agent 自己跑 AFL++：GitHub 的 Fuzzing Taskflow 怎样把覆盖率变成下一步指令？**

### 文章梗概

模糊测试真正耗人的地方，是判断下一轮该换入口、补 seed、改 harness，还是接受某条分支暂时到不了。GitHub Security Lab 把这段经验写成 Agent taskflow：YAML 描述阶段，MCP 工具负责编译和执行，SQLite 记录覆盖率缺口与 crash，Agent 每轮读取反馈再决定动作。文章沿源码还原调用顺序，解释 AFL 与 coverage 双二进制，再在小目标上跑短时回路，讨论宿主机执行、提示注入和“全自动”的边界。
### 结构提纲

1. **人工模糊测试循环到底在判断什么**：把入口选择、harness、seed、覆盖率和 crash triage 拆成决策点。
2. **三层 Taskflow 架构**：从 `run_fuzzing.sh`、YAML 阶段到 MCP 工具和 SQLite 状态追踪调用链。
3. **覆盖率如何变成 Agent 的反馈信号**：解释 AFL 二进制、coverage 二进制、LCOV、缺口表和 30s→960s 预算。
4. **Corpus 和崩溃报告为什么要持久化**：分析跨迭代 seed、stack hash、已知 crash 回归以及建议补丁的证据边界。
5. **“工具执行”与“决策”如何分权**：讨论 MCP 工具的显式参数、幂等、失败重试、宿主权限和隔离环境。
6. **在小目标上复现一轮**：记录覆盖率、耗时、生成 harness 数量、crash 分类和人工复核，不外推 GitHub 的生产效果。

### 写作所需证据

- **已有资料**：文章与两个仓库公开三层架构、任务阶段、SQLite schema、双二进制构建、覆盖率循环、持久 corpus、crash 分类和安全警告。
- **需要补做**：在 Codespace 或一次性 Linux VM 中跑 cJSON 等小目标的短预算；读取 `fuzz_context.db`、覆盖率报告和 crash 目录，手工复核一个 harness_bug 与一个真实库问题的分类。
- **适合配图**：shell—YAML—MCP—SQLite 的架构图；覆盖率反馈状态机；从 crash 到去重、复现、报告的时序图。
- **关键未验证点**：官方仓库仍标注 Active development；不同模型、目标项目和预算下的覆盖率收益没有独立基线；脚本在宿主机执行任意命令，复现必须使用隔离环境。

## 3. Chat 之外的 Agent 工作面：Copilot canvas 为什么要做成双向应用？

### 热点是什么

GitHub 于 2026 年 9 月 24 日介绍 Copilot app 的 canvas，并在文档中把它定义为供人和 Agent 共同编辑的共享交互面。canvas 不是一张静态结果页，而是一个可以包含计划、工单看板、浏览器会话、发布清单、仪表盘或表格的全栈扩展：人可以通过按钮、卡片和筛选器修改状态，Agent 也可以调用同一套能力。项目级 canvas 放在 `.github/extensions`，个人级放在 `~/.copilot/extensions`，通常由 `package.json`、入口脚本和持久化 artifact 组成。GitHub 的工程文章还举了 Connect 4、Winget、SQLite 和 Agent Loop 等例子，强调把稳定的重复交互从聊天上下文里移到可见工作面。

原始资料：

- [GitHub Blog：When chat is the wrong UI（2026-09-24）](https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/)
- [GitHub Docs：Working with canvas extensions in the GitHub Copilot app](https://docs.github.com/en/copilot/how-tos/github-copilot-app/working-with-canvas-extensions)

### 为什么值得写

事实层面，GitHub 已经把 canvas 的共享状态、双向能力和项目/用户范围写进了文档；工程文章则给出“研究—原型—计划—实现—迭代—定稿”的 Agent 工作流例子。判断层面，canvas 的关键不是换一个更漂亮的聊天框，而是把 Agent 的中间产物、人工确认和下一步动作变成可见状态，从而减少重复 token 和上下文滚动。文章可以做一个真实的工单看板或发布清单，比较“每一步都在 chat 里问 Agent”和“Agent + 共享 canvas”两种交互，测量状态丢失、重复调用、人工纠偏和恢复成本。需要提醒读者：canvas 仍是 Copilot app 的产品能力，不能直接等同于通用 Agent UI 标准。

### 建议标题

**Agent 不该一直待在聊天框里：Copilot canvas 怎样把长任务变成共享工作面？**

### 文章梗概

长任务一旦把意图、证据、待办和操作结果都堆在聊天记录里，人插入修改后 Agent 很难知道哪些内容已经确认。GitHub canvas 把这些内容搬到人和 Agent 共用的全栈表面：人通过 UI 控件改状态，Agent 调用同一套 capability，项目或个人范围决定它是否进入仓库。文章先画双向链路，再实现工单看板，对比 chat-only 与共享状态在重复调用、纠偏和恢复上的差异，最后讨论权限、并发和适用边界。
### 结构提纲

1. **聊天记录为什么会变成隐藏数据库**：拆出意图、状态、证据和操作结果，说明滚动上下文无法稳定承载它们。
2. **Canvas 的双向状态模型**：分析 UI action、Agent-callable capability、后端状态和实时回显的边界。
3. **从项目扩展到个人扩展**：阅读 `.github/extensions`、`~/.copilot/extensions`、入口文件与 artifact 的结构。
4. **共享工作面怎样减少重复调用**：用工单看板比较 chat-only 与 canvas-assisted 的 token、纠偏和恢复路径。
5. **人和 Agent 同时改状态会怎样**：设计版本号、操作日志、幂等命令和人工确认点，避免状态覆盖。
6. **什么场景不值得做 Canvas**：对照固定表单、Workflow、文档和真正需要探索的长任务，明确成本边界。

### 写作所需证据

- **已有资料**：GitHub 文章和 Docs 给出 canvas 的定义、双向交互、项目/个人范围、文件结构、示例工作流和使用场景。
- **需要补做**：按文档做一个不接真实账号的本地 issue triage canvas 原型；记录 chat-only 与共享状态两条流程的消息数、重复字段、人工修改次数和中断恢复时间。
- **适合配图**：Chat—Canvas—Agent—后端状态的双向架构图；工单状态的 UI/工具事件时序图；项目范围与个人范围的部署边界图。
- **关键未验证点**：文档没有公开 canvas 运行时的并发冲突解决、权限模型、状态持久化一致性和大规模更新性能；本地原型不能代表 Copilot app 的实现。

## 4. 高风险操作不能只看 Token：GitHub Proof of Presence 给 Agent 加哪一道门？

### 热点是什么

GitHub 于 2026 年 9 月 24 日在 Enterprise Cloud public preview 中推出 Proof of Presence。启用后，企业成员执行创建 token、编辑 webhook、修改组织安全设置、查看恢复码等高影响操作时，GitHub 会把用户重定向到企业 IdP，要求重新认证或完成 MFA；通过挑战后沿用 sudo mode 的会话和超时模型，当前支持 Microsoft Entra ID，成功后通常可在两小时内继续执行受保护动作。GitHub 明确把它和被窃取的 session cookie、长期 token 以及 Agent 越权操作联系起来，并说明即将支持在 Pull Request merge 前要求 presence proof。

原始资料：

- [GitHub Changelog：Require proof of presence for high-impact actions（2026-09-24）](https://github.blog/changelog/2026-09-24-require-proof-of-presence-for-high-impact-actions/)
- [GitHub Docs：Configuring Proof of Presence](https://docs.github.com/en/enterprise-cloud@latest/admin/configuring-settings/hardening-security-for-your-enterprise/configuring-proof-of-presence)

### 为什么值得写

很多 Agent 权限设计默认“拿到有效 token 就可以继续”，但长任务可能跨越数小时，用户也可能忘了系统已经拥有足够大的权限。Proof of Presence 把“这个 session 仍然有效”和“现在确实有一个经过 IdP 验证的人批准高影响动作”拆开了。事实是它目前只覆盖特定企业、IdP 和 public preview，且在 merge 前的支持尚未上线；判断是，这为 Agent 的人工确认设计提供了一个更具体的接口：普通读写可以自动化，高影响动作必须重新建立人的在场证据。文章适合把会话、token、IdP、Agent 工具调用和审计事件串成一条权限链。

### 建议标题

**Agent 拿到有效 Token 以后还不够：高影响操作为什么需要“人在场证明”？**

### 文章梗概

一个部署 Agent 想修改 webhook 或创建访问 token 时，早上的登录 session 仍然有效，并不代表此刻有人愿意批准这一步。GitHub Proof of Presence 在高影响操作前插入 IdP 重新认证或 MFA，并复用 sudo mode 的短时会话。文章把 Agent、凭证、工具网关和审计记录串成权限链，再用模拟网关比较 token-only、固定审批和 presence proof，分析两小时窗口、后台任务与 public preview 的限制。
### 结构提纲

1. **有效凭证不等于当前授权**：用 session cookie、长期 token 和 Agent 长任务区分身份、会话和动作授权。
2. **Proof of Presence 的请求链**：还原高影响动作、GitHub、Entra ID、重新认证/MFA 和返回放行的时序。
3. **哪些动作应该被挡住**：从创建 token、改 webhook、改组织安全设置到未来的 PR merge 建立风险分级。
4. **两小时 sudo 会话如何影响 Agent**：分析重复挑战、后台任务、人工接管和超时后的失败处理。
5. **做一个工具网关对照实验**：记录 token-only、预授权和 presence proof 三种实现的误放行与操作摩擦。
6. **Preview 的边界和推广条件**：讨论仅支持 Entra ID、企业范围、IdP 策略质量、审计留痕和非人类主体身份。

### 写作所需证据

- **已有资料**：GitHub Changelog 和 Docs 公开动作范围、重新认证/MFA 选项、Entra ID 限制、sudo mode 会话模型和 public preview 状态。
- **需要补做**：实现一个不接真实 GitHub 的模拟工具网关；为每个调用生成 session age、presence proof、动作风险、审批结果和审计事件，测试过期、并发和重复调用。
- **适合配图**：Agent—工具网关—GitHub—IdP 的认证时序图；token/session/presence 三层权限图；风险动作分类矩阵。
- **关键未验证点**：真实企业 IdP 策略、Agent 非人类身份、两小时窗口内的细粒度撤销和未来 merge gate 行为仍需等产品文档或实际环境确认。

## 5. Anthropic 用约 950 个 Agent 搜索 DNA：科学发现的“候选—实验—反馈”链条怎么搭？

### 热点是什么

Anthropic 于 2026 年 9 月 23 日介绍其生命科学研究组和一项早期结果：约 950 个 Claude Agent 花费 21 小时、使用约 2.1 亿 tokens，在超过 20 万个 reverse transcriptase 候选中筛出 3,500 个新系统，再缩到 20 个重点候选，最终发现与一组 DNA 重复序列相关的 array-associated reverse transcriptases（ART）。实验室人员完成全部湿实验；Anthropic 表示 ART 的具体功能仍未知，当前结果是一个与 CRISPR-like repeat array 相似的候选系统，并已发布 preprint。其工作流包括复现公开结果、扫描蛋白家族和基因邻域、撰写带证据的候选报告、批判性淘汰，再把通过审查的候选交给实验验证；实验反馈还会反过来影响指令和“科学品味”。

原始资料：

- [Anthropic Science：Claude discovers a novel enzyme system with CRISPR-like repeats（2026-09-23）](https://www.anthropic.com/news/claude-discovers-novel-enzyme-system)
- [Anthropic technical report（页面内 preprint 链接）](https://www.anthropic.com/news/claude-discovers-novel-enzyme-system)

### 为什么值得写

这是一个适合拆“科学 Agent 如何工作”的真实案例，但不能写成“模型已经发明了 CRISPR”。事实是 Anthropic 报告了候选发现、初步实验和仍未确定的功能；人类科学家负责实验，模型负责大规模检索、比较、候选排序和报告。判断是，真正可迁移的工程问题在于如何把数百到数千条候选变成带证据、可淘汰、可复核的队列，以及如何让实验结果更新后续搜索策略。文章可以对照普通 RAG 问答，分析多 Agent 并行、证据卡、候选去重、人工 gate 和实验反馈的差异，同时把厂商自述数字与 preprint 中可验证的方法分开。

### 建议标题

**950 个 Agent 找到的不是答案，而是一批候选：Anthropic 怎样把模型接进真实实验？**

### 文章梗概

在 DNA 数据库里找到值得实验的异常，要经过复现已知结果、比较基因邻域、写证据报告和大规模淘汰。Anthropic 的 ART 案例公开了一条链：约 950 个 Agent 并行搜索 21 小时，人类科学家决定实验，结果再回到后续指令。文章画出候选队列和人工 gate，用小数据集模拟并行检索、去重和复核，讨论什么时候只能写“候选”、什么时候才是已验证结论。
### 结构提纲

1. **科学发现任务为什么不能只看最终答案**：区分检索候选、机制假设、实验观察和已确认结论。
2. **Anthropic 的候选队列**：按复现公开结果、家族扫描、邻域分析、报告和淘汰还原工作流。
3. **多 Agent 并行怎样避免重复和噪声**：设计候选 schema、证据卡、去重键、置信度和人工 gate。
4. **实验结果如何进入下一轮**：分析实验反馈、指令更新和“科学品味”学习的可观测接口。
5. **把数字放回证据边界**：分别标注 950 Agent、2.1 亿 tokens、20 个候选和 ART 功能未知等事实与限制。
6. **搭一个小型候选—验证原型**：用公开蛋白/论文数据演示并行筛选、报告审查和人工确认，不声称复现生物发现。

### 写作所需证据

- **已有资料**：Anthropic 文章公开 Agent 数量、搜索时长、token 量、候选筛选规模、ART 的当前状态、湿实验由人完成，以及候选工作流和反馈方式。
- **需要补做**：读取页面链接的 preprint，核对数据集、候选筛选条件、实验样本和统计口径；用公开小数据集做不涉及实验的候选队列模拟，观察并行任务、去重和人工淘汰。
- **适合配图**：数据集—并行 Agent—候选报告—专家 gate—实验—反馈的闭环图；候选状态机；证据卡字段和升级条件示意图。
- **关键未验证点**：ART 的生物功能仍未确定，Anthropic 的 token/Agent 统计是自报，候选筛选和实验成功率不能据此推算；preprint 与后续同行评议可能改变结论。

## 今天最值得优先写

推荐先写第 2 题：**《让 Agent 自己跑 AFL++：GitHub 的 Fuzzing Taskflow 怎样把覆盖率变成下一步指令？》**。

它同时具备新鲜的一手发布、可直接阅读的开源仓库和明确的执行链：shell 驱动、YAML taskflow、MCP 工具、SQLite 状态、AFL++、coverage feedback 和 crash triage 都能落到源码。读者可以在隔离 Linux 环境跑一个小目标，拿到真实的覆盖率、状态和报告文件；文章也有清晰的反例和安全边界，不需要把 GitHub 的生产效果包装成独立 benchmark。PageBreak 更适合随后写成“验证器如何把漏洞候选变成证据”的安全专题，Anthropic 的 ART 则适合作为科学 Agent 的不确定性案例。

## 暂不建议追的方向

- **把 PageBreak 的 500+ XSS 写成通用漏洞发现率**：这是 Google 内部规模和基础设施下的发布方统计，缺少公开样本分母与独立复现。
- **把 Fuzzing Taskflow 的自动化等同于无人值守生产安全**：仓库明确警告它会在宿主机运行 AFL、clang 和 Agent 选择的构建命令，必须先解决隔离和权限。
- **把 canvas 直接写成“聊天已被淘汰”**：目前公开材料是 Copilot app 的产品设计和文档，真正的价值要通过共享状态、人工纠偏和恢复实验来验证。
- **把 Proof of Presence 当成所有 Agent 的通用身份标准**：当前只在 GitHub Enterprise Cloud public preview，支持范围、IdP 和高影响动作仍有限。
- **把 Anthropic 的 ART 说成已经发现可用的基因编辑工具**：官方明确表示其功能尚未确定，后续实验和同行评议仍会改变结论。
