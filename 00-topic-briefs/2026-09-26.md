## 1. n8n Agents：工作流和 Agent 到底该由谁做主？

### 热点是什么

n8n 于 2026 年 9 月 25 日发布新的 Agents 产品形态。它把 Agent 放在现有 Workflow 旁边，支持 Agent 调用已有 workflow 作为工具，也支持 workflow 通过新的 Message an Agent 节点调用 Agent。一个 Agent 自带 instructions、tools、skills、knowledge、memory、sessions、channels、sub-agents 和版本发布能力；敏感工具可以配置审批，每个工具绑定自己的凭证，Agent 本身不直接持有系统密钥。n8n 明确保留原有 AI Agent node，并把选择权交给使用者：固定步骤由 Workflow 负责，输入不确定、需要多轮判断的任务由 Agent 决定下一步。当前 Cloud 可用，自托管需要额外配置，产品仍处于 preview。

原始资料：

- [n8n Blog：Introducing n8n Agents（2026-09-25）](https://blog.n8n.io/introducing-n8n-agents/)
- [n8n Agents 文档入口](https://docs.n8n.io/advanced-ai/agents/)

### 为什么值得写

事实是，n8n 没有把 Workflow 宣布成过时方案，而是把两者做成可互相调用的边界：Agent 选择何时调用工具，Workflow 固定工具内部的每一步。它还把审批、每工具凭证、版本、session 日志写进产品模型。判断是，这比“Agent 还是 Workflow”的概念争论更适合落到一个真实工单或客服场景：哪里允许模型判断，哪里必须用确定性流程，哪个动作要人工确认。文章可以复现同一需求在三种编排方式下的差别，重点观察权限、可回放性、失败恢复和维护成本，而不是只展示拖拽界面。

### 建议标题

**Agent 和 Workflow 不必二选一：n8n 怎样把“判断”和“执行”拆开？**

### 文章梗概

工单里一句“客户怎么还没续费”，可能要查 CRM、合同和支持记录，还要决定是否通知值班人员；步骤无法提前写死，但查数据和写备注又不该交给模型自由发挥。n8n Agents 把 Agent 放在决策层，把已有 Workflow 作为受限工具，同时保留反向调用。文章用同一工单对比纯 Workflow、Agent 直连和 Agent 调 Workflow，记录权限、日志、回滚、失败恢复与人工介入点。

### 结构提纲

1. **为什么固定流程和开放任务会混在一起**：用客服工单拆出可预先确定的步骤与必须现场判断的步骤。
2. **n8n Agents 的两条调用方向**：分析 Agent 调 Workflow 与 Workflow Message an Agent 的输入、输出和会话边界。
3. **Workflow 作为工具怎样缩小权限**：阅读每工具凭证、参数约束、审批和系统记录写入的执行链。
4. **Agent 自带的 sessions、版本和 memory**：讨论发布、回滚、跨渠道复用与 session 日志能否支撑审计。
5. **三种编排的对照实验**：在本地模拟 CRM 查询、写备注和升级值班，比较错误传播、恢复和维护成本。
6. **何时把判断收回 Workflow**：建立按输入不确定性、业务副作用、合规要求和失败成本的决策表。

### 写作所需证据

- **已有资料**：n8n 官方文章给出两种调用方向、Agent 组成、Workflow 工具、审批、凭证、版本和 session 日志；文档可核对产品配置细节。
- **需要补做**：搭建一个不连接真实业务账号的本地工单 demo，分别实现纯 Workflow、Agent 直连和 Agent 调 Workflow，记录每个工具的 token、权限、审批和失败重试。
- **适合配图**：Agent 决策层—Workflow 执行层—系统凭证的架构图；两种调用方向的时序图；副作用等级与审批点矩阵。
- **关键未验证点**：preview 版本的持久化、并发、版本回滚和自托管能力可能变化；官方文章没有给出复杂任务的稳定性或成本基线。

## 2. Pydantic AI v2.50.0：让 Agent 用类型化决策做路由，而不是假装“调用了一个工具”

### 热点是什么

Pydantic AI 于 2026 年 9 月 24 日发布 v2.50.0。版本新增 `DecisionModel`，并让 `TypeSafeModel` 建立在决策协议之上：模型可以针对一个文本回答“选择哪个 route、是否满足条件、输出哪个结构”，每个字段对应一个带类型的决策问题，而不是生成一段文本再靠解析或工具调用猜路由。版本还加入按名字询问 route、`decision_route_threshold`、嵌套 route context、工具调用后的 `done` 状态，以及每次决策的 `decide` span；同时增加 `RunContext.in_durable_context` 和 Gemini 3.8 Live 支持。官方 release 把 route 兼容变化列为需要迁移时关注的部分。

原始资料：

- [Pydantic AI：Release v2.50.0（2026-09-24）](https://github.com/pydantic/pydantic-ai/releases/tag/v2.50.0)
- [Pydantic AI Docs：Decision models](https://pydantic.dev/docs/ai/models/decision/)
- [Pydantic AI 仓库](https://github.com/pydantic/pydantic-ai)

### 为什么值得写

很多 Agent 路由仍然依赖“让模型决定调用哪个工具”，结果是路由问题、结构化输出和执行动作混成一次生成，难以观察置信度，也难在低置信时停下来。Pydantic AI 的改动把路由提升成单独协议，并把阈值、context 和 trace 暴露出来。事实是，这是一组 SDK 设计和兼容性变化，不等于所有模型都能稳定做出更好的路由；判断是，它提供了一个值得对照的工程切口：把“决定去哪儿”和“执行什么”拆成两个可评估的阶段。文章可以用客服工单分流做本地测试，比较 tool-call router、枚举输出和 DecisionModel 在错误路由、置信度和可观测性上的差异。

### 建议标题

**Agent 先决定走哪条路：Pydantic AI 的 DecisionModel 解决了什么？**

### 文章梗概

工单要在退款、配送、账户安全三个队列中选一个，直接让模型调用对应工具，会把分类、参数和副作用绑在一次输出里。Pydantic AI v2.50.0 把 route 变成带名字、类型和阈值的 DecisionModel，并为决定发出独立 trace。文章对比 tool-call、枚举输出和 DecisionModel，记录低置信升级、工具副作用和可回放性，说明协议改进不等于模型准确率自动提高。

### 结构提纲

1. **路由为何不该伪装成工具调用**：拆分分类、参数填充、权限检查和副作用四个阶段。
2. **DecisionModel 的类型协议**：解释字段如何变成决策问题、route premise、嵌套 context 和 `done` 状态。
3. **阈值与 None-of-these 怎么工作**：分析 `decision_route_threshold`、不可填充 output 和人工升级路径。
4. **决策 trace 如何进入 Agent 观测**：阅读 `decide` span、`ModelSelectionContext.prompt` 和 durable context hook。
5. **三种路由实现的本地对照**：比较 tool-call、枚举结构化输出和 DecisionModel 的误路由、成本与可回放性。
6. **升级 v2.50.0 的兼容边界**：核对 release 中的兼容说明，列出现有 TypeSafeModel 用户需要重跑的测试。

### 写作所需证据

- **已有资料**：v2.50.0 release 列出 DecisionModel、route threshold、context、done、trace 和兼容变化；官方文档说明决策模型的类型映射。
- **需要补做**：固定同一模型和同一组工单，分别实现三种路由；记录 route 分布、低置信升级、token/延迟、工具副作用和 trace 内容，不能把一次本地实验外推成模型成功率。
- **适合配图**：生成文本—DecisionModel—route—工具执行的状态图；tool-call router 与 typed decision 的对照时序图；阈值与人工升级的决策矩阵。
- **关键未验证点**：不同 provider 对 DecisionModel 的支持、概率校准、复杂嵌套字段成本和 realtime 行为仍需源码与实际运行验证；release 的兼容提示不能替代迁移测试。

## 3. Qwen-Planner-Agent：把 Agent 当成被训练和被改进的系统，闭环能不能真的自进化？

### 热点是什么

Qwen 团队的论文《Qwen-Planner-Agent: A Closed-Loop AI-for-AI Framework for Real-World Mobile Planner Agents》于 2026 年 9 月 24 日发布到 arXiv，9 月 25 日提交记录可见。论文把移动端规划 Agent 放进一个闭环 AI-for-AI 框架：AI for Data 由专门 Agent 生成任务、采集轨迹、筛选和配平数据；AI for Training 结合监督冷启动与混合环境在线强化学习，并提出 CARE；AI for Model-Harness Co-Evolution 用执行证据、失败轨迹、memory、skills、tools 和 sub-agent 协调模型与 harness 的更新。论文称在 MobilePA-Bench 上达到所评估系统中的最佳整体表现，并在工具使用、记忆、skills 和子 Agent 协作上超过基础模型。

原始资料：

- [arXiv：Qwen-Planner-Agent（2609.29892）](https://arxiv.org/abs/2609.29892)
- [项目页：Qwen-Planner-Agent](https://tongyi-mai.github.io/)
- [论文 PDF](https://arxiv.org/pdf/2609.29892)

### 为什么值得写

这篇论文的价值不在于再介绍一个移动端 Agent，而在于把“Agent 变聪明”拆成数据、训练、运行时 harness 和失败证据四条连接起来。事实是，论文提出了共享 action-feedback-verification contract、human-gated data flywheel 和 model-harness co-evolution；判断是，所谓自进化如果没有版本化轨迹、可验证反馈和人工 gate，很容易退化成把错误经验反复写进 memory。文章可以围绕一个移动端购物或外卖流程，画出任务生成到失败回放的闭环，区分论文中的 benchmark 结果、框架机制和仍需独立复现的提升。

### 建议标题

**Agent 怎样越做越聪明？先拆开 Qwen-Planner-Agent 的数据、训练和 Harness 闭环**

### 文章梗概

“把失败轨迹喂回去，Agent 就会自我进化”听起来顺，但一次移动端错误可能来自模型、工具、页面变化、memory 或评测漏洞。Qwen-Planner-Agent 把闭环拆成任务/轨迹数据、混合环境训练和 execution-evidence 驱动的模型-harness 共演。文章用状态机模拟失败样本晋级、回归测试和 memory 撤销，讨论什么证据足以触发更新，以及为什么 human gate 仍不可省。

### 结构提纲

1. **自进化到底改变哪一层**：区分模型参数、任务数据、memory、skills、工具和 harness 的更新。
2. **AI for Data 的任务飞轮**：分析任务生成、交互轨迹、筛选、配平和训练反馈怎样闭环。
3. **AI for Training 的混合环境**：解释监督冷启动、在线 RL、CARE 与真实设备成本之间的取舍。
4. **Execution evidence 如何驱动共同演化**：把运行时证据、失败轨迹、回放和模型/harness 版本连接起来。
5. **移动端 Agent 的评测陷阱**：讨论页面变化、工具版本、任务污染、benchmark leakage 和人工 gate。
6. **搭一个可撤销的小型进化回路**：用模拟界面实现失败样本晋级、回归测试和错误 memory 撤销。

### 写作所需证据

- **已有资料**：论文摘要和项目页公开三段式框架、action-feedback-verification contract、CARE、模型-harness 共演和 MobilePA-Bench 结论。
- **需要补做**：通读论文方法、实验表和附录，核对 benchmark 任务、基线、训练预算和消融；用本地状态机模拟一轮失败轨迹晋级，保存版本与回归结果。
- **适合配图**：数据—训练—部署—执行证据的闭环架构图；单个移动任务的 action/feedback/verification 时序图；模型与 harness 双版本演化图。
- **关键未验证点**：论文的性能提升依赖其数据、训练预算和评测环境，尚无独立复现；“自进化”不代表系统可无监督更新，人工 gate 和失败样本质量仍是瓶颈。

## 4. DAYJOB：为什么 Agent 会做清晰的任务，却做不好“帮我看一下这个”？

### 热点是什么

Surge AI 于 2026 年 9 月 23 日发布 DAYJOB: Healthcare 和 DAYJOB: Finance，作为面向长期职业知识工作的 Agent 评测套件。它把提示从详细步骤缩短到更像同事交代的一句话，把工作环境扩大到平均 20—26 个文件，并要求 Agent 自己判断哪些资料相关、哪些版本过期、交付物是什么。首批包含 130 个专家任务，Finance 任务估计人类平均需要 16.6 小时，Healthcare 约 13.6 小时；Surge 报告最强系统在 Healthcare 任务上的通过率为 24.7%，Finance 为 23.9%。官方示例包括从多份报告、表格和讨论中发现一个被错误放大的 2,600 万美元头寸；数据集、仓库和排行榜已公开。

原始资料：

- [Surge AI：DAYJOB: Can Agents Survive a 9 to 5?（2026-09-23）](https://surgehq.ai/blog/dayjob)
- [DAYJOB GitHub 仓库](https://github.com/surge-ai/dayjob)
- [DAYJOB: Healthcare 数据集](https://huggingface.co/datasets/surgeai/DAYJOB-healthcare)
- [DAYJOB: Finance 数据集](https://huggingface.co/datasets/surgeai/DAYJOB-finance)

### 为什么值得写

DAYJOB 的核心变化是把评测对象从“执行清楚的指令”换成“从模糊请求和混乱资料里定义工作”。事实是，首批任务数量、文件规模、人类时长和通过率来自 Surge 自己的 benchmark；它还指出 GDPval 的提示更长、流程更明确。判断是，这个切口和企业 Agent 的真实落地更接近，但不能只拿 24.7% 和 23.9% 做排行榜新闻。文章可以直接读数据集和 rubric，分析上下文识别、版本判断、跨文件一致性、长期记忆和最终交付质量如何分别计分，再用一个缩小版“基金报告审查”或“医疗随访整理”实验检验短提示是否真的增加了判断难度。

### 建议标题

**Agent 终于遇到真实工作：DAYJOB 为什么把“找对问题”放进评测？**

### 文章梗概

现实任务常只有一句“帮我看一下这个”，真正的工作是找出“这个”指什么、判断哪份资料可信、发现矛盾并交付可用结果。Surge 的 DAYJOB 用短提示、多文件环境、跨天时长和专家 rubric 测这段判断，最强系统通过率仍低于四分之一。文章读数据集和评分字段，再做缩小版回放，说明 benchmark 能揭示什么，不能证明什么。

### 结构提纲

1. **清晰指令测到的是什么**：用 GDPval 与 DAYJOB 对照执行能力和专业判断的差别。
2. **DAYJOB 的任务环境**：检查短提示、20—26 个文件、跨天工作和 47.5/57.5 条 rubric 的结构。
3. **一个真实错误怎样藏在资料堆里**：还原 Finance 示例中单位、截图、表格和报告之间的矛盾发现链。
4. **通过率为何不能直接等于能力**：分析专家 rubric、LLM judge、人类参考交付物、任务难度和厂商自报口径。
5. **用公开数据做一个缩小版评测**：固定模型与预算，比较单文件、清单提示和多文件短提示三种设置。
6. **把评测结果接回 Agent 工程**：讨论上下文选择、长期状态、证据卡、人工 gate 和可回放交付。

### 写作所需证据

- **已有资料**：Surge 文章、DAYJOB 仓库和两个 Hugging Face 数据集公开任务说明、文件规模、估计人类时长、rubric 思路、示例错误和通过率。
- **需要补做**：下载数据集，核对任务/文件/评分字段与参考交付物；固定一套本地模型或记录无法调用模型的限制，先做上下文选择和 rubric 结构分析，再决定是否执行模型回放。
- **适合配图**：短提示—多文件—长期交付的评测架构图；Agent 文件选择和证据链流程图；rubric 从发现问题到最终交付的评分分解图。
- **关键未验证点**：不同模型配置、工具权限、judge 方式和完整任务耗时对分数的影响；官方通过率是 benchmark 报告，不是跨环境通用成功率。

## 5. UiPath Autopilot Agent：浏览器里写 Agent，真正难的是怎样让它先验证再发布

### 热点是什么

UiPath 在 2026 年 9 月 25 日更新 Autopilot release notes，补记一项于 9 月 23 日发布的 Studio Web public preview：Autopilot 作为 coding agent，可以在浏览器里规划、构建、运行、调试和解释自动化项目。针对 Agent 项目，它能生成 prompts、tools、memory，调试运行过程，建立 evaluation sets、evaluators、test cases，并设置 guardrails；官方文档明确要求用户在运行或发布前审查生成内容。它复用 UiPath skills 和 CLI，不需要本地安装；设置页还把工具、skills、knowledge、MCP、个性化和安全网站名单分开管理。部分 RPA、Coded App 和 Function 项目在 Studio Web 目前只能读写文件，不能通过 CLI 发布、运行和验证。

原始资料：

- [UiPath Autopilot Release Notes：September 2026](https://docs.uipath.com/autopilot/other/latest/release-notes/september-2026)
- [UiPath Docs：Autopilot Agent](https://docs.uipath.com/agents/automation-cloud/latest/user-guide/autopilot-agent)
- [UiPath Studio Web 预览文档](https://docs.uipath.com/studio-web/automation-cloud/latest/user-guide/about-studio-web)

### 为什么值得写

这条更新把 coding agent 的能力从“帮我生成几段代码”推进到“生成 Agent 定义、评测和 guardrails，再在同一环境调试”。事实是，UiPath 文档把生成、运行、评测和发布前审查列成不同步骤，也明确标出 Studio Web 的功能缺口。判断是，浏览器内开发环境真正要解决的是验证门，而不是少装一个 CLI：生成的 prompt、工具和 guardrail 只要没有被回放检查，发布按钮就只是把不确定性推给生产。文章可以用一个简单的工单 Agent 对照“直接发布”和“生成—评测—人工审查—发布”两条流程，观察工具权限、测试集覆盖和失败回滚。

### 建议标题

**浏览器里就能写 Agent，但生成完不能直接发布：UiPath Autopilot 的验证门怎么设计？**

### 文章梗概

浏览器里的 coding agent 生成了工单 Agent，prompt、工具、memory 和 guardrail 都齐了，但它是否按权限工作、遇到未知问题会不会升级，还没有证据。UiPath Autopilot Agent 把 scaffold、debug、evaluation、guardrails 和发布前审查放进同一流程。文章对比直接发布与经过评测 gate 的两条链，检查工具权限、测试覆盖、失败回滚和 preview 限制。

### 结构提纲

1. **Coding Agent 生成的对象变多了**：区分 prompt、工具、memory、评测集、guardrail 和运行代码。
2. **Studio Web 的生成—运行—调试链**：还原 Autopilot Agent 如何复用 skills 与 CLI，并标出当前项目类型限制。
3. **发布前验证门应检查什么**：设计工具权限、未知输入、升级路径、guardrail 命中和评测集覆盖。
4. **设置页其实是一张权限图**：分析 tools、skills、knowledge、MCP、trusted/blocked 网站和 AI Trust Layer 的关系。
5. **直接发布与带 gate 的对照实验**：用本地模拟工单 Agent 记录误路由、越权工具、评测漏项和回滚时间。
6. **Preview 功能怎样进入生产**：列出浏览器环境、CLI 不可用、人工审查和治理策略需要补齐的证据。

### 写作所需证据

- **已有资料**：UiPath release notes 与 Docs 公开 Autopilot Agent 的 scaffold、debug、evaluation、guardrails、复用 skills/CLI、设置范围和项目类型限制。
- **需要补做**：阅读 Studio Web 预览文档和示例项目；实现一个脱离真实租户的最小 Agent 定义，生成固定测试集，记录 guardrail、工具审批、失败和人工复核结果。
- **适合配图**：生成—运行—评测—审查—发布的门禁流程图；Autopilot 设置到 Agent runtime 的权限架构图；不同项目类型的能力矩阵。
- **关键未验证点**：public preview 的实际执行环境、CLI 缺口何时补齐、评测是否能阻止发布、AI Trust Layer 的具体策略和审计字段需要在可用租户中核对。

## 暂不建议追的方向

- **把 DAYJOB 的 24.7%/23.9% 当作所有 Agent 的通用成功率**：这是 Surge 自己的 benchmark 报告，模型配置、工具和评分实现都要随数据集一起核对。
- **把 Qwen-Planner-Agent 的“闭环”写成无需人工的自我改进**：论文明确包含 human-gated data flywheel，性能提升依赖特定训练预算、数据和 MobilePA-Bench。
- **把 n8n Agents 写成 Workflow 已经失效**：官方设计恰恰保留两者，值得写的是权限、回放和维护边界。
- **把 DecisionModel 的类型化路由等同于更高模型准确率**：它主要改变协议、阈值和可观测性，准确率需要固定模型和任务后独立测量。
- **把 UiPath Studio Web preview 当成完整生产 IDE**：官方明确列出部分项目只能读写文件，发布、运行和验证能力仍有限。
