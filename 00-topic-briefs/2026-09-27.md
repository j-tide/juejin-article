## 1. Microsoft Copilot 把 Chat、Code 和 Autopilot 放进同一套工作流，长任务的边界在哪里？

### 热点是什么

Microsoft 于 2026 年 9 月 25 日发布新的 Copilot 体验，把 Home、Code 和 Autopilot 放到同一套产品路径里。Home 汇总 Chat 和 Cowork；Code 允许用自然语言构建应用、自动化和工作流，并在租户内的 sandbox 和 Copilot Managed Runtime 中运行；Autopilot 则是持续运行的云端 Agent，拥有自己的 identity、memory、computer 和 workspace，可以监听频道、跟进线程、运行周期任务，并在几天后继续项目。文章还公布了面向 Code、Cowork、Autopilot 的 usage-based billing 和 Agent 365 的费用控制。Home、Code 和 Autopilot 的状态分别是 Frontier rollout、preview 或 private preview，不能当作已经普遍可用的承诺。

原始资料：

- [Microsoft Official Blog：Introducing the new Copilot with Home, Code and Autopilot（2026-09-25）](https://blogs.microsoft.com/blog/2026/09/25/introducing-the-new-copilot-with-home-code-and-autopilot/)

### 为什么值得写

事实是，Microsoft 把一次对话、一次可交付的 Cowork 任务、一个可构建的小应用和一个持续运行的 Autopilot 拆成了不同执行形态，同时让它们共享 Microsoft IQ、插件、权限和租户治理。判断是，真正值得拆的不是产品名称，而是“何时从 Chat 升级到长任务 Agent”：任务状态、独立身份、工作空间、预算、审计和恢复都必须有明确边界。文章可以用供应商评审或客户工单做一条长任务回放，比较单次回答、Cowork 和 Autopilot 的状态持久化、费用归属和人工接管。

### 建议标题

**Copilot 开始替你连续工作：Autopilot 的身份、记忆和预算该怎么管？**

### 文章梗概

同一件事先是问一句进度，后来变成跟进多方、更新文档、几天后继续催办；如果一直按聊天请求处理，状态和权限很快就会丢。Microsoft 新 Copilot 把 Chat、Cowork、Code 和持续运行的 Autopilot 分开，又用租户身份、memory、workspace 和 usage-based billing 串起来。文章用一条供应商评审任务对照三种执行模式，检查状态恢复、费用边界、工具授权、审计和人工接管，区分产品预览与已验证能力。

### 结构提纲

1. **四种工作形态到底差在哪**：把 Chat、Cowork、Code 和 Autopilot 的触发方式、生命周期、交付物和失败处理列成状态表。
2. **Autopilot 为什么需要自己的身份**：分析租户身份、Teams/Outlook 入口、workspace、memory 与用户代理权限的关系。
3. **从一次请求变成长任务**：画出监听事件、计划、工具调用、等待、恢复和回报进度的执行时序。
4. **Managed Runtime 和 Code 的安全边界**：检查 sandbox、租户内运行、插件同步、实时数据访问和治理责任分别落在哪里。
5. **预算不是计费页面的问题**：用 usage-based billing、模型选择和 Agent 365 spending policy 设计任务级成本记录。
6. **什么情况下应回到 Chat 或 Cowork**：按持续时间、外部副作用、状态敏感度和人工审批要求建立升级与降级规则。

### 写作所需证据

- **已有资料**：Microsoft 官方博客公开了四种工作形态、Autopilot 的 identity/memory/computer/workspace、Copilot Managed Runtime、Microsoft IQ、插件注册表和 UBB/FinOps 方向。
- **需要补做**：阅读 Copilot Managed Runtime、Agent 365 费用和权限文档；在没有真实租户时，用本地事件队列模拟“供应商评审”任务，比较一次性请求、可恢复工作流和周期 Agent 的状态记录。
- **适合配图**：Home—Chat/Cowork/Code/Autopilot 的能力分层图；Autopilot 身份与租户系统的权限架构图；长任务从触发到恢复的时序图。
- **关键未验证点**：Autopilot private preview 的实际恢复语义、memory 删除与审计字段、Managed Runtime 的网络/凭证隔离、不同模型自动路由的成本口径都要以可用租户文档或实测为准。

## 2. LiteAgents：如果 Harness 可以一行切换，Agent 的可移植性和真实差异怎么测？

### 热点是什么

LiteLLM 于 2026 年 9 月 25 日发布 LiteAgents 预览 SDK。它用统一的 `query()`、消息类型和工具适配，让同一段 Python 应用在 Deep Agents、Pydantic AI、Claude Agent SDK、Codex 和 OpenCode 之间切换；应用保留模型、工具、MCP 配置和输出处理，`profile.harness` 决定由哪个 Harness 运行 Agent loop。LiteAgents 还提供 harness-specific controls，并可接入 Temporal 让任务在客户端断开或 worker 重启后恢复。官方仓库说明，预览版本使用 GitHub release wheel，包名和运行时依赖仍在调整。

原始资料：

- [LiteLLM Blog：Introducing LiteAgents（2026-09-25）](https://docs.litellm.ai/blog/liteagents-sdk)
- [BerriAI/liteagents GitHub 仓库](https://github.com/BerriAI/liteagents)

### 为什么值得写

事实是，LiteAgents 没有把不同 Harness 的 agent loop 抹平，而是共享模型、工具、MCP 和消息接口，保留各自的 native controls，并把 durable run、operation replay 和外部副作用的幂等责任写进文档。判断是，所谓“可切换”只有在同一任务、同一模型、同一工具和同一预算下对照过，才知道差异来自 Harness 还是默认配置。文章可以用一个查询订单再生成工单的任务，分别跑 Pydantic AI、Claude Agent SDK 和 Deep Agents，记录工具参数、上下文、重试、审批、恢复和最终输出。

### 建议标题

**Agent Harness 能不能像模型一样替换？LiteAgents 的一行切换要付出什么代价**

### 文章梗概

同一套工具和模型，换一个 Agent Harness 后，循环、重试、上下文和恢复策略可能都变了。LiteAgents 预览 SDK 把 Harness 变成 profile 字段，统一工具、MCP 和消息接口，同时保留各框架的原生控制，并可用 Temporal 做持久运行。文章用同一个订单查询任务跑三种 Harness，逐步对照 prompt、tool call、streaming、approval、checkpoint 和外部副作用，判断一行配置切换能共享什么，哪些行为仍必须单独验证。

### 结构提纲

1. **Harness 负责的到底是哪一圈**：从模型请求、上下文、工具调用到结束判断，画出应用、LiteAgents、Harness 和 provider 的边界。
2. **共享接口没有共享循环**：阅读 `ProfileOptions`、`run()`、`query()`、消息归一化和 `harness_options` 的实现。
3. **同一工具在不同 Harness 里会怎样**：固定工具 schema 和模型，比较参数生成、并行调用、错误回传、重试与审批事件。
4. **Temporal 恢复的是哪些东西**：区分 operation replay、checkpoint、conversation history、工作目录和外部副作用的恢复范围。
5. **把“可移植”变成可测的契约**：设计跨 Harness 对照表，记录 token、延迟、工具轨迹、人工介入次数和结果差异。
6. **何时不该切换**：根据原生功能、生态依赖、会话迁移、锁定版本和运维复杂度给出边界。

### 写作所需证据

- **已有资料**：官方博客和仓库给出五/六种 Harness 选择、统一消息和工具、native controls、Temporal 运行、恢复和幂等说明；仓库还列出测试、cookbook 与预览安装方式。
- **需要补做**：本地安装指定 release wheel，锁定同一模型和工具，运行三种 Harness；执行 worker kill、客户端断开和重复 run，核对日志、checkpoint 和操作重放。
- **适合配图**：`your app → LiteAgents → selected harness → LiteLLM → provider` 架构图；同一任务跨 Harness 的调用时序图；可恢复状态与不可恢复副作用的边界图。
- **关键未验证点**：不同 Harness 的默认 system prompt、并发/审批语义、实时 provider 支持和 preview 版本兼容性；没有 live model 条件时不能写成质量或成功率结论。

## 3. Project Swap：Agent 代人谈判时，先解决“它真的懂我吗”

### 热点是什么

Anthropic 于 2026 年 9 月 24 日发布 Project Swap 研究，把 201 名员工和他们的 Claude Agent 放进一个书籍交换市场。参与者先用短对话说明阅读偏好，Agent 再在集中式和去中心化交易规则下寻找交换对象、报价和谈判。五分钟对话生成的偏好排序与参与者排序在 61% 的 pair 上一致；最终市场效率落后于可行最优值的部分中，约 85% 来自 Agent 对个人偏好的错误表示，只有约 15% 来自自由交易规则。研究还比较了不同模型和“ruthless/prosocial”指令，并明确提醒参与者是 Anthropic 的员工、Agent 都是受控且合作的 Claude。

原始资料：

- [Anthropic Research：Project Swap: What happens when agents trade for us?（2026-09-24）](https://www.anthropic.com/research/project-swap)

### 为什么值得写

事实是，这个实验把“多 Agent 协作”从互相分派任务推进到代表不同人的利益进行交易，并把偏好表示、市场规则、消息可见性、速率限制和履约责任拆开测量。判断是，Agent 市场的第一道门可能不是更会砍价，而是先证明 Agent 对委托人的理解足够好；还需要可回放日志、身份登记、失败交易处理和对消息洪泛的限制。文章可以把书籍交换抽象成客服转派、排班互换或供应商报价，讨论局部忠诚与整体效率如何冲突。

### 建议标题

**Agent 开始替人谈判之前，先做一次“你真的懂我吗”测试**

### 文章梗概

如果 Agent 要替人挑供应商、换班或讨价还价，最危险的错误不一定是谈判技巧差，而是它根本没理解委托人的偏好。Anthropic 的 Project Swap 让 201 名员工把 Claude 放进书籍交换市场，结果显示大部分效率损失来自偏好表示，而不是交易规则。文章按“短对话—偏好测试—市场交互—结果回放”重建实验，再把身份、隐私、速率限制、忠诚与公共规则接回企业 Agent 设计。

### 结构提纲

1. **把多 Agent 交易拆成四层**：区分委托人偏好、Agent 表示、市场规则和履约结果。
2. **Project Swap 的实验设计**：还原参与者、书籍池、集中式/去中心化市场、ground-truth ranking 与效率指标。
3. **为什么理解委托人比砍价更关键**：解释 61% pairwise agreement、0.55 市场结果、0.89 可行最优和 85/15 损失分解。
4. **模型与指令分别改变什么**：对照 Haiku、Sonnet、Opus、Fable 以及 ruthless/prosocial 指令，不把内部实验外推到真实市场。
5. **企业 Agent 需要的委托前测试**：设计少量样例决策、偏好回显、人工确认和撤销入口。
6. **市场平台要承担什么责任**：讨论 Agent 身份、消息可见性、spam/rate limit、失败履约、隐私和争议处理。

### 写作所需证据

- **已有资料**：Anthropic 页面给出实验人数、偏好一致性、效率分解、模型比较、协商策略、局限和身份/回放/速率限制建议。
- **需要补做**：通读附录，复算公开公式和 85/15 分解；用小规模模拟实现集中式匹配与 Agent 自由谈判，改变偏好噪声和消息上限。
- **适合配图**：委托人—偏好表示—交易 Agent—市场规则—履约的架构图；集中式清算与去中心化协商的双泳道流程图；效率损失瀑布图。
- **关键未验证点**：实验只覆盖 Anthropic 的员工、合作型 Claude 和低风险书籍交换；高价值交易、恶意 Agent、异构模型和非公开市场的行为没有被验证。

## 4. Surge 用 1,700 个编码任务训练 Kimi K2.7，Agent 进步来自“把最后一步做完”吗？

### 热点是什么

Surge AI 于 2026 年 9 月 24 日发布对 Kimi K2.7 的 post-training 研究：使用 1,700 个 Agentic coding 任务，只做 reinforcement learning，不做 SFT，再用不同 Harness 和外部 SWE 评测检查迁移。Surge 报告 SWE-Marathon 提升 20.0 个百分点、DeepSWE 提升 12.4 个百分点、Terminal-Bench 4 提升 7.6 个百分点；另一页 post-training 记录列出 Terminal-Bench 2.1、Terminal-Bench 3 和 SWE-Bench Pro 的变化。轨迹分析把改进归为四类：记住完整规格、测试需求而不是只测试自己的实现、保护原有行为、在没有参考答案时自己构造 ground truth。成绩和行为归因均来自 Surge 的报告，不能当作独立复测。

原始资料：

- [Surge AI：Hill-Climbing a SWE Agent（2026-09-24）](https://surgehq.ai/blog/hill-climbing-swe-agent-kimi-k-2-7)
- [Surge AI：Post-Training Runs](https://surgehq.ai/post-training)

### 为什么值得写

事实是，Surge 把训练数据、RL 配置、Harness、外部 benchmark 和成对轨迹分析放在同一页，给出了“基础模型知道怎么写，但经常没有把规格、回归和验证做完”的具体案例。判断是，Coding Agent 的提升可能更多来自执行习惯和验证回路，而不是再塞进更多代码知识；但要得出这个结论，还得区分 reward 设计、任务难度、模型本身和 Harness 差异。文章可以从 FastAPI 方法位置、命名参数、布局回归和 Zstandard 自建测试四个案例入手，复现“实现—验证—提交”的最后一公里。

### 建议标题

**Coding Agent 为什么总差最后一步？1,700 个任务里训练出来的四种执行习惯**

### 文章梗概

很多编码 Agent 不是完全不会做，而是漏掉一个规格、只测自己写过的路径、改好新功能却破坏旧行为，最后还把错误的假设当成测试基准。Surge 报告称，Kimi K2.7 用 1,700 个 RL 任务训练后，在多个外部 SWE 评测上提升，轨迹也更短。文章逐个拆四类失败和 reward 设计，再用固定仓库任务做小规模对照，区分训练报告、复现实验和 Harness 差异。

### 结构提纲

1. **“会写代码”与“交付代码”差在哪**：用报告中的失败轨迹划分规格、测试、回归和 ground truth 四个断点。
2. **1,700 个任务怎样进入 RL**：核对任务构成、隐藏检查、pass-to-pass 测试、GSPO、LoRA、上下文和评测 Harness。
3. **四种行为改变的执行链**：复现完整规格、反例测试、保留现有行为和自建验证器的具体案例。
4. **为什么步数变少不等于偷懒**：对照 DeepSWE/Terminal-Bench 的 median trajectory length 与完成质量，分开效率和成功标准。
5. **迁移成绩应该怎样读**：固定模型、任务版本、推理预算和 Harness，区分 Surge 自报结果与可独立复核的实验。
6. **把习惯接回生产 Agent**：设计规格清单、差分测试、回归门禁、未知参考答案和提交前审查。

### 写作所需证据

- **已有资料**：Surge 文章公开了外部 benchmark 变化、三种 Harness 迁移、失败轨迹案例、任务配置和四类行为解释；post-training 页面给出更多 pass@1 数字。
- **需要补做**：下载或整理可公开复现的 SWE 任务，固定一个本地模型和 Harness，分别关闭规格清单、回归测试和自建 ground truth，记录轨迹差异。没有条件时只做源码/报告复核。
- **适合配图**：规格—实现—测试—回归—提交的 Agent loop；四类失败到 reward 的映射图；训练 Harness 与评测 Harness 的对照架构图。
- **关键未验证点**：Surge 的训练任务和奖励权重是否足以解释迁移、外部 benchmark 版本与 Harness 是否一致、较短轨迹是否在所有任务上成立，都需要原始配置和独立复跑。

## 5. Claude Marketplace：当插件、Agent 和服务都能买，治理边界由谁负责？

### 热点是什么

Anthropic 于 2026 年 9 月 23 日发布 Claude Marketplace。官方把连接器和插件、Claude-powered agents/products、服务合作伙伴放到同一个入口；发布时列出超过 2,000 个可用 connectors/plugins，并允许客户用已承诺给 Anthropic 的预算购买 Agent 产品。对构建者，连接器或插件走 MCP 与 Agent Skills，Agent 产品走上架审核，服务商进入 Claude Partner Network。页面把工具发现、采购、连接、部署和企业治理连成一条链，但没有给出所有第三方工具的安全评测、权限细节或运行时隔离保证。

原始资料：

- [Claude by Anthropic：Claude Marketplace（2026-09-23）](https://claude.com/blog/claude-marketplace)

### 为什么值得写

事实是，Anthropic 正在把 Agent 生态从“自己接 MCP”推进到目录、预算、合作伙伴和购买流程；插件/连接器、Agent 产品和咨询服务被放在同一个采购面。判断是，Marketplace 的技术难点不只是分发，而是每个工具的身份、版本、权限、数据流、审计和撤销都要可被企业理解。文章可以从一个工单 Agent 需要接 CRM、知识库和代码仓库的场景出发，比较直接安装 MCP、通过 Marketplace 安装和由平台托管 Agent 三条路径。

### 建议标题

**Agent 插件开始像应用商店一样被采购，MCP 接入后的权限谁来兜底？**

### 文章梗概

过去接一个 MCP 服务器，工程师要自己找仓库、配凭证、看权限和维护升级；Claude Marketplace 把插件、连接器、Agent 产品和服务商放进同一个目录，还允许用承诺消费购买第三方 Agent。文章不把它写成应用商店新闻，而是跟着一个工单 Agent 的接入过程，比较自带 MCP、Marketplace 插件和托管 Agent 的身份、版本、数据流、审核、审计和撤销，找出平台仍没回答的治理问题。

### 结构提纲

1. **从一个工具接入到一次采购**：拆分发现、安装、授权、计费、升级和退出的状态。
2. **Marketplace 的三种商品形态**：比较 connector/plugin、Claude-powered agent/product 与服务合作伙伴的交付边界。
3. **MCP 与 Agent Skills 只解决了什么**：阅读协议和技能声明，区分接口标准、业务权限和运行时信任。
4. **企业安装一个工单插件要留哪些证据**：建立身份、版本、凭证范围、数据去向、工具调用、审批和撤销清单。
5. **采购预算和技术权限会不会脱钩**：分析 committed spend、第三方产品计费、租户管理员和业务负责人之间的控制关系。
6. **Marketplace 上线前后的最低门槛**：提出签名/来源、权限声明、版本回滚、沙箱试用、审计导出和供应商事故响应要求。

### 写作所需证据

- **已有资料**：Anthropic 官方公告给出 2,000+ connectors/plugins、三类供给方、MCP/Agent Skills、承诺预算购买和 Partner Network 路径。
- **需要补做**：阅读 Marketplace、MCP 和 Agent Skills 的开发者文档，核对上架审核、版本更新、权限确认、数据留存和管理员控制是否已有公开字段。
- **适合配图**：Marketplace 目录—租户管理员—Agent runtime—外部系统的信任边界图；插件安装、授权、调用、撤销的生命周期图；第三方 Agent 的供应链检查清单。
- **关键未验证点**：2,000+ 的统计口径、第三方插件的运行隔离、Marketplace 与直接 MCP 安装的权限差异、购买后的审计和退出流程，需要实租户或官方文档进一步核对。

## 今天最值得优先写

推荐先写第 3 题：**《Agent 开始替人谈判之前，先做一次“你真的懂我吗”测试》**。

它发生在 9 月 24 日，材料来自一手研究页面和完整附录，既有 201 名参与者、61% 偏好一致性、85/15 损失分解等可核对数据，也有身份、回放、速率限制和履约失败这些工程问题。它能把“多 Agent 协作”从常见的任务拆分，推进到代理人如何代表不同利益、市场如何约束代理行为，适合做出实验架构图和小规模模拟。Microsoft 与 LiteAgents 更适合随后写产品/SDK 拆解，Surge 题目适合在能固定模型和 Harness 后再做复现实验。

## 暂不建议追的方向

- **把 Microsoft Autopilot 的 preview 说成普遍可用的自主员工**：官方仍在 Frontier/private preview，真实恢复、权限和成本边界要等租户验证。
- **把 LiteAgents 的统一接口等同于统一行为**：每个 Harness 仍保留自己的 loop 和 native controls，切换 ongoing session 也不会自动迁移。
- **把 Project Swap 的 30% 预算信任度外推到普通用户或高价值交易**：参与者是 Anthropic 的员工，Agent、市场和规则都受控。
- **把 Surge 的外部 benchmark 增幅写成独立模型成功率**：这些是发布方报告，必须保留模型、任务、预算、Harness 和评分口径。
- **把 Claude Marketplace 的 2,000+ 连接器理解成 2,000 个经过同等安全审计的工具**：官方公告没有提供统一安全评级、权限细节或隔离保证。
