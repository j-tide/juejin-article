## 1. Google Antigravity 的运行时更新：Agent harness 先解决什么问题？

### 热点是什么

Google AI for Developers 的模型文档在 **2026-09-24 UTC** 更新了 `antigravity-preview-09-2026`。文档把它定义为运行在 Google 托管、隔离 Linux 沙箱中的通用 Agent，可规划、运行代码、管理文件并搜索网页；本次运行时更新明确列出提示缓存、原生代码搜索和按行范围编辑。文档还给出 1,048,576 的输入上下文上限（约 135k 处压缩）和 65,536 的输出上限。这里能确认的是文档中写明的能力和更新时间，尚不能据此推导真实任务的速度或成本收益。

原始资料：

- [Antigravity preview 文档（Google AI for Developers，最后更新 2026-09-24）](https://ai.google.dev/gemini-api/docs/models/antigravity-preview-09-2026?hl=en)
- [Antigravity Agent 文档入口](https://ai.google.dev/gemini-api/docs/agents)

### 为什么值得写

许多 Agent 文章只讨论换哪个模型，却很少拆“模型每次看到什么、改了哪几行、重复任务怎样复用前缀”这些运行时细节。提示缓存、代码搜索和行范围编辑分别对应上下文成本、检索粒度和写入风险，组合起来才构成可长时间工作的 harness。对做 coding agent、知识库 Agent 或工单排查的人来说，更实际的问题是：缓存失效如何处理，搜索结果怎样带证据，局部编辑怎样避免覆盖并发修改。文档没有公开完整实现和基准，这正好可以把已知事实与待验证实验分开。

### 建议标题

**Agent 运行时真正该优化什么？从 Antigravity 的提示缓存、代码搜索和行范围编辑说起**

### 文章梗概

一个 Agent 任务越长，拖慢它的往往不是模型不会想，而是每轮都重复塞上下文、在整份文件里找代码、用整文件覆盖来改动。Google 更新的 Antigravity 预览版把提示缓存、原生代码搜索和按行范围编辑放进同一运行时。文章按一次请求的执行链说明三者分别解决什么，再讨论缓存失效、搜索证据和局部编辑的版本校验。最后设计一个小型代码仓库对照实验，测 token、延迟、命中文件和误改行数；没有 API 条件的部分只写实验方案，不把文档描述当实测结果。

### 结构提纲

1. **从一次长任务开始：上下文、检索和写入分别在哪里消耗成本**——画出 Agent loop，区分模型推理、工具调用和宿主运行时。
2. **提示缓存不是“记忆”**——说明可缓存前缀、动态字段、失效条件和缓存命中错误会怎样污染结果。
3. **原生代码搜索与把整个仓库塞进上下文的差别**——比较符号检索、行号证据、召回不足和过期索引。
4. **行范围编辑为什么更容易做验证**——把补丁、版本号、上下文校验和失败重试串起来。
5. **怎样做一组可复现的 harness 对照**——固定任务、仓库和预算，记录 token、延迟、工具轮数、修改覆盖率与失败原因。

### 写作所需证据

- **已经有**：Google 官方模型文档、能力描述、上下文与输出上限、更新时间。
- **需要补做**：阅读 Antigravity Agent/Interactions API 的请求格式；若能获得 API 访问，使用同一仓库分别关闭缓存、关闭原生搜索、改用整文件写入，记录 token 与延迟；否则明确标注未执行。
- **适合配图**：一张“模型—缓存前缀—代码搜索—行范围补丁—验证”的执行链图；一张缓存命中/失效状态图。
- **关键未验证点**：缓存键和失效策略、代码索引更新时机、行范围编辑的冲突检测、文档所述上下文压缩阈值在真实任务中的行为。

## 2. Google 长视频多 Agent 框架：为什么生成视频要做全局优化？

### 热点是什么

Google Research 在 **2026-09-24** 发布《Automating coherent long-form video generation》。文章介绍一个建立在 Gemini 与 Veo 之上的多 Agent 视频协导演示，围绕 Co-Director、CANVAS、A²RD 和 VQQA 组织多镜头规划、世界状态跟踪和闭环视觉修正。VQQA 会针对提示生成视觉问题，把视觉语言模型的批评转成自然语言“梯度”，反复改写提示并从整条候选轨迹中做全局选择。Google 还给出 10 分钟连续视频示例和多个自建 benchmark 的结果，但详细训练配置、基线和代码需要以各论文为准。

原始资料：

- [Automating coherent long-form video generation（Google Research，2026-09-24）](https://research.google/blog/coherent-long-form-video-generation/)
- [Google Research 2026 年 9 月文章列表](https://research.google/blog/2026/)

### 为什么值得写

把多个模型串起来不等于多 Agent。长视频的难点是前面一个镜头的角色、道具或空间状态会影响几十个镜头之后的结果，单向流水线一旦出错，后面很难知道该回滚哪一步。Google 的材料提供了一个可拆的工程问题：怎样保存世界状态，怎样让评审器指出可执行的修正，怎样避免局部修正破坏全局叙事。它也提醒读者，厂商报告的 benchmark 分数不能直接等同于可复现的生产质量，需要追问数据、基线、采样预算和人工参与比例。

### 建议标题

**长视频为什么不能只靠一条提示词？拆 Google 多 Agent 的世界状态与闭环修正**

### 文章梗概

短视频模型能生成漂亮的几秒画面，却常在角色重现、道具变化和镜头衔接处失控。Google Research 公开的多 Agent 视频框架，把长视频当成带世界状态的全局优化问题：先规划镜头，再维护视觉记忆，最后用 VQQA 生成问题、评审结果并回到提示优化。文章把这条链和普通生成—拼接流水线对照，解释自然语言批评怎样变成反馈、为什么要从整条轨迹选候选，以及哪些环节仍依赖人工和未公开细节，并把状态、评审、回滚思路迁移到业务 Agent。

### 结构提纲

1. **线性视频流水线为什么会累积错误**——用角色漂移、道具错位和上游资产污染说明 credit assignment 问题。
2. **把故事变成可查询的世界状态**——拆解角色、环境、道具和叙事进度如何进入 Agent 上下文。
3. **VQQA 如何把视觉批评变成下一轮动作**——解释问题生成、VLM 评审、提示改写和迭代停止条件。
4. **全局选择为什么比只看最后一版可靠**——对照最后迭代、最佳候选和局部修正破坏全局的一组情况。
5. **从视频框架迁移到业务 Agent**——把状态账本、评审器和回滚点映射到工单、代码和知识库调查。
6. **如何读 benchmark 而不被分数带走**——核对任务构造、基线、采样次数、人工环节和尚未公开的实现。

### 写作所需证据

- **已经有**：Google Research 原文、VQQA 的闭环描述、10 分钟视频说明、四类 benchmark 名称和文章给出的结果。
- **需要补做**：找到 Co-Director/CANVAS/A²RD/VQQA 对应论文和补充材料，核对模型版本、采样预算、人工参与及基线；检查是否有公开代码或数据。
- **适合配图**：多 Agent 视频协同架构图（规划器、世界状态、生成器、评审器、全局选择）；一张“生成—提问—评审—改写—回滚”的闭环流程图。
- **关键未验证点**：各 benchmark 的完整指标、跨模型泛化、10 分钟视频的生成成本、VQQA 的迭代次数，以及没有人工挑选时的质量变化。

## 3. Copilot 把 Slack/Teams 对话接到代码仓库：上下文链和执行边界怎么画？

### 热点是什么

GitHub 在 **2026-09-25** 的 Changelog 中更新了 Copilot for Slack 和 Microsoft Teams。Slack 支持把文件、附件和消息链接作为上下文；Teams 支持内联图片、转发消息和频道/线程历史。Copilot 创建 GitHub 工作项前会检查相似 issue，并保留源讨论与生成工作项之间的链接；用户还可以切换后续消息使用的模型，在 Slack 中设置默认负责人和仓库。更新同时涉及长任务状态、空闲重连、重复回答和旧仓库会话继续执行等可靠性修复，目前仍是 Business/Enterprise 公共预览，且分批开放。

原始资料：

- [Updates to GitHub Copilot for Slack and Microsoft Teams（GitHub Changelog，2026-09-25）](https://github.blog/changelog/2026-09-25-updates-to-github-copilot-for-slack-and-microsoft-teams/)
- [在 Slack 中使用 Copilot coding agent](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-copilot-coding-agent-in-slack)
- [将 Copilot coding agent 集成到 Microsoft Teams](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-copilot-coding-agent-in-microsoft-teams)

### 为什么值得写

这是一个很贴近真实研发和客服场景的 Agent 入口：客户或值班人员先在群聊里发截图、转述和讨论，系统再把证据变成 issue、代码任务或审查请求。难点不在“能不能读取消息”，而在附件如何归属、引用怎样可追溯、相似 issue 如何避免重复、会话断线后谁有权继续操作，以及仓库切换时如何阻止旧任务误写新仓库。官方更新给了功能边界和故障类型，但没有公开完整的上下文拼装和去重算法，适合从事件接入、证据链和长任务状态三个层面拆解。

### 建议标题

**从群聊到 Pull Request，Copilot 怎样把一段讨论变成可追溯的代码任务？**

### 文章梗概

“客户在群里发截图，后端说像旧问题，客服又补了一段视频。”这类信息如果直接丢给编码 Agent，最容易丢的是来源和责任边界。GitHub 把 Slack/Teams 的附件、图片、转发消息和线程历史接入 Copilot，并把生成的工作项链接回原讨论。文章按事件接入、上下文归一化、相似 issue 检查、仓库选择和长任务恢复还原执行链，讨论哪些字段必须保留来源、哪些动作需要权限和预算确认。最后用模拟群聊回放验证重复工单、断线重连和仓库切换；官方未披露的实现不作臆测。

### 结构提纲

1. **群聊输入不是一段字符串**——把文本、图片、附件、转发和线程关系整理成带来源的事件模型。
2. **从上下文到工作项的证据链**——讨论引用、附件哈希、相似 issue 和回链怎样共同防止重复建单。
3. **模型切换、负责人和仓库选择的权限边界**——区分用户偏好、组织策略和 Agent 可执行权限。
4. **长任务断线后谁能继续**——拆解状态、重连、过期回复和旧仓库会话隔离。
5. **用回放而不是演示验证集成**——构造相同讨论的重复发送、图片缺失、线程更新和仓库切换测试。

### 写作所需证据

- **已经有**：GitHub Changelog 的功能、故障修复、可用计划与 Business/Enterprise 预览范围；Slack/Teams 官方集成文档入口。
- **需要补做**：阅读两套集成文档的权限、附件大小、线程范围、issue 创建和 cloud sandbox 条件；用 GitHub API 做一个不写生产仓库的模拟回放。
- **适合配图**：群聊事件到 issue/PR 的带回链数据流图；长任务状态图（queued、running、stale、reconnected、cancelled）。
- **关键未验证点**：相似 issue 的判定逻辑、附件是否进入模型上下文或只保存引用、消息和代码权限的映射、断线后的幂等键及实际滚动范围。

## 4. Shopify 的持续学习回路：Agent 怎样把生产失败变成下一轮能力？

### 热点是什么

PyTorch 在 **2026-09-22** 发布 Shopify GraphQL Agent 的社区版案例文章，页面说明内容改编自 Shopify Engineering；Shopify 原文发表于 **2026-08-05**。文章描述一条从随机生产流量、质量 rubric、人工标注和 judge 校准开始的持续学习回路：先用 autoresearch 优化 prompt、工具定义和 harness，再用多模型批评器、修复提示、SFT 与 GRPO 把难例写回模型权重，最后用 vLLM 服务。Shopify 自报 GraphQL Agent 最高约 2,000 请求/分钟、服务成本降低 96%、提示从约 6,000 压到约 1,500 个 gist token，并在特定负载测试中报告延迟、吞吐和 GPU 数量变化；这些数字目前都是案例方披露，不能当作独立实测。

原始资料：

- [How Shopify built a continual learning loop with PyTorch and vLLM（PyTorch，2026-09-22）](https://pytorch.org/blog/how-shopify-built-a-continual-learning-loop-with-pytorch-and-vllm/)
- [Sidekick's continual learning loop（Shopify Engineering，2026-08-05）](https://shopify.engineering/sidekicks-continual-learning-loop)
- [GEPA：Reflective Prompt Evolution Can Outperform Reinforcement Learning](https://arxiv.org/abs/2507.19457)
- [Agentic Context Engineering](https://arxiv.org/abs/2510.04618)

### 为什么值得写

这是一份少见的生产级“越用越好”路线图，而且把三个经常混在一起的层次分开了：先改 prompt、工具和控制循环，再把稳定的失败修复转成训练数据，最后才更新模型权重。它还把质量 rubric、judge 校准、随机流量和回归评测放在训练之前，说明自进化的核心不是让 Agent 自己改自己，而是让每次改动都能被判断、回放和撤销。文章应明确标注这是 Shopify 的案例叙述，成本和质量提升尚未由外部复现。

### 建议标题

**Agent 怎样越用越聪明？拆 Shopify 把生产失败写回模型的持续学习回路**

### 文章梗概

Agent 上线后，用户纠正、工具失败和含糊请求每天都在发生；如果只停在工单和 Slack 里，系统不会进步。Shopify 公开的 GraphQL Agent 案例把失败压成持续学习回路：先用 rubric 和 judge 定义“做对”，再用 autoresearch 改 harness，接着让批评器和人工把难例修成轨迹，用 SFT/GRPO 更新专用模型，最后通过 gist 压缩和 vLLM 降成本。文章解释质量契约、失败回放、训练数据和模型更新的关系，并给出闭环；数字只作自报结果。

### 结构提纲

1. **先定义“做对”再谈自进化**——从 rubric、随机流量和 Cohen’s kappa 说明 judge 的上限与校准。
2. **先改离散的 harness，再动模型权重**——比较 prompt、工具定义、检索和控制循环的 autoresearch。
3. **失败如何变成可训练轨迹**——拆解 hard negative、批评器、arbiter、hinting、人工兜底和 SFT/GRPO。
4. **训练出来还要能服务**——解释 gist token、提示压缩、vLLM 连续批处理与负载测试指标。
5. **自进化系统怎样避免漂移**——设计版本、回放集、灰度、质量门禁和撤销路径，映射到工单调查 Agent。

### 写作所需证据

- **已经有**：PyTorch/Shopify 案例全文、公开引用的 GEPA/ACE/GRPO 论文、GraphQL Agent 的请求规模和案例方报告的成本/延迟/吞吐数字。
- **需要补做**：追踪 Shopify Engineering 原文与案例版本差异；实现一个小型合成工单闭环，比较只改 prompt、SFT、GRPO 三条路径；记录 judge 与人工的一致性、回归集变化和撤销成本。
- **适合配图**：生产失败→judge→修复轨迹→SFT/GRPO→灰度服务→新失败的飞轮图；一张“harness 改动与权重更新”的分层图。
- **关键未验证点**：基础模型与训练硬件、训练数据规模、judge 与线上业务指标的相关性、96% 成本估算假设、长期漂移和灾难性遗忘控制。

## 今日优先写作建议

优先写 **“Agent 怎样越用越聪明？拆 Shopify 把生产失败写回模型的持续学习回路”**。它发生在近 7 天内，原始材料最完整，既有真实产品的执行链，也能自然连接到读者正在做的工单、客服和知识库 Agent。文章可以把“自进化”拆成质量定义、harness 优化、训练闭环和服务成本四个可验证层次；同时，官方明确是案例方自报结果，适合在正文里保留证据边界，避免把营销数字写成普遍结论。若希望更贴近 Agent 运行时实现，则第二选择是 Antigravity，重点做缓存、检索和局部写入的对照实验。
