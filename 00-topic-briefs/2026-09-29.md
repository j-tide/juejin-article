## 1. NVIDIA Open Agent Safety Platform：把 Agent 的边界从提示词搬到运行时

### 热点是什么

NVIDIA 在 **2026-09-28** 发布 Open Agent Safety Platform，并在同日技术博客公开参考架构。软件侧的 **OpenShell** 是 Apache 2.0 开源的 Agent 运行时，在沙箱中通过内核级隔离、声明式 YAML 策略、Landlock、seccomp、网络代理和凭证配置限制文件、进程、网络与模型访问；硬件侧的 **Sentry** 运行在 BlueField-4 DPU 上，作为 Agent 之外的监控与执行层，关联 Agent 交互、策略决定和工具/数据访问。NVIDIA 宣称 Sentry 可以在毫秒级隔离越界 Agent，这个速度和硬件效果目前属于厂商描述。

原始资料：

- [NVIDIA Open Agent Safety Platform 技术博客（2026-09-28）](https://developer.nvidia.com/blog/nvidia-open-agent-safety-platform-a-reference-for-continuous-in-silicon-agent-monitoring/)
- [NVIDIA OpenShell 官方文档](https://docs.nvidia.com/openshell/latest/about/overview)
- [OpenShell 安全策略源码](https://github.com/NVIDIA/OpenShell/blob/main/architecture/security-policy.md)

### 为什么值得写

**事实**：OpenShell 已把文件、网络、进程和凭证访问拆成不同控制面，静态策略在创建沙箱时锁定，网络策略可以热更新；Sentry 则试图把监控点放在 Agent 和宿主之外。**我的判断**：这比在 system prompt 里反复提醒“不要越权”更接近生产安全工程，但它仍然依赖策略作者写对权限、硬件路径和完整威胁模型。对工单 Agent、coding agent 和数据分析 Agent 来说，最值得拆的是“策略如何到达执行点、谁能修改策略、越界以后哪些已发生的动作无法撤回”，而不是宣传语里的“毫秒级”。

### 建议标题

**给 Agent 上两道门：NVIDIA OpenShell 和 Sentry 怎样把权限从提示词搬到运行时？**

### 文章梗概

Agent 一旦能读代码、访问数据库或调用外部 API，靠提示词提醒“只能查订单、不能碰生产”就不够了。NVIDIA 公开的 OpenShell/Sentry 把约束拆成两层：OpenShell 在沙箱内执行文件、进程、网络和凭证策略，Sentry 在独立 DPU 上观察并拦截越界行为。文章追踪工具调用中的策略加载、内核限制、代理决策、审计记录和隔离动作，比较静态权限与热更新边界，再用本地 OpenShell 测文件、网络和凭证访问。硬件效果和“毫秒级”只按官方材料记录。

### 结构提纲

1. **为什么提示词不是权限系统**——把任务目标、工具能力、系统权限和已发生副作用分开。
2. **OpenShell 的策略怎样落到内核和代理**——阅读 YAML、Landlock、seccomp、网络代理与凭证 profile 的执行链。
3. **静态控制与动态控制的取舍**——比较沙箱创建时锁定的文件/进程限制和可热更新的网络策略。
4. **Sentry 的 out-of-band 位置解决什么问题**——分析独立监控、身份治理、隔离动作与硬件依赖。
5. **从最小实验判断边界是否真的有效**——固定 Agent、工具和权限，测试越权读取、外连、凭证注入和策略更新。

### 写作所需证据

- **已经有**：NVIDIA 技术博客、OpenShell 文档和公开的安全策略源码，能核对控制层、策略域和动态更新范围。
- **需要补做**：在本地 Linux 环境安装 OpenShell，跑最小沙箱；读取策略加载、网络代理和审计代码；若无 BlueField-4，明确无法验证 Sentry 的硬件路径。
- **适合配图**：Agent—OpenShell 沙箱—内核/代理—外部服务—Sentry DPU 的分层架构图；一次越权请求从策略拒绝到隔离的时序图。
- **关键未验证点**：Sentry 的实际检测信号、隔离延迟、策略更新的竞态、宿主和供应链被攻破后的剩余风险，以及“兼容其他硬件”的具体条件。

## 2. GitHub Security Lab 的 Android 审计 Agent：漏洞发现怎样拆成可复用 Taskflow

### 热点是什么

GitHub Security Lab 在 **2026-09-28** 公开了用开源 Taskflow Agent 审计 Android 应用的过程。团队报告已发现并披露 **24 个 Android 漏洞**，把审计拆成可组合的 YAML 任务流：先收集并区分移动端入口，再按组件和入口分类漏洞类型，结合严格提示与多次运行的宽提示寻找复杂漏洞。文章给出 Codespaces 运行方式 `./scripts/audit/run_mobile.sh myorg/myrepo`，结果写入 SQLite；同时明确说 LLM 擅长发现候选，但不擅长判断严重性，需要研究员、调试器和 PoC 复核。

原始资料：

- [How we found 24 Android vulnerabilities using our open source AI security agent（GitHub Security Lab，2026-09-28）](https://github.blog/security/how-we-found-24-android-vulnerabilities-using-our-open-source-ai-security-agent/)
- [GitHub Security Lab Taskflow Agent](https://github.com/GitHubSecurityLab/seclab-taskflow-agent)
- [Android 审计 Taskflow](https://github.com/GitHubSecurityLab/seclab-taskflows-fuzzing)

### 为什么值得写

**事实**：Taskflow 把一次大而模糊的安全审计切成入口识别、漏洞分类、重复运行和结果落库，案例中包含跨组件逻辑漏洞，并由研究员确认和披露。**我的判断**：可复用的价值不在于“模型找到了 24 个”，而在于把安全研究经验写成版本化流程，让 Agent 在每个阶段都有明确输入、输出和停止条件。这个思路可以迁移到工单排查：先定位入口，再查调用链，再要求证据和复现，而不是让 Agent 一次性给结论。

### 建议标题

**Agent 找到漏洞只是第一步：GitHub Security Lab 如何把 Android 审计拆成可复用 Taskflow**

### 文章梗概

安全审计最怕让 Agent 自由发挥而漏掉关键入口，也怕把所有漏洞类别塞进一条提示词而得到无法复现的候选。GitHub Security Lab 的 Android Taskflow 把工作拆成入口收集、移动端筛选、漏洞分类、多次运行和 SQLite 结果查询，并用 PoC 与人工研究员判断严重性。文章逐个追踪任务输入输出，解释严格提示与宽提示为何并行，以及发现漏洞、证明可利用、评估影响为何要分成三道门。最后把结构改写成工单排查模板。

### 结构提纲

1. **从整库扫描改成入口清单**——说明攻击面定位如何降低上下文噪声和漏检。
2. **把漏洞类别写成任务流约束**——拆解 YAML 任务的输入、输出、依赖和组件范围。
3. **严格提示与宽提示为什么要并行**——比较重复运行、召回率和误报的关系。
4. **候选、PoC、严重性不是同一个结果**——用 OsmAnd/Wikipedia 案例说明复现和影响判断的必要性。
5. **如何把安全 Taskflow 迁移到工单 Agent**——映射入口、证据、复现、人工确认和结果落库。

### 写作所需证据

- **已经有**：GitHub 原文、Taskflow Agent 仓库、审计脚本入口、两类 Android 漏洞实例和作者对误报/严重性限制的说明。
- **需要补做**：阅读 `gather_mobile_entry_point_info.yaml`、`classify_application_local.yaml` 和结果写库代码；在一个无敏感数据的示例 Android 项目上跑完整流程。
- **适合配图**：入口发现→组件分类→漏洞候选→PoC→人工确认的流水线图；一个 Taskflow 的输入输出契约图。
- **关键未验证点**：24 个漏洞的独立复核范围、不同模型和重复次数对召回/误报的影响、SQLite 结果是否支持增量复查，以及中型仓库实际 token 和运行成本。

## 3. gh-aw 的 Issue Arborist：Agent 失败了 34 次，为什么自动化仍然可信？

### 热点是什么

GitHub Agentic Workflows 在 **2026-09-28** 发布了一次 “Agent of the Day” 实例：Issue Arborist 每天读取 `github/gh-aw` 最近 100 个开放 issue，找出没有父 issue 的相关问题，创建跟踪父 issue、建立子 issue 关系并发布讨论摘要。该任务默认只读 issue 权限，写入通过 `safe-outputs` 的独立任务完成。9 月 28 日这次运行消耗约 63.2k tokens 和 11.6 AIC，34 次 `link_sub_issue` 因触发上下文不匹配失败，但已成功创建的两个父 issue 和讨论没有被回滚，审计报告把失败标为 critical。

原始资料：

- [Agent of the Day – September 28, 2026：Issue Arborist](https://github.github.io/gh-aw/blog/2026-09-28-agent-of-the-day/)
- [GitHub Agentic Workflows 仓库](https://github.com/github/gh-aw)

### 为什么值得写

**事实**：这不是一篇只展示成功截图的案例，日志里明确留下了工具调用失败、成功输出和审计结果三种状态。**我的判断**：对自动化系统来说，“部分成功且可追踪”比“任何一步失败就全部回滚”更适合 issue 整理、报告生成和工单聚合，但前提是每个输出都幂等、可定位、可重试。这个真实运行也提供了一个很好的反例：Agent 完成了主要工作，不代表整次任务成功，最终状态必须按输出拆开统计。

### 建议标题

**Agent 失败了 34 次，为什么这次自动化仍然值得信任？拆 gh-aw 的 safe outputs**

### 文章梗概

自动化系统最容易被误判：界面显示绿色，实际有工具调用失败；或者一步出错就回滚所有结果。GitHub 公开的 Issue Arborist 运行记录显示，Agent 整理出两个问题簇，但 34 次子 issue 链接因上下文不匹配失败，审计报告如实标红，已成功的父 issue 和讨论仍保留。文章从 Markdown 编译、只读 Agent job、safe outputs 和审计记录入手，解释部分成功、幂等、重试与人工接管如何组合，并把语义迁移到飞书工单聚合。

### 结构提纲

1. **一次 Agent 运行到底有哪些结果**——区分任务状态、工具调用状态和外部写入状态。
2. **从 Markdown 到 GitHub Actions**——阅读 frontmatter、编译产物和最小权限配置。
3. **safe outputs 为什么要独立于 Agent job**——分析只读执行、验证写入和按输出提交。
4. **34 次失败如何不污染已完成结果**——讨论幂等键、上下文错误、重试和部分成功。
5. **审计报告怎样成为交付的一部分**——设计对工单 Agent 有用的状态表、告警和人工接管规则。

### 写作所需证据

- **已经有**：Issue Arborist 原文、一次真实运行的 token/AIC、失败工具调用和成功输出、gh-aw 仓库的安全/权限说明。
- **需要补做**：检查 `Issue Arborist` 工作流源文件和编译后的 lock 文件；在测试仓库中人为制造一个 safe output 失败，验证其他输出是否保留。
- **适合配图**：Agent job 与 safe-output job 分离的执行架构图；多输出状态机（pending、applied、failed、retryable、needs-review）。
- **关键未验证点**：safe outputs 的幂等实现、重试上限、跨任务回滚能力、AIC 计费定义，以及真实生产仓库的权限最小化配置。

## 4. PriceBench：让 Agent 替你订酒店之前，先测它会不会被列表顺序牵着走

### 热点是什么

论文 **PriceBench** 在 **2026-09-25** 提交 arXiv，提供了一个用选择行为测量 LLM 购买偏好的诊断基准。作者构造了来自纽约 179 家真实酒店的 3,600 个二选一/三选一任务，测试 8 家提供商的 28 个模型，并用 logit choice model 估计价格、质量和品牌权重。论文报告：5 个模型在温度 0 下几乎固定选择第一项；其余模型的价格—质量取舍差异很大，按照同一任务估计的平均入住价格从 247 美元到 393 美元。作者同时公开任务、代码和 28 组响应，但明确指出工具增强、多轮 Agent 和真实订房流程尚未测试。

原始资料：

- [PriceBench 论文（arXiv，2026-09-25）](https://arxiv.org/abs/2609.31468)
- [PriceBench 代码与任务集](https://github.com/Pashasan/pricebench-emnlp)

### 为什么值得写

**事实**：PriceBench 不把“回答像不像人”当作购买 Agent 评测，而是从重复选择中估计偏好、位置锁定和价格敏感度，并公开完整响应集。**我的判断**：当 Agent 替用户排序商品、订房或选供应商时，模型自身的稳定偏好会变成真实的金钱结果；只测任务成功率，可能完全看不到“第一项偏置”或对品牌的隐性倾向。它给工程师一个可落地的上线前检查，但不能直接推出真实多轮交易中的行为。

### 建议标题

**让 Agent 替你订酒店之前，先测它会不会被列表顺序牵着走**

### 文章梗概

当 Agent 替用户订酒店、挑套餐或选供应商时，任务成功率看不到它如何权衡价格、质量、品牌和列表顺序。PriceBench 用 3,600 个酒店选择任务和 logit choice model，把隐含偏好变成可测参数：有些模型几乎总选第一项，有些模型在相同任务上花出不同价格。文章重建二选一/三选一实验，解释位置锁定、价格系数和稳健性检查，再设计带工具调用的商品 Agent 回放，讨论何时改排序、换模型或让用户确认。论文未覆盖真实多轮订房，结论不越界。

### 结构提纲

1. **为什么成功率看不见购买偏好**——把“完成订房”与“选了什么、为什么选”分开。
2. **PriceBench 的选择实验和 logit 模型**——说明任务构造、随机化顺序和参数识别。
3. **位置锁定与价格—质量权衡**——解读第一项偏置、价格敏感度和品牌系数。
4. **稳健性与可复现材料**——复跑公开代码，比较提示格式、采样和选项数量变化。
5. **从离线选择到真实工具 Agent**——设计商品检索、排序、确认和审计的上线前门禁。

### 写作所需证据

- **已经有**：arXiv 论文、3,600 个任务、代码和 28 组响应；论文还提供位置锁定、价格跨度和多种格式稳健性结果。
- **需要补做**：固定一个模型版本重跑公开任务；加入价格/质量平局、随机排序和多轮工具调用，记录选择、解释和最终费用。
- **适合配图**：选项随机化与选择记录的数据流图；模型在“决断程度—价格偏好”二维图上的位置示意。
- **关键未验证点**：论文模型版本与当前 API 是否一致、酒店数据的时间有效性、真实工具结果排序的影响，以及多轮对话中偏好是否稳定。

## 5. Claude Sonnet 5.5：模型更快了，Agent 就会更便宜吗？

### 热点是什么

Anthropic 在 **2026-09-28** 发布 Claude Sonnet 5.5，官方称其输出速度比 Sonnet 5 快 30% 以上、同价位下多数任务成本最高可降 30%，API 价格为每百万输入 token 2 美元、输出 10 美元、缓存读取 0.20 美元；上下文窗口 1M、最大输出 128K。官方报告 Terminal-Bench 4.0 为 70.6%，Sonnet 5 为 10.3%，并说明 effort、工具调用、缓存和安全回退会改变成本。GitHub 同日把模型加入 Copilot，称早期测试中步骤、token 和工具调用更少。以上性能和成本数字都是 Anthropic/GitHub 及合作方披露，不能替代独立复测。

原始资料：

- [Introducing Claude Sonnet 5.5（Anthropic，2026-09-28）](https://www.anthropic.com/claude-sonnet-5-5)
- [Prompting Claude Sonnet 5.5（官方平台文档）](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)
- [Claude Sonnet 5.5 in GitHub Copilot（GitHub Changelog，2026-09-28）](https://github.blog/changelog/2026-09-28-claude-sonnet-5-5-in-github-copilot/)

### 为什么值得写

**事实**：Sonnet 5.5 把 effort、initiative、工具回合和缓存读写暴露成影响任务成本的变量，迁移文档还要求关注 `between_tools` 等调用行为。**我的判断**：模型降价只是账单的一部分；如果更快的模型开始主动多跑几次工具、做更多检查，单次任务未必更便宜。与其复述 benchmark，不如把“模型—effort—工具回合—缓存—最终交付”放进同一张成本表，对 coding agent 和工单 Agent 都有直接参考价值。

### 建议标题

**模型更快了，Agent 就会更便宜吗？拆 Claude Sonnet 5.5 的 effort、工具回合与成本**

### 文章梗概

新模型发布时，大家会先看 benchmark 和 token 价格，但 Agent 真正花钱的单位是完成一次任务：调用几轮工具、检查多少次、缓存命中多少、失败后重试几次。Sonnet 5.5 同时公开 effort、工具使用、缓存价格和 Terminal-Bench，适合把能力与账单放在一起。文章区分单价、token 数量和耗时，比较不同 effort 的 coding 回合，解释 `between_tools` 迁移，再用同一组任务做成本—质量—延迟对照。benchmark 只作待复核基线。

### 结构提纲

1. **从模型价格切换到任务成本**——定义输入/输出 token、缓存、工具调用、重试和人工等待。
2. **effort 和 initiative 如何改变执行轨迹**——比较低、中、高 effort 下的回合数、检查动作和停止条件。
3. **Terminal-Bench 分数能说明什么**——拆任务定义、评分方式、模型配置和不能外推的部分。
4. **迁移到 Sonnet 5.5 时哪些接口会变**——核对 `between_tools`、JSON、进度更新和工具调用文档。
5. **为自己的 Agent 建立成本—质量回放**——固定任务、预算、工具和评测标准，记录每一步的 token、时间、结果和失败原因。
