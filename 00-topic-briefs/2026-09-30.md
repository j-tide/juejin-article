## 今日判断

这几天的新材料没有集中在“又一个更大的模型”，而是开始回答 Agent 真正落地时的几个硬问题：科研假设怎样进实验闭环，长任务怎样管理上下文，跨界面操作如何复用，回答怎样保留工具来源，以及生成模型怎样在不改主模型的情况下被控制。下面五个方向都有一手材料，但各自的证据边界不同：论文结果、厂商内部评测、公开轨迹和湿实验验证不能混成一件事。

## 1. Microsoft Quine：科研 Agent 怎样把模型、工具和实验接成一个闭环

### 热点是什么

Microsoft Research 在 **2026-09-29** 发布 Project Quine 的介绍（文章发布日期同为 9 月 29 日）。Quine 由两部分组成：跨基因组、蛋白质、化学、细胞状态和生物成像等尺度的生物学世界模型，以及连接编排/推理模型、科学工具、文献、实验室和科学家的交互式 harness。微软与 Broad Institute 合作，用它筛选可能改变胰腺癌细胞状态的化合物，并把排名靠前的候选交给多种湿实验验证。微软称从缩小候选空间到确定实验对象用了一个周末，同时强调 Quine 仍是研究技术，不能直接用于临床。

原始资料：

- [Introducing Quine: An AI research system designed for the complexity of biology（Microsoft Research，2026-09-29）](https://www.microsoft.com/en-us/research/blog/introducing-quine-an-ai-research-system-designed-for-the-complexity-of-biology/)

### 为什么值得写

**事实**：Quine 的交付物不是一段科研问答，而是“问题→候选假设→实验设计→测量结果→下一轮问题”的闭环，世界模型和 harness 被放在同一条反馈链里；PDAC 案例给出了候选排序和湿实验验证的叙述。**我的判断**：这提供了一个比“让 Agent 查论文”更接近真实科研的系统切口，关键不在模型是否永远正确，而在它怎样把不确定的预测变成可审查、可排队、可复做的实验。文章也能把这种闭环映射到工单 Agent 的“证据→排查假设→验证查询→经验更新”。

### 建议标题

**模型给候选、实验给答案：Microsoft Quine 怎样把科研 Agent 做成闭环？**

### 文章梗概

科研 Agent 真正难的地方不是读完一篇论文，而是把一个问题变成可验证的候选，再把实验结果送回下一轮决策。Quine 将生物学世界模型与工具编排、文献检索和湿实验团队放进同一条环路，微软还用胰腺癌细胞状态案例说明候选排序如何进入实验。文章从一次科学问题的状态流开始，拆开模型、harness、工具和科学家各自负责什么，再讨论实验反馈如何成为新证据，以及“预测命中”与“科研结论”之间为什么必须留出人工复核。

### 结构提纲

1. **科研问题为什么不能只交给一次模型调用**——把问题定义、候选生成、实验设计和结论确认拆成不同状态。
2. **Quine 的世界模型与 harness 如何分工**——根据公开架构说明多模态表示、编排模型、文献和科学工具的边界。
3. **从候选排序到湿实验验证**——复盘 PDAC 案例中哪些是模型输出、哪些是实验事实、哪些仍是微软的内部叙述。
4. **实验结果怎样回到下一轮**——设计测量、置信度、失败原因和新假设的结构化回写方式。
5. **把科研闭环迁移到工单 Agent**——对应历史工单、代码阅读、只读查询、复现和人工确认的交付链。

### 写作所需证据

- **已经有**：Microsoft Research 的系统分层、跨模态范围、PDAC 案例、湿实验验证和研究用途限制。
- **需要补做**：阅读 Quine 公开页面和 Fellows 资料，确认是否公开模型接口、数据格式、工具编排协议和置信度输出；对可公开材料做一次“问题—假设—证据—决策”状态建模。
- **适合配图**：科学家→问题解析→世界模型/文献/工具→候选排序→湿实验→测量回写→下一轮问题的闭环架构图；模型预测与实验事实的证据边界图。
- **关键未验证点**：世界模型的训练数据和实际结构、候选排序的独立复现、实验选择是否有随机对照，以及“一个周末”描述中哪些步骤由系统自动完成。

## 2. Continuous Context Management：上下文每轮都压缩，Agent 会更省吗？

### 热点是什么

论文 **Continuous Context Management（CCM）** 于 **2026-09-28** 提交 arXiv。它不等到上下文达到阈值才压缩，而是每一轮同时输出一个更新后的 memory 和环境 action；下一轮只保留原始任务、memory 与最新 observation，不再把完整历史塞回提示词。作者在 TerminalBench-2 上用 Claude Sonnet 4.6、Claude Opus 4.6、GLM-5 和 Kimi K3 做无微调测试，报告累计输入量和活动提示词大小明显下降，但多数模型的任务成功率也下降，Kimi K3 的成功率基本保持。论文还用带完整历史的 privileged distillation 配合 GRPO 改进开放模型，并在 WebShop 与 Endless Terminals 上做了对照。

原始资料：

- [Continuous Context Management（arXiv:2609.35540，提交于 2026-09-28）](https://arxiv.org/abs/2609.35540)

### 为什么值得写

**事实**：CCM 把“压缩”从偶尔触发的维护动作改成 Agent 每轮都要完成的输出，并同时评估提示词大小、累计输入用量和任务成功率；论文明确报告了模型之间不同的收益和损失。**我的判断**：这比单纯比较上下文窗口大小更接近生产问题：省下的输入 token 是否值得丢掉一部分历史，取决于任务、模型和 memory 更新质量。文章可以把压缩当成一个有状态的工具接口来设计，而不是把摘要当作不可追踪的黑盒。

### 建议标题

**上下文每轮都压缩，Agent 反而更省吗？拆 Continuous Context Management**

### 文章梗概

长任务越跑越贵，最直接的办法是定期摘要，但摘要往往把下一步需要的细节一起删掉。Continuous Context Management 把压缩改成每轮动作：Agent 必须维护一份 memory，再用原始任务、memory 和最新观察继续工作。文章用一个反复查日志的 Agent 对比完整历史、阈值压缩和 CCM，再比较论文结果，最后给出 memory 版本和丢失信息的记录方法。论文结果按作者配置理解，不外推成所有模型都适用。

### 结构提纲

1. **完整历史为什么会同时拖慢和污染长任务**——拆输入 token、活动提示词、旧观察和真正需要的状态。
2. **CCM 每轮究竟保存什么**——按照论文定义区分原始任务、memory、observation 和 action，并画出单轮状态转移。
3. **省 token 与丢能力如何同时发生**——解读 TerminalBench-2 中不同模型的成功率、输入量和模型差异。
4. **privileged full-history distillation 在补什么**——说明训练时看完整历史、执行时看压缩 memory 的信息不对称。
5. **把压缩做成可审计组件**——设计 memory schema、版本、丢弃原因、回放和人工恢复入口。

### 写作所需证据

- **已经有**：论文的 CCM 定义、TerminalBench-2 模型配置、GRPO 与 privileged distillation 方法，以及 WebShop/Endless Terminals 的对照结果。
- **需要补做**：下载论文正文和附录，核对每个任务的上下文预算、压缩提示和评分方式；在一个本地脚本 Agent 上实现三种策略，先用确定性模拟观察，再决定是否需要真实模型调用。
- **适合配图**：完整历史、阈值压缩、每轮 CCM 三条执行链的对照图；memory 版本从生成、读取、更新到回滚的状态机。
- **关键未验证点**：论文是否公开实现和数据、memory 漏掉哪些类型的信息、不同任务的压缩频率是否需要自适应，以及训练时的完整历史能否代表生产分布。

## 3. Holo4：为什么一个 Agent 要同时会点屏幕、写代码和调 MCP？

### 热点是什么

H Company 在 **2026-09-28** 通过 Hugging Face Team Article 发布 Holo4。模型有 27B dense 和 35B-A3B MoE 两种规格，可以在 GUI、代码沙箱、MCP、API、桌面和 Android 环境中完成任务；团队称同一个模型、同一套调用方式覆盖这些界面。其 Agentic Task Factory 已生成约 10,000 个网页、MCP 和桌面任务，训练和 harness 会根据任务失败原因迭代。H Company 同时公开了 7,366 条 Holo4 27B/35B-A3B 轨迹，包含每一步的推理、动作、工具结果和截图。文章报告 Holo4 27B 在 OSWorld 2.0 上为 61.7%，但闭源对照、成本和部分基准使用了不同版本、子集或厂商自己的 harness。

原始资料：

- [Holo4: powering generalist computer-use agents（H Company，2026-09-28）](https://huggingface.co/blog/Hcompany/holo4)
- [Hcompany/trajectories：公开 Agent 轨迹数据集](https://huggingface.co/datasets/Hcompany/trajectories)
- [Hcompany/Holo4-27B：模型卡](https://huggingface.co/Hcompany/Holo4-27B)

### 为什么值得写

**事实**：Holo4 不把“电脑操作”限定为截图点击，而是让 GUI、代码、MCP 和 API 成为同一任务中可以切换的执行接口；公开轨迹还保留了动作、工具返回和截图，便于逐步回放。**我的判断**：它最值得拆的不是 27B 是否追平某个闭源模型，而是训练数据、任务工厂、记忆、shell 和 harness 如何共同决定一个 Agent 能不能跨界面完成工作。公开轨迹也给了工程师一个检查“模型错了还是环境错了”的入口。

### 建议标题

**会点屏幕还不够：Holo4 为什么要把 GUI、代码、MCP 和 API 放进同一个 Agent？**

### 文章梗概

一个真实任务经常先在网页上找信息，再写脚本处理数据，最后调用业务 API。若每换一种接口就换一个模型，状态、权限和失败恢复都会被切断。Holo4 把 GUI、代码、MCP 和 API 放进同一个执行回路，并公开数千条带截图和工具结果的轨迹。文章从一条跨界面任务开始，拆出模型、harness、任务工厂和环境的职责，再用公开轨迹回放“动作选择—观察—记忆—下一步”的链路，最后把厂商自测与可独立复核的部分分开。

### 结构提纲

1. **跨界面任务为什么不能只靠一个点击模型**——用网页检索、脚本处理和 API 提交说明接口切换带来的状态问题。
2. **Holo4 的统一动作空间是什么**——整理 GUI、代码、MCP、API、桌面和 Android 的观察与动作格式。
3. **Agentic Task Factory 怎样制造可验证任务**——分析从文档/截图生成环境、任务和验证器的流程。
4. **公开轨迹能检查哪些失败**——选取一条轨迹，区分模型决策、工具返回、环境状态和 harness 记忆问题。
5. **分数、成本和复现边界**——核对 OSWorld 2.0、AutomationBench 的版本/子集/harness 差异，并设计自己的回放指标。

### 写作所需证据

- **已经有**：Holo4 发布说明、27B/35B-A3B 规格、约 10,000 个任务、7,366 条轨迹、OSWorld 2.0 分数和 harness 迭代描述。
- **需要补做**：下载公开轨迹的 `data/index.json` 与一组完整 JSON，统计成功/失败、步骤数、工具调用和 token；在可用环境中运行模型卡示例，不能把厂商 API 结果写成独立评测。
- **适合配图**：同一任务在 GUI、shell、MCP、API 之间切换的执行架构图；轨迹回放时 observation→action→tool result→memory 的时序图。
- **关键未验证点**：公开轨迹是否覆盖报告分数的全部任务、模型卡和 API 版本是否一致、工具权限如何隔离，以及跨界面记忆是否会把一个环境的错误状态带到另一个环境。

## 4. ProvenanceGuard：事实没错，出处错了，MCP Agent 也会误导人

### 热点是什么

Multiverse Computing 在 **2026-09-29** 通过 Hugging Face 发布了 ProvenanceGuard 的实现解读文章。需要说明的是，相关论文并非 9 月 29 日才出现：arXiv 版本于 **2026-06-16** 首次提交、**2026-08-27** 修订；这次新的是面向工程读者的公开说明。ProvenanceGuard 保留 MCP trace 中的 tool ID、source ID 和原始输出，先把答案拆成原子 claim，再路由到来源特定证据，用 NLI 与 token 对齐检查支持关系，并比较答案声称的来源和实际支持来源，最后做逐 claim 与整答案的 allow/block 决策。论文在 281 条医疗 Agent trace、361 条人工核验 claim 上报告 block F1 0.802、source accuracy 0.858；相似多源测试中的 source-plus-relation accuracy 降到 0.229，说明近似来源仍很难区分。

原始资料：

- [Getting the Source Right, Not Just the Fact: Source-Aware Verification for MCP Agents（Hugging Face Team Article，2026-09-29）](https://huggingface.co/blog/MultiverseComputingCAI/getting-the-source-right-not-just-the-fact-source)
- [ProvenanceGuard: Source-Aware Factuality Verification for MCP-Based LLM Agents（arXiv:2606.18037，v3 2026-08-27）](https://arxiv.org/abs/2606.18037)

### 为什么值得写

**事实**：系统针对的是 cross-source conflation：一句话可能在某个工具结果里为真，却被答案错误地归因给另一个工具；它把来源身份贯穿 claim 分解、证据路由、支持判断和修复回路。**我的判断**：对工单 Agent、医疗助手和企业检索来说，“答对事实”与“把事实归给正确系统”是两道不同的门。这个角度比泛泛讲幻觉更适合工程实现，也能直接对应客户工单中的订单记录、知识库、日志和代码证据。

### 建议标题

**事实没错，出处错了：MCP Agent 为什么还需要一层来源校验？**

### 文章梗概

一个客服 Agent 同时查了订单、退款政策和操作日志，最后说“根据订单记录，用户可以退款”。这句话可能事实正确，出处却错了；把所有工具结果混在一起的 faithfulness 检查很难发现。ProvenanceGuard 保留 MCP 的来源身份，逐条拆 claim，分别做证据支持和归因校验，失败后再修复或回退。文章用一组多来源工单演示这条验证链，解释 block F1、source accuracy 和相似来源降分分别意味着什么，并讨论延迟、保守拦截与人工复核的取舍。

### 结构提纲

1. **“有证据”为什么不等于“引用正确”**——构造订单、政策和日志三种来源的交叉归因错误。
2. **来源身份怎样跟着 MCP trace 走**——定义 tool ID、source ID、原始输出和 claim 的数据结构。
3. **支持判断与归因判断为何要拆开**——解释 claim 分解、证据路由、NLI、token 对齐和 allow/block。
4. **读懂论文中的保守结果**——对照 281 条 trace、361 个人工 claim、相似多源测试和 50 个注入归因错误。
5. **修复、回退和上线门禁**——把 blocked answer 接到 RARR 式重写，并设计工单 Agent 的人工接管规则。

### 写作所需证据

- **已经有**：Hugging Face 工程解读、arXiv v3 摘要和指标、医疗多来源场景、修复回路与约半秒的本地配置开销说明。
- **需要补做**：阅读论文中的路由、NLI、校准和消融细节；用三份相似的模拟工单资料构造错归因样本，分别测试“来源盲”与“来源感知”校验。
- **适合配图**：MCP 工具输出保留 source ID 的数据流图；claim→证据路由→支持判断→归因判断→修复/拦截的流程图。
- **关键未验证点**：论文数据是否能公开复现、claim 分解模型对结果的影响、近似来源下的低 source accuracy、真实云模型延迟，以及保守回退对用户体验的影响。

## 5. Google Diffusion Controller：不改主模型，也能控制生成方向吗？

### 热点是什么

Google Research 在 **2026-09-29** 发布 Diffusion Controller 介绍文章；对应论文早于热点日，arXiv 首次提交于 **2026-03-07**。Diffusion Controller 把反向扩散采样写成状态型随机控制问题，在冻结的预训练模型旁接一个轻量 side network，根据中间 denoising 输出注入控制修正，既覆盖可访问权重的 white-box 训练，也覆盖只能暴露中间结果的 gray-box 适配。Google 文章以 Stable Diffusion v1.4 做 SFT、reward-weighted loss 和 PPO 实验，并报告 HPS-v2 与人工偏好胜率；这些数字来自论文/Google 团队，尚非独立复测。

原始资料：

- [How Diffusion Controller unifies and simplifies AI image generation（Google Research，2026-09-29）](https://research.google/blog/how-diffusion-controller-unifies-and-simplifies-ai-image-generation/)
- [Diffusion Controller: Framework, Algorithms and Parameterization（arXiv:2603.06981，2026-03-07）](https://arxiv.org/abs/2603.06981)

### 为什么值得写

**事实**：Diffusion Controller 用统一的控制视角解释推理时 guidance、微调和奖励优化，并提出“冻结主干+轻量控制修正”的参数化；文章公开了 gray-box 与 white-box 结构和 Stable Diffusion v1.4 实验。**我的判断**：它的工程价值在于把“无法改权重的模型定制”从 prompt 猜测变成可分析的控制层，但是否能迁移到真正闭源、没有中间 denoising 输出的服务，仍然取决于供应商暴露的接口。文章应把数学推导、可复现实验和营销式“完美控制”分开。

### 建议标题

**不改主模型，也能改生成方向？Google Diffusion Controller 的灰盒控制思路**

### 文章梗概

想让图像模型稳定画出指定属性，工程师通常要在 prompt、guidance、LoRA 和完整微调之间反复试错；模型一旦是闭源的，后两条路就走不通。Diffusion Controller 把反向扩散看成控制过程，在冻结主模型旁边训练 side network，逐步修正生成轨迹。文章从“戴墨镜的蜥蜴”约束开始，解释中间状态、控制强度、奖励函数和稳定性惩罚，再比较 gray-box 与 white-box 的边界。结果按 Stable Diffusion 配置复述，不能外推到闭源 API。

### 结构提纲

1. **生成质量和约束满足为什么会互相拉扯**——用多属性 prompt 说明强行 guidance 可能带来的形变。
2. **反向扩散怎样改写成控制问题**——从状态、转移核、终端目标和 divergence cost 解释统一视角。
3. **side network 如何在冻结主干旁工作**——追踪中间 denoising 输出、控制修正和推理时 guidance strength。
4. **SFT、reward-weighted loss 与 PPO 的差异**——对照训练目标、稳定性约束和论文中的实验设置。
5. **灰盒控制的真实边界**——列出需要暴露哪些中间接口、没有接口时哪些结论不能成立，并设计小规模复现。

### 写作所需证据

- **已经有**：Google Research 文章的架构图、DiffCon 论文摘要、LS-MDP 推导、side-network 参数化、Stable Diffusion v1.4 和 HPS-v2/人工评测说明。
- **需要补做**：阅读论文方法和附录，确认训练数据、奖励模型、控制强度和随机种子；查找可用代码或按论文公式做最小 toy diffusion 实验，不能把 toy 结果冒充图像质量结论。
- **适合配图**：冻结扩散主干与 side network 的双路架构图；单次反向扩散中每一步“预测—控制—更新”的时序图。
- **关键未验证点**：真实闭源模型是否提供所需中间量、gray-box 适配的接口成本、奖励函数换域后的稳定性，以及论文胜率能否在同一 HPS-v2 版本重现。

## 今日优先写作建议

优先写 **“会点屏幕还不够：Holo4 为什么要把 GUI、代码、MCP 和 API 放进同一个 Agent？”**。它在 9 月 28 日发布，公开文章给出了模型规格、任务工厂和 harness 设计，还放出了 7,366 条逐步轨迹，材料足够画出执行链并做小规模回放。OSWorld/AutomationBench 的版本和成本口径存在差异，反而能把“模型能力、环境、harness 和评测”拆开讲清楚。若更偏研究系统，第二选择是 CCM：论文对上下文压缩的收益和损失都有明确对照。
