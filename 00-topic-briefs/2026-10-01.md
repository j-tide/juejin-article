## 今日判断

这几天的材料把 Agent 的问题从“模型能不能答”推向了“系统怎样持续工作”：OpenAI 把 Agent 放到后台，Replit 让模型自己决定是否分工，Google 和 OpenAI 都在用长任务与成本重新定义模型比较方式，ParaAgent 则把探索工具和并行执行写进训练目标。它们适合写工程分析，但证据边界不同：Dots 的能力和权限仍是产品方描述，Replit、Gemini 和 GPT-6.1 的数字主要来自厂商评测，ParaAgent 是刚提交的预印本。文章中应把机制、运行环境、预算和评分口径一起交代。

## 1. OpenAI Dots：一个 Agent 开始在后台替你做事以后，系统要保存什么？

### 热点是什么

OpenAI 在 **2026-09-29** 发布 Dots。官方把它定义为由 GPT-6 Astra 驱动的“always-on” Agent：每个 Dot 有自己的云端计算机、浏览器和已连接的应用，可以在 ChatGPT、Slack 和 Teams 中接收任务并持续推进。Dots 还提供 proactive research，后台读取已连接应用但默认不能发送消息或改动内容；需要产生外部影响的动作会进入 Custom Rules、auto-review 和人工审批。企业还可以配置有独立身份、凭证和职责的 specialist dots。当前功能按地区和套餐分批开放，企业用户仍以 beta 和试点为主。

原始资料：

- [Introducing dots（OpenAI，2026-09-29）](https://openai.com/index/introducing-dots/)
- [ChatGPT Release Notes：Meet your dot（OpenAI，2026-09-29）](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)

### 为什么值得写

**事实**：Dots 把交互从“一次请求一次响应”改成目标、后台进度、跨渠道消息和审批组成的持续任务；官方明确区分只读的 proactive research、可配置权限和必须由人完成的敏感动作。**我的判断**：真正的新问题是 Agent 的长期状态和触发边界。系统要知道哪些观察可以缓存、哪些动作必须再次确认、用户改了规则后正在运行的任务如何收敛，还要能让人回看它在云端计算机里做过什么。这个切口比“个人助理更聪明”更容易落到可实现的状态机和审计记录。

### 建议标题

**Agent 开始在后台替你做事以后，任务状态和权限该放在哪里？**

### 文章梗概

以前的 Agent 等用户发消息才运行，Dots 把任务变成可以跨天持续的后台进程：它有自己的云端计算机，能读取已连接应用，遇到需要对外发消息或修改数据的动作再请求批准。文章从“监控客户反馈并准备修复 PR”的一条任务开始，拆开触发器、工作记忆、云端执行环境、只读研究和动作审批的状态转移，再讨论规则更新、任务中断、凭证隔离与回放。官方描述不能代替独立实测，重点放在一套可审计的持续 Agent 设计。

### 结构提纲

1. **从对话到持续任务发生了什么变化**——把目标、触发、观察、动作和交付拆成持久状态，而不是一串聊天消息。
2. **云端计算机、应用连接和工作记忆如何分层**——区分模型上下文、任务笔记、外部系统状态与凭证，说明各自的失效方式。
3. **只读研究和可写动作为什么要走两条路**——画出 proactive research、工具调用、auto-review 和人工批准的状态机。
4. **规则改了，正在运行的任务怎么办**——讨论版本化权限、撤销、暂停、重放和幂等，避免旧规则继续生效。
5. **持续 Agent 上线前要记录哪些证据**——设计事件日志、动作前后快照、审批理由和人工接管入口。

### 写作所需证据

- **已经有**：Dots 官方功能描述、云端计算机、4,000 多个应用连接、只读 proactive research、Custom Rules、auto-review、审批和 specialist dots 的边界。
- **需要补做**：阅读官方帮助中心与 system card，确认各类动作的审批矩阵、任务保留时间、并发限制和企业管理员配置；没有登录条件时不声称已实测。
- **适合配图**：目标→触发器→后台运行→工具访问→风险动作审批→交付/暂停的生命周期图；模型、云端沙箱、应用连接和审计服务的分层架构图。
- **关键未验证点**：长时间任务的唤醒策略、跨 Slack/Teams/ChatGPT 的一致状态、凭证过期后的恢复，以及规则变更是否能立即影响已排队动作。

## 2. Replit 新 harness：模型自己决定要不要分工，真的比固定多 Agent 更省吗？

### 热点是什么

Replit 在 **2026-09-29** 发布 *Free the models: Harness design at the frontier*。文章把核心 loop 设计成一个可组合的 harness：模型可以逐步调整 effort，决定是否派出 explorer、worker、reviewer 或 tester，选择子 Agent 的规格，并在后续回到已经 briefing 过的子 Agent。Replit 公开了生产环境中 Fable 5、Fable 5.1 和 GPT-6 Astra 的一周统计，也用四次重复的 DeepSWE v1.1 和 Terminal-Bench 4.0 对比 Astra 单体和“长期 sidekick”架构。文章中的任务分数、成本和生产分布均为 Replit 自己的运行结果，不能直接视作独立排行榜。

原始资料：

- [Free the models: Harness design at the frontier（Replit，2026-09-29）](https://replit.com/blog/free-the-models)
- [DeepSWE v1.1 leaderboard（文中引用的公开基线）](https://deepswe.datacurve.ai/)
- [Terminal-Bench 4.0（文中引用的公开基准）](https://www.tbench.ai/)

### 为什么值得写

**事实**：Replit 不让一个静态路由器在请求开始时选模型，而是让 core loop 在任务进行中决定 effort、是否委派和是否复用已有子 Agent；其公开表格显示不同模型的委派习惯不同。**我的判断**：这说明 harness 的职责可能从“规定流程”转向“提供可选动作和安全边界”。但模型自主分工会把成本、上下文复用和失败恢复交给运行时，必须用轨迹验证它真的省下了重复工作，而不是多开了几个昂贵的回合。

### 建议标题

**模型自己决定要不要分工，真的比固定多 Agent 更省吗？拆 Replit 新 harness**

### 文章梗概

固定的多 Agent 流程看起来可控，却可能让小任务也付出拆分和上下文同步成本。Replit 的新 harness 把“要不要分工、派谁、用多大 effort、是否唤醒旧子 Agent”交给 core loop，并用生产轨迹和软件工程基准比较单体、sidekick 与可组合委派。文章先复现一条任务的 dispatch 图，再解释 effort、缓存和子 Agent 复用，最后把 Replit 自测的分数—成本曲线与公开基线分开，讨论何时应让模型自由组织、何时仍要固定流程。

### 结构提纲

1. **固定路由器和动态委派各自解决什么问题**——比较请求级选模型、回合级调 effort 和任务中途派工的观察范围。
2. **Replit 的四个 harness 原语如何协作**——拆 domain subagent、tier/effort、可复用子 Agent 和动态升级的接口。
3. **一条生产轨迹怎样决定是否继续分工**——按 explorer、worker、tester 的顺序画出上下文传递、回收和复用。
4. **模型委派习惯为什么会不同**——解读 Fable 5、Fable 5.1 和 Astra 的 dispatch/return 统计，不把比例当成普遍规律。
5. **分数、成本与重复次数怎样一起看**——核对 DeepSWE、Terminal-Bench 的任务数、四次重复、基线和 GPU 任务排除项。

### 写作所需证据

- **已经有**：Replit 对 core loop、四类原语、生产委派比例、DeepSWE/Terminal-Bench 对照配置和成本数字的完整说明。
- **需要补做**：阅读文章引用的 GPT-6 Astra、Fable 5.1 和排行榜原始页面；用一个本地模拟 harness 重放“单体、sidekick、动态委派”三种轨迹，先测回合数、并行度和缓存命中，不把模拟结果当模型能力。
- **适合配图**：请求级路由、固定 sidekick、动态 core loop 三种架构对照图；一次任务中 effort 调整与子 Agent dispatch/return 的时序图。
- **关键未验证点**：公开成本是否包含所有工具和回退调用、生产轨迹是否受任务分布影响、动态委派失败时谁负责回滚，以及不同模型的缓存实现能否公平比较。

## 3. Gemini 4 Argon 的评测表到底在测什么？

### 热点是什么

Google 在 **2026-09-30** 发布 Gemini 4 Argon。官方称它面向复杂、长时间的工程、法律、金融和网络防御工作，输出上限从此前 64K 扩展到 1M tokens，并计划以每百万输入 2 美元、输出 10 美元的介绍价开放。Argon 目前通过 Fairwind 计划给受信任的网络防御者和早期测试者，尚未向所有开发者开放。Google 同时公布 DeepSWE v1.1、AutomationBench、LVBench、CWE-bench 等结果，以及内部代码迁移和漏洞修复案例；这些数字来自 Google 的评测环境、内部使用或合作方数据，方法页和公开 API 仍需单独核对。

原始资料：

- [Gemini 4 Argon: our next era of frontier intelligence（Google，2026-09-30）](https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-argon/)
- [Gemini 4 Argon 模型页与评测表（Google DeepMind）](https://deepmind.google/models/gemini/)
- [Gemini 4 Argon evals methodology（Google DeepMind）](https://deepmind.google/models/evals-methodology/gemini-4-argon)

### 为什么值得写

**事实**：Argon 的发布把软件工程、知识工作、长上下文、计算机使用和网络防御放在同一张表里，同时强调输出预算、受信任试用和多层安全控制。**我的判断**：这张表不能直接回答“谁是最强模型”，因为每一行对应不同工具、任务长度、环境和验收条件。更值得写的是如何把模型分数翻译成 Agent 的执行链：是能写出补丁，还是能在沙箱中验证、修复并交付。文章还可以提醒读者，1M 输出上限不等于每个任务都应该生成百万 token。

### 建议标题

**Gemini 4 Argon 的评测表到底在测什么？从分数回到 Agent 执行链**

### 文章梗概

Gemini 4 Argon 的发布表同时列了编码、企业知识工作、长上下文、电脑操作和网络防御，读者很容易把它读成一张总排名。文章把一项“找到并修复漏洞”的任务拆成检索、代码理解、工具调用、验证和交付五个环节，再逐项对应 Google 公布的基准与内部案例，说明不同评测测到的其实是不同执行链。最后讨论 1M 输出预算、可信试用、提示注入防护和模型可用性，给出如何设计自己的任务级评测，而不是照抄厂商数字。

### 结构提纲

1. **一张总表为什么会掩盖执行环境**——区分知识问答、终端 Agent、电脑操作和真实企业流程的输入输出。
2. **Argon 的长输出预算解决了什么**——解释 64K 到 1M 的变化与成本、状态压缩、验证回合之间的关系。
3. **DeepSWE、AutomationBench、LVBench 和 CWE-bench 各测哪一段**——将每个指标映射到工具、环境和验收条件。
4. **内部代码迁移和漏洞修复案例如何读**——分清模型建议、自动测试、人工审计和上线结果。
5. **从厂商表格到自己的 Agent 评测**——制定任务集、预算、成功定义、回放证据和独立复测的最小规范。

### 写作所需证据

- **已经有**：Google 发布日期、Fairwind 分阶段开放、1M 输出上限、介绍价、官方评测表、内部代码迁移/漏洞防御叙述和安全控制说明。
- **需要补做**：阅读 methodology 页面和各 benchmark 的原始定义，确认是否使用 offline subset、哪一版 harness、是否包含 fallback 与人工复核；没有 API 访问时不声称完成模型实验。
- **适合配图**：同一漏洞任务的检索→理解→修改→测试→人工审计执行链；“基准分数—工具权限—验收条件”的三维对照图。
- **关键未验证点**：内部案例能否独立复现、1M 输出上限的实际可用性和费用、提示注入评测的攻击分布，以及 Fairwind 期间模型版本是否稳定。

## 4. GPT-6.1 Sol：模型便宜五倍以后，Agent 的预算和路由会怎么变？

### 热点是什么

OpenAI 在 **2026-09-29** 的 DevDay 更新中发布 GPT-6.1 Sol。官方定位是接近 GPT-6 Astra 能力、但标准输入和输出 token 价格约为 Astra 五分之一；缓存输入为每百万 0.10 美元，并提供 API、ChatGPT Work 和 Codex 入口，普通 Chat 的可用性另行说明。OpenAI 给出了 DeepSWE、GDP.pdf、AutomationBench、OSWorld 2.0、Terminal-Bench Science 和 factuality 的比较，并在 system card addendum 中补充自动审查、电脑使用安全和生化网络安全分级。官方也明确说明，竞争模型数字来自公开报告，评测环境、system prompt、工具和 effort 可能与生产不同。

原始资料：

- [GPT-6.1 Sol（OpenAI，2026-09-29）](https://openai.com/index/introducing-gpt-6-1-sol/)
- [Addendum to GPT-6 Astra System Card: GPT-6.1 Sol（OpenAI Deployment Safety，2026-09-29）](https://deploymentsafety.openai.com/gpt-6-1-sol/respecting-auto-review)
- [ChatGPT Release Notes：GPT-6.1 Sol in ChatGPT Work and Codex（OpenAI，2026-09-29）](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)

### 为什么值得写

**事实**：Sol 的卖点不是单项最高分，而是更低的单位价格、缓存价格和在多种 Agent 任务上的接近 Astra 的结果；官方同时提醒跨模型比较存在环境差异。**我的判断**：当模型价格下降，系统设计会从“怎样省一次调用”变成“怎样给不同回合分配预算”：简单检索用低 effort，失败恢复和最终审查才升级，缓存与并行是否真的降低任务成本要靠完整轨迹核算。这个角度能把模型发布转成路由、预算和验收策略，而不是复述排行榜。

### 建议标题

**模型便宜五倍以后，Agent 的预算和路由会怎么变？看 GPT-6.1 Sol 的任务级成本**

### 文章梗概

如果一个模型的 token 价格降到旗舰的五分之一，工程师会不会把所有回合都换成它？GPT-6.1 Sol 的官方材料给出了 Agent 基准、缓存价格和安全评估，也承认竞争模型数据来自不同公开报告。文章用一个代码修复任务拆算输入、缓存、工具和重试成本，比较低 effort 常驻、按阶段升级和并行子 Agent 三种策略，再把分数放回各自环境。结论不是“Sol 永远更划算”，而是任务级成本必须和完成定义一起测。

### 结构提纲

1. **token 价格为什么不是任务成本**——加入缓存、工具回合、失败重试、并行分支和人工审查。
2. **Sol 与 Astra 的能力—价格曲线怎样读**——区分模型分数、effort、输入输出价格和每任务成本。
3. **按回合升级还是按 Agent 分工**——设计低 effort 常驻、失败升级和并行 worker 三种路由。
4. **跨模型基准为何不能直接横排**——检查 system prompt、工具集、评测版本、fallback 和公开报告的缺口。
5. **把安全门禁纳入预算模型**——结合 system card 的 auto-review、电脑使用和高风险能力分级，定义上线前必须人工确认的步骤。

### 写作所需证据

- **已经有**：OpenAI 的价格、缓存价格、可用平台、各基准分数、跨模型比较说明和 GPT-6.1 Sol system card addendum。
- **需要补做**：核对 API 价格与 rate limit 文档，提取 DeepSWE/AutomationBench/OSWorld 的任务定义；在同一模型、同一工具集上做确定性成本模拟，真实模型调用需另行标注。
- **适合配图**：任务级成本瀑布图；按回合升级、并行子 Agent、固定旗舰三种路由的状态流程图。
- **关键未验证点**：实际缓存命中率、不同 effort 的输出长度、API 与 Codex 的工具差异、模型升级后的价格稳定性，以及安全审查失败带来的额外回合。

## 5. ParaAgent：工具越多，为什么还要把探索和执行拆开？

### 热点是什么

论文 **ParaAgent: Reinforcing Parallel Acting in Open-World Tool Environments** 于 **2026-09-27** 首次提交 arXiv。作者提出 ParaAct：在阶段层面往返于 Exploration 和 Execution，在动作层面并行发起互不依赖的工具调用；训练阶段先用 Planner、Retriever、Executor、Critic、Answerer 生成多 Agent 冷启动轨迹，再用带 step、phase、trajectory 多级优势分解的强化学习训练。论文介绍 ToolEnv 模拟器覆盖 50,011 个现实工具接口，并称 ParaAgent-4B 在两个开放世界工具基准上取得最高平均成功率，尤其在多工具任务上提升明显。当前材料是预印本，尚未看到可直接复现实验的官方代码。

原始资料：

- [ParaAgent: Reinforcing Parallel Acting in Open-World Tool Environments（arXiv:2609.33618，2026-09-27）](https://arxiv.org/abs/2609.33618)
- [ParaAgent PDF 与 TeX 源码入口（arXiv）](https://arxiv.org/pdf/2609.33618)

### 为什么值得写

**事实**：ParaAgent 不只是把多个工具调用并发执行，而是让 Agent 先明确当前处于探索还是执行，再把可并行的调用组织成计划，并为不同粒度提供奖励信号。**我的判断**：这正好击中了企业工单和开放 API 场景的瓶颈：工具目录很大，盲目搜索浪费回合，串行调用又把无依赖工作拖成长链。文章可以把论文的结构化计划翻译成一个可运行的 DAG 调度器，同时保留“模型是否真的知道依赖关系”这一未验证问题。

### 建议标题

**工具越多，为什么还要先探索再执行？拆 ParaAgent 的并行行动回路**

### 文章梗概

当 Agent 面对数万种工具时，先找工具还是先调用工具并不是简单的顺序选择：找得太多会浪费上下文，调用太早又会选错接口。ParaAgent 用 ParaAct 把探索和执行放在可往返的阶段状态里，再把同一阶段中没有依赖的动作并行化，并用多级奖励训练这种组织方式。文章先用一个订单、库存和营销数据的开放工具任务画出探索—执行 DAG，再逐项解释 ToolEnv、冷启动轨迹和优势分解，最后讨论并行调用的幂等、限流、失败回滚与论文结果的复现边界。

### 结构提纲

1. **开放世界工具为什么让串行 Agent 变慢**——区分工具发现、参数确认、依赖等待和真正执行的时间。
2. **ParaAct 的两个粒度如何配合**——画出 Exploration↔Execution 阶段状态和动作级并行层。
3. **ToolEnv 怎样把工具训练变成可控实验**——说明 50,011 个接口、模拟响应、失败注入和缓存的作用。
4. **多 Agent 冷启动与多级奖励在教什么**——分别解释 step、phase、trajectory 信号，避免把训练数据数量当成功率。
5. **并行执行落地前要补哪些运行时约束**——讨论依赖 DAG、幂等键、限流、部分成功和补偿事务。

### 写作所需证据

- **需要补做**：下载论文 PDF/TeX，核对基准名称、任务数量、baseline、并行度和消融实验；先写一个不调用模型的 DAG 调度模拟器，再决定是否做小模型复现。
- **适合配图**：工具发现→候选检索→依赖分析→并行调用→汇合验证的流程图；step/phase/trajectory 三层奖励与轨迹的对应图。
- **关键未验证点**：官方代码和数据是否会发布、模拟工具响应与真实 API 的差异、并行调用的成本收益、错误补偿策略，以及性能提升是否只来自更好的任务分布。
