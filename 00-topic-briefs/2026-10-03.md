## 1. Agent 不只选模型：HydraFusion 和 Dynamic Workflows 把编排拆成两层

### 热点是什么

GitHub 在 **2026-09-30** 将 HydraFusion 研究预览扩展到 VS Code 和 GitHub Copilot app。HydraFusion 不是一个新模型，而是根据推理、代码生成、调试和工具使用等能力信号，在三种执行方式中选择：单模型直接完成、先用高效模型再由质量门决定是否升级的 cascade，以及由不同模型家族的只读 critic 检查并让原模型修订一次的 critique。GitHub 在 **2026-10-01** 又宣布 Dynamic Workflows 进入 Copilot CLI、Copilot app 和 Copilot SDK：流程本身由代码定义，可以串行或并行运行工具和 Agent，传递结构化结果，在检查点暂停并等待人工恢复。

两项能力都处于公开预览，HydraFusion 仍是 research preview，Dynamic Workflows 也明确提示会变化。

原始资料：

- [HydraFusion in VS Code and the GitHub Copilot app（GitHub Changelog，2026-09-30）](https://github.blog/changelog/2026-09-30-hydrafusion-in-vs-code-and-the-github-copilot-app/)
- [Dynamic workflows in Copilot CLI and the Copilot app（GitHub Changelog，2026-10-01）](https://github.blog/changelog/2026-10-01-dynamic-workflows-in-copilot-cli-and-the-copilot-app/)

### 为什么值得写

**事实**：HydraFusion 负责在一次请求里选择执行策略和协调模型，Dynamic Workflow 负责把可复用的过程、并行分支、结构化交接和人工检查点写进代码；GitHub 还特意把它们和 `/fleet` 的自由委派区分开。**我的判断**：这提示 Agent 编排正在分成两层：上层决定“这次该用哪种解法”，下层决定“流程必须经过哪些步骤”。文章可以借一次事故排查，比较模型自由发挥、固定工作流和两层编排在可靠性、成本与可观测性上的差异。

### 建议标题

**Agent 不只选模型：HydraFusion 和 Dynamic Workflows 把编排拆成两层**

### 文章梗概

同一个线上事故，有时一个模型直接处理最快，有时需要便宜模型先收集日志、强模型再复核；一旦涉及多个系统、人工审批和可回放步骤，提示词就不够了。GitHub 的 HydraFusion 负责选择单模型、级联或批评修订，Dynamic Workflows 则把串并行步骤、结构化结果和暂停点写进代码。文章从事故排查出发，拆开“策略选择”和“过程执行”两层，比较 `/fleet`、固定流程与动态工作流的边界，最后讨论可审计的编排接口。内部路由和质量门仍未公开，不能把预览描述当成普遍收益。

### 结构提纲

1. **自由委派为什么无法保证同一件事每次都按同样步骤完成**——对照普通聊天、`/fleet` 和代码化流程。
2. **HydraFusion 选择的究竟是模型还是工作流**——解释 single、cascade、critique 和能力信号。
3. **Dynamic Workflow 怎样把过程变成程序**——拆串行/并行、结构化交接、子 Agent 互查和 checkpoint。
4. **两层编排如何共同决定成本和质量**——设计一个事故排查流程，明确每个分支的升级条件。
5. **预览能力上线前要补哪些观测**——记录路由选择、模型调用、暂停恢复、失败重试和人工改写。

### 写作所需证据

- **已经有**：两篇 GitHub Changelog 的发布日期、HydraFusion 三种 workflow、Dynamic Workflow 的代码化编排能力、与 `/fleet` 的边界和预览状态。
- **需要补做**：阅读 GitHub 官方 Dynamic Workflows 文档和 HydraFusion 研究/基准说明，确认扩展 API、状态持久化和模型路由是否可见；用一个本地模拟器实现单模型、cascade、critique 三种策略的确定性回放。
- **适合配图**：上层“策略选择器”连接下层“代码化工作流”的双层架构图；事故排查中串行、并行、质量门和人工 checkpoint 的流程图。
- **关键未验证点**：HydraFusion 的选择信号和阈值、动态工作流失败后的恢复语义、预览版的计费与超时，以及真实任务中额外 critic 是否抵消了收益。

## 2. 桌面没有 API，Agent 还能接吗？GitHub Copilot Computer Use 的权限边界

### 热点是什么

GitHub 在 **2026-10-01** 将 Computer Use 作为公开预览放进 GitHub Copilot CLI 和 Copilot app，支持 macOS 与 Windows。Copilot 可以读取应用的可访问性内容和视觉上下文，点击控件、输入和编辑文字、按键、滚动、拖拽，并跨应用完成没有 API、命令行或 MCP 接口的旧系统工作流。GitHub 的示例是让 Copilot 在 Safari 中处理报销流程。

控制权仍由用户和组织设置掌握：首次控制应用前需要批准，用户可以查看或重置“始终允许”的应用；macOS 还要单独授予 Accessibility 和 Screen Recording 权限，组织管理员可以禁用此能力。CLI 通过 `/computer on|show|off` 控制，Copilot app 也提供设置入口。

原始资料：

- [GitHub Copilot can now interact with desktop apps with computer use（GitHub Changelog，2026-10-01）](https://github.blog/changelog/2026-10-01-github-copilot-can-now-interact-with-desktop-apps/)
- [Computer use in GitHub Copilot CLI and the Copilot app（GitHub Docs）](https://docs.github.com/en/copilot/concepts/agents/computer-use)

### 为什么值得写

**事实**：Computer Use 把没有 API 的桌面应用纳入 Agent 工具范围，同时把应用批准、操作系统权限和组织开关放到执行链上。**我的判断**：它的工程难点不在“会不会点击”，而在视觉观察、可访问性树、用户批准和不可逆动作怎样共同形成权限边界。文章可以把一个报销流程拆成观察—动作—确认—回退四类状态，说明 GUI Agent 与浏览器自动化、MCP 工具调用在失败恢复和审计上有什么不同。

### 建议标题

**桌面没有 API，Agent 还能接吗？拆 GitHub Copilot Computer Use 的权限边界**

### 文章梗概

很多企业系统没有 API，员工却每天要在桌面软件里复制、核对和提交信息。GitHub Copilot Computer Use 把应用界面纳入 Agent 工具循环：模型读取视觉和可访问性上下文，执行点击和输入，遇到高风险动作再请求批准。文章用旧报销系统的流程，比较 GUI 操作、浏览器自动化和 MCP 调用的状态差异，拆解应用白名单、macOS 权限、组织禁用开关和“始终允许”后的撤销路径。公开预览没有成功率、录屏保留和误操作统计，只能列为待验证问题。

### 结构提纲

1. **没有 API 的旧系统为什么仍然值得自动化**——区分网页 DOM、可访问性树和纯视觉界面。
2. **Computer Use 的观察与动作接口**——整理截图、可访问性内容、鼠标键盘动作和跨应用切换。
3. **批准发生在什么位置**——画出应用授权、系统权限和组织策略三层门禁。
4. **点击成功不等于流程完成**——设计提交前确认、结果读取、重试和撤销状态。
5. **如何做一组可回放的桌面评测**——记录动作序列、窗口状态、人工介入、数据暴露与最终业务结果。

### 写作所需证据

- **已经有**：GitHub 官方 Changelog 的支持平台、动作范围、批准机制、macOS 权限、组织开关和 CLI 控制命令。
- **需要补做**：阅读 GitHub Docs 的权限、应用列表和日志说明；在可用的 macOS/Windows 环境用无敏感数据的报销表做一次人工批准与拒绝回放，不能把一次演示写成稳定性结论。
- **适合配图**：视觉观察、可访问性树、动作执行、用户批准、业务验证五段式架构图；“始终允许”到撤销的权限状态机。
- **关键未验证点**：模型如何处理窗口变化和遮挡、失败动作是否可逆、屏幕内容和录屏的保留策略、跨应用凭据隔离以及预览版的速率限制。

## 3. 不用生成文本的模型，Agent 反而更快：Cloudflare Clef 把路由变成概率决策

### 热点是什么

Cloudflare 在 **2026-10-01** 发布 Clef 与 Clef-flash，这是 Workers AI 团队训练的开放权重 decision model。它不生成一段文本，而是读取状态和一组类型化问题，返回每个允许答案的概率：`noul` 处理是/否，`choice` 从枚举中选择并给出概率与置信度，`score` 按有序等级评分。27B 的 Clef 和 9B 的 Clef-flash 以 Apache 2.0 权重发布在 Hugging Face，并可通过 Workers AI 调用；Cloudflare 同时开放面向自有工作负载的 RL 微调服务。

Cloudflare 在 43 次基准运行中报告 Clef 中位延迟 209.3ms、p95 238.6ms，Clef-flash 中位延迟 38.8ms；在 10 个 decision benchmark 中称 Clef 在 7 个项目拿到最高分。这些是厂商报告，网络往返、题目分布和校准方式仍需独立复测。

原始资料：

- [Introducing Clef: Cloudflare's first open-source decision models（Cloudflare Changelog，2026-10-01）](https://developers.cloudflare.com/changelog/post/2026-10-01-clef-workers-ai/)
- [Introducing Clef: our open-source decision models, and new RL fine-tuning platform（Cloudflare Blog，2026-10-01）](https://blog.cloudflare.com/clef-decision-models/)
- [Cloudflare/clef：模型卡与权重](https://huggingface.co/Cloudflare/clef)

### 为什么值得写

**事实**：Clef 把“路由、阻断、升级人工”这类热路径决定变成结构化概率输出，省去解析自由文本和等待长推理；它还与 Jev 的 System One API 兼容，一次请求最多问 64 个问题。**我的判断**：很多 Agent 不需要每一步都调用一个会长篇思考的模型，先用小而确定的决策层筛选，再把复杂任务交给 LLM，可能更容易做延迟、成本和审计。文章可以用工单分流和工具调用前检查两个例子，讨论概率输出不等于授权、置信度不等于校准，以及何时仍需要完整模型。

### 建议标题

**不用生成文本的模型，Agent 反而更快：Cloudflare Clef 把路由变成概率决策**

### 文章梗概

客服工单是否紧急、该交给哪个团队、工具调用是否需要人工确认，通常不需要长答案，却常被塞进昂贵的 LLM 回路。Cloudflare Clef 用类型化问题返回概率和置信度，再把结构化决定交给后续 Agent。文章从工单路由开始，比较自由文本分类、规则表和 decision model 的接口，拆开 `noul`、`choice`、`score` 与 LLM 的协作边界，再核对 Cloudflare 的延迟和基准口径。概率只是输入，不自动等于授权或安全结论。

### 结构提纲

1. **为什么自由文本不适合所有 Agent 决定**——分析解析、重试、漂移和长推理的热路径成本。
2. **Clef 的类型化决策接口**——用 `noul`、`choice`、`score` 还原输入状态与输出结构。
3. **决策模型与 LLM 怎么串起来**——设计“先分流、后调查、再升级”的工单执行链。
4. **概率、置信度和授权不是一回事**——说明阈值、拒答、校准与人工门禁如何组合。
5. **厂商基准怎样独立复测**——固定网络、批大小、问题集和 p95 计算，避免把延迟表当成结论。

### 写作所需证据

- **已经有**：Cloudflare Changelog、博客、模型卡、Apache 2.0 权重、三种问题类型、43 次延迟比较和 10 个基准摘要。
- **需要补做**：阅读模型卡和 Workers AI API 文档，核对输入限制、视觉输入、价格和 RL 服务状态；用一组公开的 BANKING77/CLINC150 样本先比较结构化输出与文本分类解析。
- **适合配图**：决策模型位于 Agent 热路径、LLM 位于复杂任务路径的分层架构图；状态→类型化问题→概率→阈值/人工→工具调用的流程图。
- **关键未验证点**：真实网络延迟、概率校准、分布外问题的拒答能力、Apache 权重和 RL 服务的可用范围，以及 27B/9B 在本地部署时的资源要求。

## 4. 语音 Agent 先听完再思考就晚了：MAI-Transcribe-2-Streaming 的 partial transcript loop

### 热点是什么

Microsoft AI 在 **2026-10-01** 发布 MAI-Transcribe-2-Streaming，同时推出 MAI-Voice-2.1 和低延迟版本 MAI-Voice-2.1-Flash。转录模型支持 60 种语言和连续语言检测，不等说话结束就会在略高于 100ms 后发出 partial transcript，随着更多音频到达再修订并提交稳定文本；微软称这让语音 Agent 可以在用户说完前开始推理或调用工具。MAI-Voice-2.1 支持 23 种语言、26 个 locale，Flash 版本声称端到端生成 45 秒音频的延迟约 150ms；转录模型的介绍价格是每小时 0.54 美元，语音模型分别按字符计费。

微软引用 Artificial Analysis 的榜单和自己的内部比较来描述准确率、速度和成本；Azure 文档同时注明 MAI-Transcribe-2-Streaming 仍是 public preview，没有 SLA，不建议直接用于生产负载。

原始资料：

- [Our first streaming transcription model debuts at no. 1 on Artificial Analysis（Microsoft AI，2026-10-01）](https://microsoft.ai/news/our-first-streaming-transcription-model/)
- [MAI-Transcribe-2-Streaming overview（Microsoft Learn）](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/mai-transcribe-2-streaming)

### 为什么值得写

**事实**：微软把 partial、修订和 final 结果放进同一条流式协议，并明确把这段提前获得的时间留给 Agent 推理、工具调用和语音回复；官方文档仍把能力标为预览。**我的判断**：实时语音 Agent 的瓶颈不只是识别准确率，而是“在不确定的 partial 上提前行动”会不会造成错误调用。文章可以从一句包含纠正和停顿的口语开始，拆开端点检测、partial 版本、取消工具调用和最终提交，说明一个快的 STT 如何反而要求 harness 更会回滚。

### 建议标题

**语音 Agent 先听完再思考就晚了：MAI-Transcribe-2-Streaming 的 partial transcript loop**

### 文章梗概

传统语音助手等用户说完才处理，识别、推理、调用工具和合成语音全堆在句尾，交互会变慢。MAI-Transcribe-2-Streaming 让 Agent 先收到 partial，再随上下文修订并提交 final，能提前检索，却也把误听回滚带进执行层。文章从一次带自我纠正的客服来电开始，画出音频分片、partial 版本、工具调用、取消和 final commit 的时序，再比较微软的速度/价格口径与 Azure 预览限制，给出延迟、准确率和可撤回动作三项指标。

### 结构提纲

1. **为什么等 final transcript 会浪费交互窗口**——把识别、推理、工具和 TTS 的端到端延迟拆开。
2. **partial、revision、final 是什么关系**——定义分片 ID、版本号、稳定提交和纠正事件。
3. **提前调用工具如何避免听错造成副作用**——设计可取消查询、幂等写入和 final 前只读策略。
4. **转录和语音输出怎样组成一个闭环**——比较 MAI-Transcribe、MAI-Voice-2.1 与 Flash 的职责和延迟口径。
5. **预览服务上线前怎么测**——在噪声、多人说话、代码切换和网络抖动下分别测 WER、首字延迟、回滚和成本。

### 写作所需证据

- **已经有**：Microsoft AI 发布说明、60 种语言、partial 超过 100ms、23 种语言/26 个 locale、Flash 延迟和价格，以及 Microsoft Learn 的 public preview/SLA 限制。
- **需要补做**：阅读 Realtime API 与 Azure Speech SDK 的流式协议；用公开音频和本地状态机模拟 partial 修订，不把厂商内部 WER 写成独立结果。
- **适合配图**：音频分片→partial→推理/工具→取消→final commit→TTS 的时序图；可撤回读操作与不可撤回写操作的分层架构图。
- **关键未验证点**：真实噪声和多人场景的 WER、partial 修订频率、端点检测策略、跨语言切换的音色稳定性、预览 API 的 SLA 和实际计费。

## 5. 同一个 2B 模型，为什么换 Harness 后差 48 倍？拆 Mingbird 的本地优先 Agent

### 热点是什么

论文 **Mingbird: A Local-First Agent Harness Enabling Small Open Models to Complete Real Tasks** 于 **2026-10-01** 提交 arXiv。作者认为 2—9B 模型在面向大云模型设计的 harness 中失败，常见原因是工具预填充撑爆上下文、自我纠正发散、工具调用循环和任务静默放弃，于是做了与失败形态一一对应的十项机制，包括字节级 net-zero prefill、重新阅读原始任务的 finish gate 和按签名检测工具循环。

论文给出一个控制比较：同一台机器、4 个 harness、4 个开放模型、18 个真实任务、确定性产物评分共 288 个单元格，报告 Mingbird 总体 0.886，对比 goose 0.631、opencode 0.479、agent-mini 0.405；在另一套 τ²-bench 上报告 0.856、0.791 和 0.737。论文承认 LRAB 是自建基准、单机实验、部分消融只有单次评分。公开仓库还提供了全部单元格、复现脚本、离线模式和五环安全网，但仓库后续版本不能直接和论文固定版本混用。

原始资料：

- [Mingbird: A Local-First Agent Harness Enabling Small Open Models to Complete Real Tasks（arXiv:2610.02001，提交于 2026-10-01）](https://arxiv.org/abs/2610.02001)
- [Mingbird/Mingbird-agent：代码、基准协议和 288 个单元格](https://github.com/Mingbird/Mingbird-agent)

### 为什么值得写

**事实**：Mingbird 将 prefill 预算、完成门、循环检测、输出分块、文件回滚和本地离线边界都做成 harness 机制，并把同一模型换不同 harness 的结果公开。**我的判断**：这提供了一个很少见的工程对照：模型大小不是唯一变量，提示装配、工具协议和完成判断也能决定任务是否“看起来会做、实际上做完”。文章可以把它与用户已有的 DeepSeek Harness 阅读区分开，前者看一个可运行的本地系统怎样补小模型短板，后者继续解释运行时结构。

### 建议标题

**同一个 2B 模型，为什么换 Harness 后差 48 倍？拆 Mingbird 的本地优先 Agent**

### 文章梗概

同一个 2B 模型，在一个 Agent 框架里不断循环，在另一个 harness 里却能写代码、跑测试并交付文件。Mingbird 论文把差异归因到执行层：工具预填充、输出上限、完成判断和循环检测都可能让模型还没做事就被系统拖垮。文章用“写代码并跑测试”对照完整历史、工具结果和 finish gate，再拆 net-zero prefill、分块写入、签名级循环检测和五环安全网，复核 288 个单元格的实验口径。结果固定在指定版本和单机环境，不能外推到所有模型或云端 harness。

### 结构提纲

1. **小模型失败究竟发生在模型还是 harness**——把上下文溢出、自我纠正发散、工具循环和静默放弃分开记录。
2. **Mingbird 如何给每种失败加一个执行机制**——追踪 prefill 预算、输出分块、finish gate 和签名级循环检测。
3. **同一模型换 harness 的实验怎样控制变量**——解读 LRAB-288、τ²-bench、单机、版本锁定和确定性产物评分。
4. **本地优先不仅是隐私选项**——分析离线模式、MCP 可见性、零外联构造和文件回滚的系统边界。
5. **哪些结果仍然不能下结论**——讨论自建基准、单次消融、竞品版本漂移和从 Windows 到 macOS/Linux 的迁移。

### 写作所需证据

- **已经有**：arXiv 摘要、十项机制中的代表性设计、288 个实验单元格、τ²-bench 对照、论文限制，以及 GitHub 的代码、版本地图、482 项回归测试和离线模式说明。
- **需要补做**：固定 `v1.5.0`、Ollama 版本和论文指定 collection window，跑通一个 benchmark 单元格；阅读 `benchmarks/README.md`、prefill 与 finish gate 实现，不能把仓库当前版本的新增安全探针写入论文结果。
- **适合配图**：小模型 Agent 的“提示装配→工具调用→结果写入→完成判断”执行链；失败形态与 harness 机制的映射图；本地离线模式切断外联的边界图。
- **关键未验证点**：竞品 harness 的固定版本是否仍可获取、不同模型家族的结果、非 Windows 环境性能、真实云模型成本，以及每项机制独立贡献能否在多次运行中稳定出现。

- **Agents Are Systems, Not Models（2026-10-01）**：预印本在四项科学任务和超过 18,000 条轨迹上报告，同一配置重复运行本身解释了约 54% 的结果方差，信息量对结果的影响超过时间预算和模型大小；“提示词要求验证”不如提供专门验证工具。它和本次 Mingbird 的 harness 主题相近，先保留作后续评测专题。原始资料：[arXiv:2610.01618](https://arxiv.org/abs/2610.01618)。
