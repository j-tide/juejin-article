## 1. Agent 进入长任务以后，真正要管的不是上下文，而是运行中的状态

### 热点是什么

OpenAI 在 **2026-10-02** 发布《A model guide for the GPT-6 family》，把 GPT-6 Astra、GPT-6.1 Sol 和 GPT-6 Luna 的选择、价格、推理 effort 与长任务运行放在同一份生产指南里。指南建议用 prompt caching 和 compaction 控制上下文与成本，用 success、latency、cost per successful task 做部署指标；对小时级任务，Responses API 可以使用 mid-turn steering、异步工具调用和多 Agent delegation，Codex 则可以在任务运行中接收澄清或改向。文中还给出“先 API/连接器、再 computer use”的工具选择原则，并引用 Harvey、Cognition、Hex、Invideo 的案例。

这是一份官方实践指南，不是跨模型的独立基准。缓存节省、任务成功率和案例效果都不能直接外推到读者自己的工作负载。

原始资料：

- [A model guide for the GPT-6 family（OpenAI，2026-10-02）](https://openai.com/index/practical-guide-building-gpt-6/)

### 为什么值得写

**事实**：OpenAI 把模型选择、上下文压缩、运行中接管、异步工具和委派接口放进一条生产链，而不是只讨论如何写提示词。**我的判断**：长任务 Agent 的难点正在从“模型能不能回答”转成“任务运行时状态如何被更新、暂停、恢复和审计”。这适合用一次跨仓库调研任务，展示缓存命中、上下文压缩、慢工具、用户改向和子任务依赖如何改变最终结果，再区分 API 能力与产品案例。

### 建议标题

**Agent 进入长任务以后，真正要管的不是上下文，而是运行中的状态**

### 文章梗概

一个任务跑了半小时，测试还没结束，用户突然补充“只改后端，别动数据库”。如果系统只能等模型下一轮自然看到这句话，就可能继续执行错误分支。OpenAI 的 GPT-6 指南把缓存、压缩、mid-turn steering、异步工具和 delegation 放进同一条长任务链。文章从一次跨仓库调研开始，画出状态、工具、用户修正和子任务依赖的时序，解释哪些更新能排队、哪些动作无法撤回，再用成功率、延迟和成功任务成本设计验收指标。指南里的价格和案例只作为厂商口径，实际收益需要在自己的任务集上复测。

### 结构提纲

1. **长任务为什么不是把上下文窗口做大就够了**——拆任务状态、证据、工具结果和用户新指令四类变化。
2. **缓存与 compaction 分别保存了什么**——对照稳定指令、变化输入和压缩后的可继续状态。
3. **steering、异步工具和 delegation 的执行语义**——明确排队、并行、依赖等待和已完成动作之间的边界。
4. **如何让 Agent 被接管后仍然可审计**——设计事件日志、状态版本、暂停点和恢复检查。
5. **生产验收到底看什么**——用成功任务率、端到端延迟、失败恢复率和每个成功任务成本组成指标。

### 写作所需证据

- **已经有**：OpenAI 指南的模型定位、价格表、缓存与压缩建议、steering/异步工具/delegation 说明，以及“API 优先、computer use 兜底”的原则。
- **需要补做**：阅读 Responses API 的 steering、异步工具和 delegation 文档；用本地状态机模拟慢测试、用户中途改向和子任务依赖，分别记录可取消与不可取消动作。
- **适合配图**：长任务状态机（queued/running/waiting/steered/paused/resumed/finished）；缓存、压缩、工具回执和人工输入汇入同一状态日志的时序图。
- **关键未验证点**：缓存命中率与实际账单、压缩后信息损失、异步工具异常恢复、delegation 的上下文边界，以及指南中的产品案例能否在公开 API 上复现。

## 2. 代码审查 Agent 变成 API 以后，谁来决定它该审多深？

### 热点是什么

GitHub 在 **2026-10-02** 宣布 Copilot code review 的 REST 和 GraphQL API 正式支持：团队可以从自己的脚本、CI 或内部工具发起审查，并在每次请求里设置 review effort level。`Default` 的默认级别已经改为 `Balanced`，这一变更自 **2026-09-28** 对新旧仓库和组织生效；如果管理员或仓库明确选了 `Lite`，则继续沿用显式设置。该能力对 Copilot Pro、Pro+、Max、Business 和 Enterprise 计划开放。

官方公告说明了“如何触发”和“如何选 effort”，但没有在同一页面给出完整的评审状态机、结果回调、速率限制或每个级别的质量差异。

原始资料：

- [Copilot code review: API support and new default effort level（GitHub Changelog，2026-10-02）](https://github.blog/changelog/2026-10-02-copilot-code-review-api-support-and-new-default-effort-level/)

### 为什么值得写

**事实**：代码审查从 PR 页面上的按钮变成可以被内部流程调用的能力，而且每次请求可以显式设置审查深度。**我的判断**：接入 API 后，工程问题不再是“要不要让 Agent 看 PR”，而是“什么风险触发什么 effort，结果怎样进入合并门禁”。文章可以把一个支付改动的 CI 流程拆成变更分类、审查请求、结果回写、人工确认和合并五步，讨论 review Agent 的输出如何与测试、代码所有者和分支保护组合，而不是把审查意见直接当成通过信号。

### 建议标题

**代码审查 Agent 变成 API 以后，谁来决定它该审多深？**

### 文章梗概

以前，开发者在 PR 页面点一下 Copilot review；现在，CI 识别到支付、权限或数据库变更时就能主动发起审查，并选择 effort。GitHub 的 API 更新让审查进入可编排流程，却没有替团队决定什么结果能阻塞合并。文章从一条高风险文件流水线开始，拆解变更分类、review 请求、结果回写、重试和人工确认，再比较 Lite、Balanced 与更高 effort 的预算取舍。重点把审查意见、测试结果和分支保护分开，设计可回放的评测，而不是把模型评论数量当成质量。

### 结构提纲

1. **为什么审查按钮不等于审查流程**——区分 PR 事件、请求、运行中状态和最终合并门。
2. **API 请求里 effort level 改变了什么**——讨论按风险分级、默认值继承和显式覆盖。
3. **审查结果怎样回到 CI**——设计幂等触发、结果存档、失败重试和人工接管。
4. **模型评论、测试和 CODEOWNERS 谁负责最终判断**——建立多信号门禁，避免单一 Agent 结论阻塞或放行。
5. **如何评测审查深度是否值得**——用缺陷召回、误报、等待时间、Token/请求成本和开发者修复率做对照。

### 写作所需证据

- **已经有**：GitHub 官方公告中的 REST/GraphQL 支持、每次请求设置 effort、Balanced 默认值的生效日期和计划范围。
- **需要补做**：阅读 GitHub API 文档，核对请求字段、返回状态、权限、回调和限流；用一个本地 GitHub Actions 模拟器按文件风险分配 effort，记录审查结果进入检查门的路径。
- **适合配图**：PR 事件→风险分类→Copilot review API→结果回写→测试/CODEOWNERS→合并门的流程图；Lite/Balanced/高 effort 的成本—等待—召回三轴对照图。
- **关键未验证点**：API 返回是否提供稳定的 run ID 和增量结果、不同 effort 的真实质量差异、失败重试是否重复计费，以及企业权限和审查数据保留策略。

## 3. 模型的隐藏推理也会被“搬运”：OpenAI 如何防一场 Agent 式蒸馏攻击

### 热点是什么

OpenAI 在 **2026-09-30** 披露并总结了一场协同的模型蒸馏活动。官方称最早在 7 月 1 日观察到低量行为，7 月 24—25 日出现约 16,000 次相关请求，来自超过 4,000 个用户；进一步调查发现超过 15,000 个用户的相关提示模式，并在 7 月 28 日完成阻断。攻击者没有入侵数据库或破解加密，而是操纵模型交互，试图让受保护的推理内容以请求者可见的形式被复制；官方还描述了跨会话转移加密推理、要求另一会话解密转录等模式。

OpenAI 表示已采用账号处置、基础设施控制、跨用户/工作区/模型族的隐藏推理保护、流式输出拦截和行业共享。官方同时说核心活动归因于与 Moonshot AI 相关的人员，但不能确定相关时段的所有操作者都来自同一方；文中的请求数字是尝试次数，不代表成功提取次数。

原始资料：

- [Disrupting a coordinated model-distillation campaign（OpenAI，2026-09-30）](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)

### 为什么值得写

**事实**：攻击面不只是模型权重和 API 密钥，工具输出、流式响应、跨会话状态和可重放的推理工件都可能成为蒸馏通道。**我的判断**：一旦 Agent 能跨轮次、跨工具和跨用户工作区保存中间产物，安全边界就必须覆盖“模型生成过什么”和“哪些中间状态能被再次读取”。文章可以把一个带工具调用的 Agent 画成数据流，标出隐藏推理、工具结果、缓存、日志和用户可见回答的边界，再讨论检测、阻断和误伤之间的取舍。

### 建议标题

**模型的隐藏推理也会被“搬运”：OpenAI 如何防一场 Agent 式蒸馏攻击**

### 文章梗概

模型 API 看起来只返回答案，但长任务 Agent 还会产生流式片段、工具结果、压缩摘要和可重放状态。OpenAI 披露的蒸馏活动说明，攻击者可以把这些交互面组合起来，试图让受保护推理跨会话暴露。文章不复现真实攻击，而是用一个脱敏的玩具 Agent 画出“生成—存储—重放—输出”的数据流，解释账号治理、跨工作区隔离、流式拦截和工具输出检查各自堵在哪里，再讨论误报、可观测性和第三方托管部署的责任边界。官方数字只代表尝试规模，不能写成成功率。

### 结构提纲

1. **为什么隐藏推理不是单个字段**——区分可见答案、流式片段、工具输入输出、压缩摘要和缓存工件。
2. **一次蒸馏活动怎样穿过交互链**——按跨会话复制、解密转录、批量请求和第三方服务重放还原攻击面。
3. **四层防线各自能挡什么**——对照账号治理、会话隔离、流式检测、模型拒答与工具输出审查。
4. **Agent 日志怎样既可审计又不变成泄露源**——设计脱敏、访问控制、保留期限和不可重放标记。
5. **哪些结论仍不能从公开披露推出**——区分尝试量、成功量、归因判断和独立验证。

### 写作所需证据

- **已经有**：OpenAI 对时间线、请求规模、攻击手法、处置措施、第三方服务协作和归因不确定性的原始披露。
- **需要补做**：阅读 OpenAI 对跨会话推理保护和流式输出处理的后续说明；写一个只使用虚构字符串的 Agent，演示状态分层、脱敏日志和重放拒绝，不接触真实模型隐藏推理。
- **适合配图**：模型→流式输出→工具→缓存/日志→用户的攻击面数据流图；账号、会话、工作区、模型族和第三方服务组成的分层防御图。
- **关键未验证点**：真实成功提取比例、工具输出攻击的检测覆盖率、第三方托管部署的责任分工、误拦截对正常调试的影响，以及披露中“受保护推理”的具体协议边界。

## 4. 多模态 Agent 不是“看见就行”：Google Guided Vision 的相机、语音和安全边界

### 热点是什么

Google 在 **2026-10-01** 宣布 Guided Vision 在 Gemini Live 的兼容 Android 设备上推出，面向盲人、低视力用户和需要视觉辅助的人。用户在 Live 会话里共享摄像头，系统以语音描述环境、读取小字、查找物体，并在镜头偏高、偏近或偏离目标时用自然语言提示用户平移、俯视或后退，以获得更清晰的视觉上下文。Google 称该能力与 Aira 合作，用数万小时视觉解释数据训练，并由 Trusted Tester 网络的 1,000 多名成员参与压力测试和安全护栏改进。

Google 明确把 Guided Vision 定位为辅助工具，不是医疗设备、导航工具、白手杖或安全出行替代品；文章还说明它可能出错，并要求用户继续使用现有安全实践。产品在 Gemini Live 支持的地区和语言中逐步可用。

原始资料：

- [Guided Vision in Gemini Live: built for accessibility（Google，2026-10-01）](https://blog.google/innovation-and-ai/products/gemini-app/guided-vision-gemini-live/)

### 为什么值得写

**事实**：Guided Vision 把摄像头输入、视觉理解、语音反馈和“请重新取景”做成连续对话，而不是一次图片问答；Google 还把社区测试和不可替代的安全边界写进产品说明。**我的判断**：多模态 Agent 的关键不只是模型看得准，还包括它能否发现输入不够、主动要求补充、把不确定性说清楚，并在高风险场景拒绝给出安全保证。文章可以把“找桌上的药盒”拆成观察、取景反馈、识别、确认和停止五个状态。

### 建议标题

**多模态 Agent 不是“看见就行”：Google Guided Vision 的相机、语音和安全边界**

### 文章梗概

让模型看一张照片很容易，陪用户在真实空间里找到东西却完全是另一件事：镜头偏了要不要提示，识别不确定要不要继续问，涉及出行又该在哪里停下。Google Guided Vision 把相机共享、视觉描述、语音追问和重新取景接成一个实时循环，并明确不承担导航或安全出行责任。文章从“在厨房找到调料”这个低风险任务开始，画出观察—反馈—确认—停止的状态机，再分析社区测试、隐私和错误提示如何影响产品边界，最后给出多模态 Agent 的输入质量、响应延迟和风险拒答指标。

### 结构提纲

1. **一次图片问答为什么不等于实时视觉助手**——拆连续视频、语音回合、用户移动和状态保持。
2. **Agent 如何判断“我还没看清”**——解释重新取景提示、补充问题和输入质量门。
3. **从识别到行动建议中间缺哪一层**——区分描述、定位、确认和不可逆行动。
4. **社区测试如何进入安全护栏**——分析 Aira 合作、Trusted Tester 和多语言场景反馈的作用。
5. **怎么评测辅助性而不制造安全承诺**——设计清晰度、首响应延迟、误识别、拒答和用户纠正指标。

### 写作所需证据

- **已经有**：Google 官方说明中的功能范围、重新取景提示、Aira 数据合作、1,000 多名测试者、支持入口和明确的非导航边界。
- **需要补做**：阅读 Gemini Live 与 Guided Vision 的支持页面，核对设备、地区、语言、摄像头权限和数据保留；用公开视频或静态物品搭建一个只读的“取景不足→追问”原型。
- **适合配图**：摄像头帧→质量判断→语音提示→新帧→描述/追问的闭环流程图；低风险描述、需确认操作和应拒答场景的风险分层图。
- **关键未验证点**：真实首响应与连续帧延迟、遮挡和弱光下的误识别、摄像头数据是否保存、用户纠正如何更新状态，以及“主动提示”是否会增加认知负担。

## 5. 记忆越多，Agent 未必越聪明：为什么不干预检索就测不出记忆价值？

### 热点是什么

预印本 **Causal Memory Policy: Making Memory Utility Identifiable by Intervening on Retrieval** 于 **2026-10-01** 提交 arXiv。论文指出，记忆系统通常只在检索到某条记忆时观察它对任务的影响；从未被抽到上下文的记忆，无论有用还是无用，结果都一样，这形成了 retrieval-level positivity violation。作者提出 CMP：固定一部分上下文槽位，用已知倾向概率抽取记忆，再用 self-normalized inverse propensity weighting 估计记忆效用，并推导无偏性、方差和不可逆保留操作下的决策规则。

论文报告 LongMemEval 中 54%、LoCoMo 中 67% 的必要记忆存在识别失败；CMP 把 required 与 non-required 的区分 AUC 从 0.54 提升到 0.66。但按查询估计出的效用最高可到 0.78 AUC，仍不能预测同一记忆在未见查询上的价值。代码链接是匿名评审仓库，结果仍需独立复跑。

原始资料：

- [Causal Memory Policy: Making Memory Utility Identifiable by Intervening on Retrieval（arXiv:2610.02070，提交于 2026-10-01）](https://arxiv.org/abs/2610.02070)
- [论文代码（匿名评审仓库）](https://anonymous.4open.science/r/cmp-release-D0C3/)

### 为什么值得写

**事实**：CMP 不是再做一个向量库，而是改变检索策略，让系统有机会观察“本来不会被取出的记忆”对任务的影响。**我的判断**：Agent 的记忆评测经常把“被成功召回”误当成“值得长期保留”，这会把检索偏差写进记忆策略。文章可以从客服工单中的历史结论开始，区分记忆写入、候选生成、检索、注入和保留五个动作，说明干预会增加上下文成本，却为撤销错误记忆提供了可解释的证据。

### 建议标题

**记忆越多，Agent 未必越聪明：为什么不干预检索就测不出记忆价值？**

### 文章梗概

一个 Agent 总是召回同一条旧经验，于是系统以为它“很有用”，却从没给那些从未被召回的记忆一次被验证的机会。Causal Memory Policy 把问题写成因果识别：如果检索概率从来不是正的，记忆效用就无法估计。文章从历史工单记忆开始，拆开写入、候选、检索、注入和长期保留，推导为什么要保留少量已知概率的探索槽位，再解释逆倾向加权和“当前查询有效、不代表未来有效”的限制。最后给出低成本的线上试验设计，避免把一次命中当成永久记忆策略。

### 结构提纲

1. **记忆系统到底在估计什么**——区分写入成功、召回概率、当前任务帮助和跨任务长期价值。
2. **检索不探索为什么会造成不可识别**——用一个从未被抽到的记忆反例说明 positivity violation。
3. **CMP 如何干预 retrieval**——拆固定探索槽位、已知倾向概率和 self-normalized inverse propensity weighting。
4. **从效用估计到保留决策还差什么**——解释不可逆删除/保留操作、方差和未来查询分布变化。
5. **工程上怎样做一轮小规模试验**——设计灰度探索、查询分层、撤销机制和成本/质量对照。

### 写作所需证据

- **已经有**：论文对 retrieval-level positivity violation 的定义、CMP 的估计方法、LongMemEval/LoCoMo 的失败比例、AUC 变化和跨查询泛化限制。
- **需要补做**：通读论文的因果分解、估计量和方差推导；尝试运行匿名代码或先实现一个两臂检索模拟器，比较只取 top-k 与带探索槽位的估计偏差。
- **适合配图**：记忆写入→候选→检索→注入→任务结果→保留策略的因果图；“从不被检索”与“有概率被探索”的对照流程图。
- **关键未验证点**：匿名代码是否可复现论文数字、探索槽位对上下文和延迟的开销、不同记忆类型的倾向概率、跨查询效用如何聚合，以及线上删除操作的回滚窗口。

## 今日优先写作建议

优先写 **“记忆越多，Agent 未必越聪明：为什么不干预检索就测不出记忆价值？”**。这篇预印本给了一个很具体的工程切口：记忆系统不是“存得越多越好”，甚至也不是“召回后看效果”就够了，而要主动留出可解释的检索干预。论文有清晰的问题定义、公式、公开代码和明确限制，适合做一张因果图、一个小型模拟实验，再和已有的记忆系统文章形成递进。需要把作者的 AUC 和失败比例严格标成预印本结果，先复跑再下结论。
