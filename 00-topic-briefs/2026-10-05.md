## 今日判断

今天更适合写“Agent 系统怎么被验证和维护”，不适合追一条没有材料的新模型新闻。GitHub 的模型退役公告把一个经常被忽略的事实摆到台面上：Agent 依赖的模型标识会变化，替换后行为、价格和权限都可能变。四篇预印本则分别从配置方差、过程级评测、共享状态和显式信念状态切入，回答“为什么同一个模型换一套运行系统，结果会完全不同”。它们都适合做代码级的小实验或状态机模拟，但公开材料尚不足以证明论文数字能迁移到生产环境。

## 1. 模型下线不是改名：Copilot Agent 依赖怎样迁移和回归

### 热点是什么

GitHub 在 **2026-10-02** 宣布，以下模型在 Copilot Chat、inline edits、ask/agent 模式和代码补全等全部 Copilot 体验中退役：Gemini 3.5 Flash、Gemini 3.6 Flash、Kimi K2.7 Code 和 Claude Opus 4.7。公告同时给出建议替代模型：前两个迁移到 Gemini 3.8 Flash，Kimi K2.7 Code 迁移到 Kimi K3，Claude Opus 4.7 迁移到 Claude Opus 5.5。企业管理员可能需要在模型策略中显式打开替代模型；退役模型不需要用户手工删除。

GitHub 的模型文档还提醒，模型可用性会变化，企业可以限制模型访问；自动选择有长期支持模型作兜底，评估模型则可能随时加入、更新或移除。模型退役历史表记录了这次 10 月 2 日的迁移，但没有承诺替代模型在每类代码任务上行为等价。

原始资料：

- [Selected models in GitHub Copilot deprecated（GitHub Changelog，2026-10-02）](https://github.blog/changelog/2026-10-02-selected-models-in-github-copilot-deprecated/)
- [Supported AI models in GitHub Copilot（GitHub Docs，持续更新）](https://docs.github.com/en/copilot/reference/ai-models/supported-models)

### 为什么值得写

**事实**：一批模型在 Agent 模式和补全等多个入口同时退役，企业还要处理模型策略和替代模型的可见性。**我的判断**：模型名不应该直接写进业务流程里当成永久依赖；真正需要版本化的是“任务—模型—工具—预算”的组合。替代模型即使接口兼容，也可能改变工具选择、补丁范围、推理深度和失败模式。文章可以用一个支付模块改动的 Copilot Agent 任务，演示固定模型、自动选择和迁移后的回放差异，把“能调用”与“行为可接受”分开。

### 建议标题

**模型下线不是改名：Copilot Agent 依赖怎样迁移和回归？**

### 文章梗概

周一还能运行的代码 Agent，周五可能已经换了一套模型；接口没变，工具选择、补丁范围和等待时间却可能变了。GitHub 这次同时退役四个模型，并要求企业检查替代模型策略，说明模型名称不能直接当作长期契约。文章从一个需要修改支付逻辑的仓库任务开始，建立模型别名、能力标签、预算和回放样本，比较固定模型、自动选择与替代模型在同一任务上的轨迹差异，再设计迁移前后的契约测试和人工兜底。公告只证明了退役与替代关系，质量、成本和安全差异需要读者在自己的任务集上复测。

### 结构提纲

1. **模型标识为什么不是稳定依赖**——区分模型名称、能力、计划权限、客户端版本和长期支持策略。
2. **一次模型退役会影响哪些 Agent 状态**——从提示、工具选择、补丁、上下文长度和预算逐项梳理行为漂移。
3. **迁移前如何做可回放基线**——固定任务输入、仓库快照、工具权限、超时和评分标准。
4. **自动选择、别名和显式 pin 怎样组合**——比较稳定性、可用性和维护成本，说明各自适用边界。
5. **替代模型上线后的门禁**——把测试通过、工具调用正确性、补丁差异、成本和人工复核纳入灰度。

### 写作所需证据

- **已经有**：GitHub Changelog 的退役清单、建议替代模型、影响范围和企业模型策略说明；GitHub Docs 的支持模型、自动选择、长期支持与退役历史。
- **需要补做**：阅读模型策略和自动选择 API/CLI 文档；在一个固定仓库任务集上记录模型名、调用工具、补丁 diff、Token、耗时和失败原因，模拟替代模型切换。
- **适合配图**：模型别名→能力策略→任务路由→工具调用→回放评分的迁移流程图；固定模型、自动选择和 LTS 兜底的决策表。
- **关键未验证点**：替代模型在真实 Agent 任务上的质量差异、企业策略传播延迟、客户端版本兼容性、自动选择的实际兜底触发条件，以及模型退役是否改变数据处理边界。

## 2. Agent 是系统，不只是模型：为什么同一配置重复跑也会变

### 热点是什么

预印本 **Agents Are Systems, Not Models: Rethinking Agentic Evaluation** 于 **2026-10-01** 提交 arXiv。作者在四个科学任务上测试一个需要找到并正确操作专业模型的 coding agent，比较任务信息、推理、自检、时间预算和 backbone model 五类配置。论文报告：大约 **54% 的结果方差来自重复运行同一配置**，而不是更换配置；提供给 Agent 的信息对结果影响最大，超过时间预算和模型大小。作者还观察到，单靠提示“请验证”几乎不会改变验证行为，提供专用验证工具却能明显改变轨迹，并发布了超过 18,000 条 Agent 轨迹。

这些结论来自论文作者的新 benchmark 和预印本实验，任务数量、模型版本和运行预算都需要在阅读全文后核对，不能直接当作所有 Agent 的通用比例。

原始资料：

- [Agents Are Systems, Not Models: Rethinking Agentic Evaluation（arXiv，提交于 2026-10-01）](https://arxiv.org/abs/2610.01618)

### 为什么值得写

**事实**：论文把任务信息、工具化验证、时间预算和模型选择放在同一个配置空间里，并报告重复运行本身带来很大波动。**我的判断**：只比较“模型 A 的成功率”和“模型 B 的成功率”，可能把提示、工具和随机轨迹的影响混在一起。对工程团队来说，评测对象应该是可配置的完整 harness：输入材料怎么给、验证能力在哪里、允许跑多久、失败后能否继续。文章可以用一个“查资料并运行专用模型”的任务，逐个关闭信息、验证工具和时间预算，展示哪个改动真的改变了行为。

### 建议标题

**Agent 是系统，不只是模型：为什么同一配置重复跑也会变？**

### 文章梗概

同一个模型、同一份提示、同一个任务，为什么一次找对工具，下一次却在错误的模型上浪费时间？一篇 10 月 1 日提交的预印本把 Agent 当成可配置系统来测：任务信息、自检方式、时间预算和 backbone 都会改变结果，而且重复同一配置本身就有很大波动。文章从一个可回放的科学检索任务开始，固定模型和仓库后逐项改变输入材料、验证工具与时间限制，记录轨迹而不只看最终答案，再讨论如何用置信区间、成本和校准度报告差异。论文数字只作为待复核的研究结果，不能直接当成模型排行榜。

### 结构提纲

1. **为什么模型排行榜不能代表 Agent 质量**——把模型、提示、工具、时间和随机轨迹拆成独立变量。
2. **五类配置怎样改变执行轨迹**——用任务信息、推理、自检、时间预算和模型逐一建立实验矩阵。
3. **提示里的“请自检”为什么不够**——对照自然语言要求与真正可调用的验证工具。
4. **重复运行的波动如何进入报告**——设计多次运行、置信区间、成本和轨迹聚类，而不是只报一次成功率。
5. **工程团队该固定什么、开放什么**——给出任务集、工具接口、预算和模型替换时的评测契约。

### 写作所需证据

- **已经有**：预印本对四个科学任务、五类配置、54% 方差、信息影响和专用验证工具效果的摘要说明，以及 18,000 多条轨迹的发布承诺。
- **需要补做**：通读论文的 benchmark 定义、运行次数、模型和预算；下载轨迹或重建一个小型任务，比较“提示自检”和“验证工具”两种条件。
- **适合配图**：Agent 配置空间的实验矩阵；同一任务多次运行的轨迹分叉图；最终答案、工具验证和校准度的三层评测图。
- **关键未验证点**：54% 方差在不同模型和任务上的稳定性、18,000 条轨迹的许可与格式、验证工具的额外成本，以及论文结果能否迁移到代码修复和工单排查。

## 3. 最终答案对了还不够：企业 Agent 为什么要测过程

### 热点是什么

预印本 **Continuous Process-Level Evaluation for Evolving Enterprise AI Agent Skills** 于 **2026-10-01** 提交 arXiv。作者提出一套持续评测框架，把最终结果检查和过程检查放在一起，针对企业 Value Aware Resiliency 系统中的 Revenue 与 Productivity 两个 skill 变体，覆盖工具选择、参数、执行顺序和数据库完整性。框架会独立计算每次运行的 ground truth，生成可复用的模板测试，并使用范围很窄的 LLM judge 辅助检查。

论文报告了 240 次试验，跨两个 skill、两个规格变体、两个 harness 和三个模型。在通过最终数值检查的 175 次运行中，有 162 次仍被过程评测发现偏差（92.6%）；使用更宽的最终状态定义时，151/164 次运行仍违反轨迹检查（92.1%）。作者还报告依赖归因能把每次平均 6.34 个失败检查归并为 2.65 个根因。纵向验证真实 API 演进仍被列为未来工作。

原始资料：

- [Continuous Process-Level Evaluation for Evolving Enterprise AI Agent Skills（arXiv，提交于 2026-10-01）](https://arxiv.org/abs/2610.01833)

### 为什么值得写

**事实**：论文中的 Agent 有时最终数字正确，却在工具选择、参数、执行顺序或数据库状态上留下过程偏差。**我的判断**：企业系统不能只在最后比对一个答案；过程检查更接近权限边界、幂等性和数据完整性，但也会增加模板维护成本。文章可以把“更新一个客户账单”的 skill 拆成工具调用图，展示最终余额正确却走了错误接口的情况，再设计一套把结果、过程、根因和规格版本一起保存的回归框架。

### 建议标题

**最终答案对了还不够：企业 Agent 为什么要测过程？**

### 文章梗概

账单最终算对了，Agent 却调用了不该调用的工具；报表数字也对，数据库里却多写了一行。企业 Agent 的风险经常藏在过程里。10 月 1 日提交的预印本把最终状态检查和轨迹检查放进同一套持续评测，检查工具、参数、顺序和数据库完整性。文章用一个“更新客户账单”的小型 skill 演示 ground truth、模板测试、过程事件和根因归并，再讨论模型或 API 变化时怎样发现漂移。论文的 92.6% 与 92.1% 只代表作者的 240 次试验，哪些验证仍要本地复做会单独标出。

### 结构提纲

1. **最终状态为什么会掩盖错误过程**——构造“结果相同、工具路径不同”的最小反例。
2. **过程级 ground truth 怎么定义**——为工具、参数、顺序、写入和权限分别设可检查条件。
3. **模板测试如何跟着 skill 规格变化**——把规格版本、运行输入和预期轨迹绑定起来。
4. **LLM judge 应该放在哪一层**——区分程序化断言与需要语义判断的窄范围检查。
5. **从失败检查归并到可修复根因**——用依赖图降低告警数量，同时保留原始轨迹。
6. **持续评测的边界**——讨论 API 演进、测试模板维护、误报和纵向证据缺口。

### 写作所需证据

- **已经有**：论文对两个 skill、两个规格、两个 harness、三个模型、240 次试验、过程偏差比例和根因归并的摘要结果。
- **需要补做**：通读论文的模板格式、断言实现、数据库模型和统计区间；在本地用 SQLite 与假的账单工具复现“最终正确但过程错误”的两条轨迹。
- **适合配图**：skill 运行事件→工具检查→数据库检查→最终状态→根因归并的流水线；规格版本变化导致回归测试更新的生命周期图。
- **关键未验证点**：论文 240 次试验的具体任务分布、LLM judge 的误报、模板在真实 API 变更中的维护成本，以及根因归并是否会隐藏多个独立故障。

## 4. 每个 Agent 都没说错，为什么团队还是会错？先把共享状态和提交管起来

### 热点是什么

预印本 **Global Coherence: When Every Agent Is Right and the Team Is Still Wrong** 于 **2026-10-01** 提交 arXiv，把多 Agent 协作失败定义为共享状态问题，而不只是模型能力问题。论文提出 Observation-Aliasing Impossibility Theorem：如果多个世界产生同一个观测，却要求不同且互斥的动作，那么仅增加推理、角色、消息或采样无法恢复缺失的信息。作者给出一套运行时语义，把拓扑、状态类别、可逆转换、局部视图合并和最小历史放在 harness 中，并主张模型提出方案、harness 管理共享状态和提交。

论文的九组研究报告了几个对照：决定事件可见时控制任务为 40/40，隐藏时测试组为 12—17/40；TeamBench 中普通团队 5/5 次超过共享预算，只有可见计数仍有 4/5 次违规，加上提交约束后为 0/5；在 silent revert 的 tau2-bench Telecom 场景中，带当前状态检查的得分为 0.07，而带 harness 约束为 1.00。它是单篇预印本的作者实验，具体环境和统计不应被当成通用保证。

原始资料：

- [Global Coherence: When Every Agent Is Right and the Team Is Still Wrong（arXiv，提交于 2026-10-01）](https://arxiv.org/abs/2610.02036)

### 为什么值得写

**事实**：论文把“局部决策都合法、整体结果却非法”归因到不可见的共享事实，并用提交约束而非更多对话来修复预算和回滚问题。**我的判断**：多 Agent 系统首先需要一个可读、可锁定、可提交的共享状态；投票和角色分工解决不了事实缺失，也解决不了两个 Agent 同时写同一资源。文章可以用一个团餐优惠额度被两个 Agent 同时扣减的场景，展示局部视图、隐藏回滚、版本检查和 commit gate 的差异。

### 建议标题

**每个 Agent 都没说错，为什么团队还是会错？先把共享状态和提交管起来**

### 文章梗概

两个 Agent 分别检查了订单和优惠规则，都给出局部正确的结论，合并后却把同一份团餐额度扣了两次。Global Coherence 预印本把这类问题称为共享状态缺失，并用不可观测世界的反例说明：更多角色和消息不能替代一个看不见的事实。文章从额度扣减的最小模拟开始，比较普通消息协作、共享计数、版本检查和 commit gate，画出“模型提案—harness 验证—提交”的执行链。论文的 40/40、0/5 等结果只作为作者实验，重点放在状态所有权、回滚和适用边界，而不是宣传多 Agent 一定更可靠。

### 结构提纲

1. **局部正确如何拼出全局错误**——用共享额度与 silent revert 构造最小协作反例。
2. **不可观测事实的上限在哪里**——解释 observation aliasing，区分信息缺失和推理能力不足。
3. **共享状态该由谁维护**——设计权威计数、版本、锁和最小历史字段。
4. **消息、投票和提交门分别解决什么**——比较协商、可见状态、事务提交和回滚的执行语义。
5. **怎样测全局一致性**——用隐藏/可见事实、并发写入、预算越界和回滚恢复构造实验矩阵。
6. **何时不值得上多 Agent**——明确单 Agent 已持有全部相关状态时，额外协作的成本与收益边界。

### 写作所需证据

- **已经有**：预印本的 observation-aliasing 定理、运行时语义、九组研究以及预算和 silent revert 的作者报告。
- **需要补做**：通读其状态模型和 benchmark 定义；用两个 Python worker、一个版本化存储和一个 commit gate 复现额度重复扣减与回滚。
- **适合配图**：局部视图汇合到权威状态、提交和回滚的时序图；普通消息协作与 commit gate 的对照架构图。
- **关键未验证点**：单作者理论与实验的独立复核、tau2-bench 配置、harness 得分的统计区间，以及状态锁对延迟和吞吐的影响。

## 5. 长任务 Agent 需要的不是更多历史，而是一份会更新的“当前信念”

### 热点是什么

预印本 **Beyond Memory: Harnessing Long-Horizon Agents with Explicit Belief States** 于 **2026-10-01** 提交 arXiv。作者提出 PoS（Inference-Time Framework），不再把交互历史直接当作决策上下文，而是持续维护显式 belief state：一部分描述当前世界状态，另一部分记录尚未解决的任务要求。框架会检查信念的一致性、监控任务进度，识别 Agent 反复行动却没有接近目标的 **Belief Trapping**，再按陷阱模式和未解决要求选择恢复策略。

论文称在覆盖执行和诊断的四个 benchmark、三个 LLM backbone 上，PoS 获得每个 benchmark 的最高总体成绩；消融实验显示一致性检查和恢复机制都重要，context-scaling 实验则报告对上下文增长更有韧性。这些是预印本作者结果，不能替代在真实长任务上的独立实验。

原始资料：

- [Beyond Memory: Harnessing Long-Horizon Agents with Explicit Belief States（arXiv，提交于 2026-10-01）](https://arxiv.org/abs/2610.01415)

### 为什么值得写

**事实**：PoS 把“当前世界是什么”和“任务还缺什么”分开维护，并在检测到无进展时按类型恢复。**我的判断**：很多 Agent 的记忆设计停留在“把历史压缩得更短”，却没有一份可检查的当前状态；长任务真正需要的是可更新、可验证、能指出缺口的工作记忆。文章可以用一个跨天排查营销活动的工单，比较完整日志、摘要记忆和显式 belief state 在价格规则变化、证据冲突和重复行动下的差别。

### 建议标题

**长任务 Agent 需要的不是更多历史，而是一份会更新的“当前信念”**

### 文章梗概

长任务最麻烦的时刻，不是上下文窗口装不下，而是 Agent 还在执行失效假设：优惠规则变了，订单状态没更新，它却重复调用同一工具。Beyond Memory 预印本提出显式 belief state，把当前世界状态和未解决任务要求写成可检查对象，用一致性检查和进度监控识别“越做越远”的 Belief Trapping。文章用一个跨天排查营销活动的工单，对照日志截断、摘要记忆和 belief state 在冲突证据、重复行动和恢复路径上的差别，再讨论状态维护成本。论文 benchmark 结果只作为待复核线索。

### 结构提纲

1. **历史记录为什么不能直接当当前状态**——拆出事实、假设、未完成要求和过期证据。
2. **belief state 应该记录哪些字段**——定义世界估计、任务缺口、证据来源、置信度和版本。
3. **一致性与进度如何被检查**——设计冲突检测、停滞计数和“重复行动”判定。
4. **恢复策略为什么要看陷阱类型**——对照补充观察、重新规划、回滚状态和请求人工确认。
5. **怎么和现有记忆系统配合**——区分长期案例、当前工作记忆和不可直接继承的旧假设。
6. **长任务的验收指标**——加入状态一致性、有效进展、恢复成功率、上下文成本和人工接管率。

### 写作所需证据

- **已经有**：预印本对 PoS、belief state、Belief Trapping、一致性检查、进度监控和四个 benchmark 的摘要结论。
- **需要补做**：通读 PoS 的状态格式、恢复分类和消融设置；在本地工单模拟器中对照日志截断、摘要和显式状态三种方案。
- **适合配图**：历史事件→当前 belief→工具动作→新证据→一致性检查→恢复的闭环图；三种记忆方案的状态字段对照图。
- **关键未验证点**：四个 benchmark 的任务构成、三个 backbone 和上下文增长曲线、belief 更新的额外调用成本，以及状态错误时是否会造成更自信的错误。

## 今日优先写作建议

优先写 **“最终答案对了还不够：企业 Agent 为什么要测过程？”**。它和真实企业系统的连接最直接：工具选择、参数、执行顺序和数据库完整性都能落到可运行的断言，文章也能用一个小型账单 Agent 做出“最终数字正确但过程违规”的对照。论文给出了清晰的测试维度和明确的未验证点，既有研究新鲜度，也有工程落地路径。建议先复现一个假的账单工具和两条轨迹，再引用论文的 240 次试验与 92.6%/92.1% 数字，并始终标明这些是预印本作者结果。
