## 今日判断

今天有一个值得优先写的真实产品与开源评测更新：GitHub 把代码审查 Agent 的数据集、标注、评分和自助运行入口公开了。它比“某个模型又提高了几个点”更有工程价值，因为读者可以追问评测集怎样构成、什么叫有效评论、离线分数能不能预测线上体验。

另外四篇 10 月 2 日提交的论文，分别把 Agent 的难题往更底层推进：harness 能不能自己变难、执行和验证怎样一起分配预算、网页证据如何跨语言和模态连起来、终端命令怎样按依赖关系分配训练信用。它们适合写成机制分析和小实验，不适合直接把论文的结果改写成生产结论。

## 1. 代码审查 Agent 不能只看评论数：GitHub 为什么做 ReviewBench

### 热点是什么

GitHub 在 **2026-10-05** 发布 ReviewBench，一个面向 AI code review agent 的公开离线评测。GitHub 先分析了 **1.039 亿个 Pull Request** 的语言、仓库规模和变更形态，再选出 **219 个来自 187 个公开仓库、覆盖 19 种语言**的 PR 作为代表性语料。每个 PR 的参考问题来自人工审查、多个前沿模型、静态分析和作者后续修复等多种来源，再经过语义去重和统一 rubric 判断。

ReviewBench 将 finding 按严重程度和类别结构化，提供 grounded precision/recall 与 augmented precision/recall 等指标，允许按 correctness、security、reliability、maintainability、testing 等类别切片。GitHub 称独立高级工程师对 golden true-positive 的复标一致率为 **96.6%**，并开放完整数据集、评分方法、judge 配置、自助 runner 和 leaderboard。GitHub 还报告，在 Copilot code review 的一个多模型 ensemble 实验中，离线结果与线上 A/B 方向一致：addressed rate 上升 8.0%、recall 上升 13.6%、评论量上升 61%、每次审查成本下降 8.0%；这些是厂商自己的实验，不能当成独立复现。

原始资料：

- [ReviewBench: An open benchmark for AI code review（GitHub Blog，2026-10-05）](https://github.blog/ai-and-ml/github-copilot/reviewbench-an-open-benchmark-for-ai-code-review/)
- [ReviewBench 评测入口](https://review-bench.ai/)

### 为什么值得写

**事实**：ReviewBench 不把“评论越多”当成越好，而是同时记录已知问题的 grounded 指标、对新发现问题的 augmented 指标、严重程度、类别和 precision/recall 偏好。**我的判断**：代码审查 Agent 的关键不是生成一段漂亮解释，而是能在真实 PR 分布里稳定找到值得修的问题，并且让离线改进可以被线上行为验证。文章可以从一个支付改动的 PR 开始，把“发现问题、判断严重度、开发者采纳、线上回归”分成四层，说明 benchmark 能覆盖哪三层、还缺哪一层。

### 建议标题

**代码审查 Agent 不能只看评论数：拆开 GitHub 的 ReviewBench**

### 文章梗概

一个代码审查 Agent 一次发 30 条评论，可能只是放大噪声；另一个只提 3 条，却抓住权限和数据一致性问题。GitHub 10 月 5 日发布 ReviewBench，用 1.039 亿个 PR 的分布抽样，多来源建立 golden set，再按严重度、类别和 precision/recall 评分。文章从支付 PR 开始，拆数据代表性、finding 去重、grounded/augmented 指标和线上 addressed rate，设计一个可复跑的小评测。96.6% 一致率与线上收益均为官方报告，仍需独立复核。

### 结构提纲

1. **为什么评论数量不是质量指标**——用同一 PR 的高噪声与高价值两种输出区分 precision、recall 和严重度。
2. **ReviewBench 怎样让测试集更像真实工作**——解释 1.039 亿 PR 的分布分析、219 个 PR 的抽样和变更规模偏置。
3. **golden set 为什么要容纳多个来源**——拆人工、模型、静态分析、作者修复、语义去重和统一 rubric。
4. **grounded 与 augmented 指标分别回答什么**——说明固定已知问题和允许发现新问题的评测差别。
5. **离线分数怎样连接线上体验**——对照 addressed rate、仍需人工发现的缺陷、评论量和成本。
6. **自己接入时还要补哪些验证**——讨论仓库领域差异、数据泄漏、judge 偏差、隐私和版本化。

### 写作所需证据

- **已经有**：GitHub 官方文章中的 PR 规模、语料分布、219/187/19 的代表性语料、golden set 来源、96.6% 复标一致率、指标定义、自助运行流程和离线—线上实验对照。
- **需要补做**：下载或申请 ReviewBench 数据与 runner，核对数据许可、judge prompt、匹配算法和完整 leaderboard；选一个小型代码审查 Agent 跑 25 个测试 PR，保存逐条 finding 与分数。
- **适合配图**：PR 采样→多来源 finding→语义去重→rubric/judge→grounded/augmented 指标→线上 addressed rate 的证据链；严重度与 precision/recall 的可调评测矩阵。
- **关键未验证点**：219 个 PR 对中文业务仓库的代表性、judge 与人工审查的系统偏差、augmented 指标的分母变化、数据是否含模型训练污染，以及官方 A/B 相关性能否被第三方复现。

## 2. Harness 也会进化：把 Agent 失败变成下一轮更难的题

### 热点是什么

预印本 **Recursive Harness Self-Improvement for Frontier Reasoning Data Synthesis** 于 **2026-10-02** 提交 arXiv。作者提出 task-harness co-evolution：任务分布变难的同时，生成任务的 harness 也一起更新。在线自改进把中间 solver 的失败转成可复用技能；每批任务结束后，系统还会修改 skill、prompt 和 workflow，只有在候选方案能在成本增加受限的情况下生成“更难且仍有效”的任务时才接纳。模型权重和验证标准保持不变。

论文在数学、编码和科学任务上做了 14 轮进化，作者报告平均 solver accuracy 从 100.0% 降到 54.8%；组合在线与批后两种更新时，生成的题目比固定 harness 或只用一种更新更难。作者还报告合成数据能改善下游 SFT/GRPO，27B 学生模型用 1 万条合成数学样本在 APEX 上达到 62.5% mean-16 accuracy。这些都是预印本结果，难度、验证器和训练配方需要阅读全文后复核。

原始资料：

- [Recursive Harness Self-Improvement for Frontier Reasoning Data Synthesis（arXiv，提交于 2026-10-02）](https://arxiv.org/abs/2610.03548)

### 为什么值得写

**事实**：这套方法不直接改模型权重，而是让题目生成器、技能、提示和工作流在固定验证标准下递归变化。**我的判断**：自进化系统最容易把“自己生成的难题”误当成真正进步，因此关键不是循环次数，而是候选变更的验收门、成本上限和停滞检测。文章可以做一个小型代码题生成器：先让 Agent 根据失败样例改写任务模板，再用固定测试和独立求解器筛掉伪难题，展示 harness 的变化怎样影响题目分布。

### 建议标题

**Harness 也会进化：Agent 如何把自己的失败变成下一轮更难的题？**

### 文章梗概

Agent 总解决同一类题，成功率上升不代表能力变强；让它自己出难题，也可能只是把题目写坏。10 月 2 日预印本提出 task-harness co-evolution：从 solver 失败中提取技能，同时更新题目 prompt、workflow 和规则，只有验证通过且成本受控才接纳。文章用代码题生成器做小闭环，固定验证器，记录难度、失败类型、成本与训练收益，再讨论停止条件、数据污染和“难但无效”。14 轮与 27B 结果仅作待复核信号。

### 结构提纲

1. **任务变难和模型变强有什么区别**——拆分题目分布、求解器能力、验证器和训练数据四条变化路径。
2. **在线失败如何变成可复用 skill**——跟踪一次失败从轨迹、抽象、候选技能到下一题生成的生命周期。
3. **批后更新为什么还要改 workflow**——比较只换题目、只换 prompt、同时改 harness 的差异。
4. **候选方案怎样过接纳门**——定义有效性、难度、成本上限、验证器独立性和回滚记录。
5. **如何防止自进化自我欺骗**——引入独立题库、冻结测试集、交叉求解器和停滞检测。
6. **合成数据何时值得进入训练**——把题目难度、可验证性、数据污染和 SFT/GRPO 收益分开验收。

### 写作所需证据

- **已经有**：预印本对 task-harness co-evolution、在线/批后更新、固定权重与验证标准、14 轮难度变化和下游训练结果的摘要说明。
- **需要补做**：通读生成 harness、skill 表示、候选接纳规则和 APEX 评测设置；实现一个只生成 Python 小题的离线循环，用独立测试判定“更难且有效”。
- **适合配图**：solver 失败→skill 提取→harness 修改→题目生成→独立验证→候选接纳的闭环；固定 harness 与共进化 harness 的难度/成本曲线。
- **关键未验证点**：论文 14 轮的任务规模、验证器是否独立、候选成本上限、27B 训练收益的基线与数据污染风险，以及循环在真实企业工单上的迁移性。

## 3. Agent 的执行和验证要不要同时花钱？JOVE 把预算变成在线决策

### 热点是什么

预印本 **JOVE: Joint Execution and Verification for Resource-Aware LLM Task Graphs** 于 **2026-10-02** 提交 arXiv。作者把复杂问题拆成有向无环任务图，允许不同子任务分配给异构 LLM，并在执行同时决定哪些中间输出值得付费验证。验证是异步的，反馈会更新未来的模型分配，因此系统必须在“当前请求多花钱验证”和“用验证换取后续学习”之间做取舍。

JOVE 以长周期预算和单请求延迟约束为条件，假设模型服务质量、调用价格和耗时一开始都未知，每个请求通过混合整数线性规划决定执行器和验证动作，在线学习更新任务相关质量估计，并用 information-gain bonus 计入学习价值。作者在四个 reasoning benchmark 上报告与标准推理基线相当的准确率，同时平均成本和延迟至少降低 3.17 倍；论文仍是预印本，服务质量分布和预算假设需要独立复核。

原始资料：

- [JOVE: Joint Execution and Verification for Resource-Aware LLM Task Graphs（arXiv，提交于 2026-10-02）](https://arxiv.org/abs/2610.03296)

### 为什么值得写

**事实**：JOVE 把执行器选择、付费验证、异步反馈、长期预算和延迟约束放进一个在线优化问题，而不是执行完成后再统一打分。**我的判断**：Agent 规模上来后，验证本身就是一种资源调度；如果每个中间结果都检查，延迟和成本会失控，如果完全不检查，错误会一路传下去。文章可以用一个研究 Agent 的任务图，比较固定验证、随机验证和信息增益驱动验证，展示一次验证如何改变后续模型路由。

### 建议标题

**Agent 的执行和验证要不要同时花钱？JOVE 把预算变成在线决策**

### 文章梗概

一个任务图有十个子任务，便宜模型可以先跑，昂贵模型可以复核，但每次验证都会消耗预算和延迟；最麻烦的是，验证结果还可能改变下一次路由。JOVE 预印本把执行与验证放进同一个在线决策：根据当前质量估计、调用价格、剩余预算和信息增益选择执行器与验证点。文章从一个并行调研任务开始，模拟固定验证、随机验证和信息增益策略，画出反馈如何更新模型选择，再讨论混合整数优化的工程代价、冷启动和失败时的预算保护。论文报告的 3.17 倍只代表作者的四个 benchmark 配置，不能直接推成生产收益。

### 结构提纲

1. **为什么任务图里的验证不是最后一步**——区分中间结果错误、依赖传播、最终回答错误和可提前停止。
2. **执行器选择和验证选择如何耦合**——建立任务、模型、价格、质量和延迟的状态表。
3. **信息增益为什么也要计入预算**——对照只追求当前准确率与愿意为未来学习付费的策略。
4. **MILP 在线求解适合什么规模**——讨论决策频率、近似求解、冷启动和服务波动。
5. **如何做一轮可复跑的对照实验**——固定任务图、模型池、预算和延迟，记录质量、成本、等待和学习速度。
6. **什么时候验证不值得做**——给出高置信、低风险、不可恢复和强依赖任务的边界。

### 写作所需证据

- **已经有**：预印本对 DAG 任务图、异构模型、异步付费验证、长期预算、MILP 决策、在线学习和四个 benchmark 结果的摘要说明。
- **需要补做**：通读质量估计、regret、information-gain bonus 和 MILP 约束；用三个假的 LLM 服务模拟价格、耗时和质量逐步变化，比较三种验证策略。
- **适合配图**：任务图中执行器、验证器和反馈回路的时序图；预算在当前质量、验证成本和未来信息之间分配的决策图。
- **关键未验证点**：3.17 倍的基线和硬件/价格假设、MILP 求解耗时、验证器本身的错误、异步反馈延迟，以及真实 API 质量漂移时的稳定性。

## 4. 浏览 Agent 真正难的不是搜到网页，而是把跨语言证据串起来

### 热点是什么

预印本 **HyperBrowseComp: A Multilingual and Multimodal Stress Test for Web-Browsing Agents** 于 **2026-10-02** 提交 arXiv。作者构建了 **423 个由人工编写并验证的问题**，覆盖 **13 种语言**；题目要求找到简洁、公开可验证的答案，但线索可能分散在视频、扫描文档、图片、地图等异构来源中，需要多步发现和连接证据。作者先用不能上网的模型过滤过于简单、只靠参数记忆就能回答的问题。

论文在统一 Agent 协议下比较 provider-native search 与共享外部检索 harness，并对部分问题做人工评测。作者将难度定义为跨语言、跨模态和多步证据发现，而不是单纯把网页数量做大。论文目前提供 benchmark 设计和评测协议，具体模型分数、检索器差异和人工样本结果需要阅读全文与复跑后再引用。

原始资料：

- [HyperBrowseComp: A Multilingual and Multimodal Stress Test for Web-Browsing Agents（arXiv，提交于 2026-10-02）](https://arxiv.org/abs/2610.03574)

### 为什么值得写

**事实**：HyperBrowseComp 把浏览任务从“搜到一个相关网页”提升到跨语言、跨模态、跨站点线索链，并用统一协议比较原生搜索和共享检索 harness。**我的判断**：浏览 Agent 的可靠性瓶颈通常在证据链，而不是回答生成；如果没有来源、媒介、时间和实体之间的关系图，模型很容易把几个局部正确的片段拼错。文章可以构造一个跨语言门店活动核验任务，让 Agent 先找文字公告，再确认图片/视频时间和地图位置，评测证据覆盖、引用正确性和中途失败恢复。

### 建议标题

**浏览 Agent 真正难的不是搜到网页，而是把跨语言证据串起来**

### 文章梗概

“帮我确认这家店去年是否参加过某个活动”看似只是搜索，实际可能要读外语公告、看视频日期、核对扫描文件和地图。HyperBrowseComp 用 423 个多语种、多模态、多步线索问题测试持久信息搜寻，并比较原生搜索与共享检索 harness。文章从跨语言门店核验开始，设计证据节点、来源时间、媒体类型和引用回链，分析发现、转译、交叉验证与停止判断，给出证据覆盖率和可回放轨迹指标。论文分数与人工评测需先复做。

### 结构提纲

1. **为什么“搜到相关页面”不等于完成任务**——区分发现候选、确认实体、连接线索和形成可核验结论。
2. **多语言与多模态证据怎样进入同一条轨迹**——设计文本、图片、视频、扫描件和地图节点的统一表示。
3. **外部检索 harness 与厂商原生搜索怎么比**——固定 Agent 协议、工具权限、预算和停止条件。
4. **证据链在哪些地方断掉**——分析翻译、时间对齐、实体消歧、引用回链和来源冲突。
5. **如何做一个小型持久浏览评测**——构造跨语言问题集，记录证据覆盖、引用精度、工具次数和恢复率。
6. **浏览 Agent 的适用边界**——明确公开可验证资料、动态页面、登录墙和高风险事实核验的差别。

### 写作所需证据

- **已经有**：预印本对 423 个问题、13 种语言、异构证据来源、无网络过滤、统一 Agent 协议和人工评测设计的摘要说明。
- **需要补做**：通读问题构造、语言分布、过滤阈值、证据标注和评分方法；做 20 个公开资料的跨语言小测试，记录每个证据节点和来源回链。
- **适合配图**：问题→线索发现→跨语言转译→多模态读取→证据图合并→引用结论的流程图；证据链断点与恢复策略的状态图。
- **关键未验证点**：423 题的许可和泄漏风险、13 种语言的难度是否可比、模型原生搜索的工具差异、视频/扫描件读取误差和人工评测的一致性。

## 5. 终端 Agent 该把功劳算给哪条命令？用依赖图做信用分配

### 热点是什么

预印本 **Credit Where It Matters: Dependency-Aware Policy Optimization for Terminal Agents** 于 **2026-10-02** 提交 arXiv。作者关注编码、调试等多步终端任务：后续命令往往依赖早先命令产生的文件、输出或状态，但已有 trajectory-level 和 step-level 信用分配没有显式追踪这些读写依赖，可能把训练信号给到与最终结果无关的操作。

论文提出 DepGPO：从终端执行轨迹构造 command dependency graph，再从任务验证器最终检查的资源反向追踪，把信用分配给相关写入及其支撑读取，并据此重新分配各步骤的 trajectory advantage。作者报告在复杂终端任务上，DepGPO 的对比实验和消融实验都改善了任务表现与训练稳定性；摘要没有给出统一的收益百分比，具体任务、模型和训练预算需要阅读全文核对。

原始资料：

- [Credit Where It Matters: Dependency-Aware Policy Optimization for Terminal Agents（arXiv，提交于 2026-10-02）](https://arxiv.org/abs/2610.03634)

### 为什么值得写

**事实**：DepGPO 把终端轨迹转换成读写依赖图，再从 verifier 访问的最终资源向后追踪相关步骤。**我的判断**：终端 Agent 的训练难点不只是“哪一步出错”，而是“哪一步为最终状态提供了必要因果支持”；命令很多、状态隐式、失败可重试时，按时间平均分配奖励会把偶然动作当成技能。文章可以从一个修改配置并运行测试的任务开始，对照按时间分配、按最后命令分配和按依赖图分配三种策略，展示日志结构怎样影响训练信号。

### 建议标题

**终端 Agent 该把功劳算给哪条命令？用依赖图做信用分配**

### 文章梗概

终端 Agent 修好一个测试时，真正有用的可能是第 3 条写配置命令和第 7 条读取日志的命令，中间还有几次无效重试。DepGPO 预印本不按时间顺序平均分配训练信用，而是从 verifier 最终检查的资源反向追踪命令之间的读写依赖，把优势重新分配给必要写入和支撑读取。文章做一个最小代码修复任务，记录文件、进程和命令依赖，对照时间级、末步级与图级信用分配，分析隐式状态、重试和副作用如何改变训练信号。论文只在摘要中说明表现和稳定性改善，具体收益与训练成本需要阅读全文和复跑。

### 结构提纲

1. **终端轨迹为什么不等于因果链**——用无效重试、覆盖写入和读取旧日志构造反例。
2. **命令依赖图需要记录什么**——定义文件读写、进程输出、环境变量和 verifier 资源。
3. **从最终状态反向分配信用**——解释相关写入、支撑读取和 advantage 重分配。
4. **三种信用策略如何做公平对照**——固定模型、任务、预算和 verifier，比较学习速度、成功率和稳定性。
5. **依赖图的工程代价**——讨论日志完整性、动态路径、并发命令、不可观测外部状态和图构建误差。
6. **什么时候图级信用会误导**——区分真正必要的步骤、可替代步骤和只在训练集成立的偶然依赖。

### 写作所需证据

- **已经有**：预印本对终端任务、command dependency graph、verifier 反向追踪、相关读写信用和 DepGPO 的摘要定义。
- **需要补做**：阅读全文核对依赖图构建、奖励公式、训练步数、模型与任务集；实现一个假的终端环境，比较三种信用分配策略。
- **适合配图**：命令→文件/进程→测试 verifier 的依赖图；从最终失败资源反向标记命令并重分配优势的示意图。
- **关键未验证点**：复杂终端任务的具体规模、依赖图对动态脚本和网络调用的覆盖、训练稳定性的统计方式、额外日志成本，以及错误依赖图对策略学习的影响。
