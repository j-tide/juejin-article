## 今日判断

今天最值得先写的是 OpenAI 的 Decisions API。它不是又一个“模型更强”的发布，而是把一类原本由提示词和 JSON 解析承担的判断，单独做成了带概率、置信度和阈值的 API。这个切口可以直接落到工单分流、图片质检和人工复核队列，读者也能清楚看到它和 Structured Outputs、函数调用的边界。Mistral Large 4 的公开预览更热，但大量结果仍是厂商或第三方评测方的报告，权重要到月底才公开，适合做第二篇深挖。

## 1. Mistral Large 4 的开源承诺，到了能跑 Agent 的哪一层？

### 热点是什么

Mistral 于 2026 年 10 月 6 日发布 Mistral Large 4 公共预览。官方披露它是 1.05T 总参数、49B 激活参数的原生多模态 MoE，支持文本、图片、工具调用和 Agent 工作流；预览 API 已在 Mistral Studio 开放，模型权重计划在 10 月底发布。官方还描述了 160 多种语言、3,800 张 Grace Blackwell GPU 训练、可组合的 RL 环境，以及在 DeepSWE、Terminal-Bench 4、AutomationBench、视觉 grounding 等任务上的结果。这些数字和比较主要来自 Mistral 自己、Artificial Analysis、vals.ai 或 Surge AI 的评测，不能当成独立复测结论。

原始资料：

- [Mistral Large 4 官方发布说明（2026-10-06）](https://mistral.ai/news/mistral-large-4/)
- [Mistral Large 4 官方模型文档（2026-10-06）](https://docs.mistral.ai/fr/models/mistral-large-4-0)

### 为什么值得写

它的看点不是参数规模本身，而是把“开放权重模型”直接放在 Agent 的运行时问题里讨论：模型能否稳定调用工具、视觉输入如何进入工作流、RL 环境如何把代码沙箱、搜索和外部 API 组合在一起，以及权重公开后企业是否真的能自行部署。对做代码 Agent、知识工作 Agent 和安全分析 Agent 的团队来说，这比单看聊天榜单更接近选型决策。判断上，Mistral 把训练环境和服务基础设施一起公开描述，是值得拆的工程信号；但在权重、架构和 post-training 细节发布前，不能把预览阶段的指标外推到自部署环境。

### 建议标题

**Mistral Large 4 的开源承诺，到了能跑 Agent 的哪一层？**

### 文章梗概

某个企业 Agent 负责人拿到 Mistral Large 4 的预览接口，发现它在代码、文档图片和多步工具任务上都很强，但真正决定能不能上线的不是榜单分数：权重何时可用，工具调用是否稳定，长轨迹的上下文和验证怎么处理，安全策略能不能按自己的规则部署。文章先拆官方公布的 MoE、多模态和 RL 训练环境，再把“模型能力”和“服务运行时”分开，用同一套工具任务比较预览 API、闭源模型和未来自部署版本，最后列出在权重落地前不能下的结论。

### 结构提纲

1. **先把发布内容分成三层**：模型规格、预览服务和月底才会公开的权重分别能证明什么。
2. **Agent 任务到底调用了哪些能力**：从多模态输入、函数调用、上下文窗口到工具结果回填，画出一轮完整执行链。
3. **RL 环境为什么比“训练了多少 token”更重要**：分析代码沙箱、搜索、API、单元测试和 LLM judge 如何组成可组合任务。
4. **安全与主权的取舍**：对比官方托管、欧洲区域部署和自部署在拒答、审计、数据驻留上的边界。
5. **怎样做一次公平复测**：固定模型、工具、任务、预算和评分标准，避免把服务差异误算成模型能力。

### 写作所需证据

- **已有资料**：官方发布说明和模型文档；文中公开的 DeepSWE、Terminal-Bench 4、AutomationBench、Dense 200、B3 等指标；官方对训练与 RL rollout 的描述。
- **需要补做的源码阅读或实验**：阅读预览 API 的工具调用和视觉输入协议；若能获得接口，固定 20—30 个代码、文档图片和多步工具任务，与已用模型做相同预算的对照；权重发布后再做一次 API 与本地推理复测。
- **适合的图**：`用户请求 → 多模态编码 → 模型规划 → 工具/沙箱 → 验证器 → 下一轮上下文`，旁边标出训练时 RL 环境和线上运行时的分界。
- **关键未验证点**：权重发布日期和许可证、完整架构与上下文限制、预览 API 与自部署的工具调用差异、官方安全指标能否被独立重现。

## 2. Agent 先别生成答案：Decisions API 为什么把模型变成分类器？

### 热点是什么

OpenAI 在 2026 年 10 月 6 日的 API changelog 中发布 Decisions API 公共 Beta。官方文档把它定义为一个专门处理文本或图片判断的接口，当前只支持 `gpt-6-luna`，通过 `POST /v1/decisions` 接收共享输入和多个问题，返回 `predicate`、`choice` 或 `score` 类型的答案。结果包含概率分布或置信度，官方称响应速度约为 Responses API 的 10 倍；当前只计输入 token，价格为每百万 token 0.10 美元。10 倍速度是官方口径，尚未有独立基准。

原始资料：

- [OpenAI API changelog（2026-10-06）](https://developers.openai.com/api/docs/changelog)
- [Decisions API 官方指南](https://developers.openai.com/api/docs/guides/decisions)

### 为什么值得写

很多 Agent 系统并不需要一段长答案，而是要先判断“这个工单是不是支付问题”“图片里有没有破损”“请求属于哪个队列”。过去常用一个大模型生成 JSON，再由代码解析；现在 API 把问题类型、允许选项、概率和阈值放到接口层，能让路由、人工复核和成本控制更可见。它适合客服工单、图片质检、文档分级等高频入口，但不能替代需要解释、抽取自定义对象或请求工具的 Responses API。文章可以用一个真实的工单分流例子，把三种 API 的边界讲清楚。

### 建议标题

**Agent 先别生成答案：Decisions API 为什么把模型变成分类器？**

### 文章梗概

下午客服群里同时进来一张破损商品照片、一条“重复扣款”的文字消息和一份合同截图，值班同学真正要的不是三段漂亮的回复，而是可用于分流、排序和人工复核的稳定判断。Decisions API 把输入、问题类型和允许的选项拆成独立字段，返回概率、置信度或有序分数。文章会用同一批工单分别走 Decisions、Structured Outputs 和函数调用，解释它们在输出约束、阈值、成本和后续动作上的差异，并指出概率不是校准后的事实，阈值仍要由业务错误代价决定。

### 结构提纲

1. **从一个工单入口开始**：为什么“先判断再生成”能减少不必要的长回答和工具调用。
2. **读懂 `predicate`、`choice`、`score`**：三种结果的数学含义、适用条件和容易混淆的地方。
3. **和 Structured Outputs、函数调用分界**：一个负责判断，一个负责生成结构化对象，一个负责请求动作。
4. **概率怎样进入业务决策**：用误报、漏报和人工复核成本推导阈值，而不是直接把 `confidence` 当真值。
5. **延迟和成本如何实测**：固定输入、问题数、图片大小和网络条件，比较端到端耗时与输入 token。

### 写作所需证据

- **已有资料**：官方 changelog、完整请求字段和三类答案示例、输入计费和 ZDR/HIPAA 说明。
- **需要补做的源码阅读或实验**：阅读 API reference 和 SDK 是否已经支持 `/v1/decisions`；构造 100 条人工标注工单，比较 Decisions 与 Responses+JSON 的准确率、P50/P95 延迟、输入 token 和人工复核量；对阈值做校准曲线。
- **适合的图**：`原始工单/图片 → Decisions API → 概率与选项 → 路由/复核/生成回复`，旁边放 Responses API 和函数调用的分叉对比。
- **关键未验证点**：Beta 的限流和 SDK 支持、概率是否可跨任务比较、并发问题数对延迟的影响、官方“10 倍”是否包含网络和排队。

## 3. Agent Harness 和推理引擎终于要互相听懂：HEAR 协议在解决哪一层的浪费？

### 热点是什么

论文《Can Agent Harnesses and Inference Engines Hear Each Other? The HEAR Protocol for Agentic LLM Serving》于 2026 年 10 月 5 日提交 arXiv。它提出一个双向 Harness—Engine Pairing 协议：Harness 发送 Agent 角色、依赖、上下文生命周期、未来复用意图和执行要求；推理引擎返回 KV cache 驻留、队列、资源压力、能力和实际执行结果。协议把语义和优化策略分开，论文在 SCBench、Mooncake、BrowseComp-Plus 和 DeepResearchBench 上报告了 1.61 倍批处理加速、2.23 倍中位 TTFT 改善以及 1.23—2.45 倍端到端加速。结果来自作者设定的硬件、模型和工作流实验。

原始资料：

- [HEAR Protocol 论文摘要](https://arxiv.org/abs/2610.06597)
- [HEAR Protocol HTML 全文](https://arxiv.org/html/2610.06597v1)

### 为什么值得写

现在的 Agent Harness 知道哪个子任务已经准备好，却通常不知道某个前缀还在 GPU KV cache 里；推理引擎知道队列和显存压力，却不知道哪个 Agent 正在等一条关键工具结果。两边各自优化，常常会出现缓存命中率和尾延迟互相打架。HEAR 的价值在于先定义“意图、控制、观察、保证、接受、完成”的接口语义，再让调度策略自行演化。这个切口适合解释 Agent 性能问题为什么不只在模型或 vLLM 参数，而在工作流层和服务层之间缺一条可验证的反馈链。

### 建议标题

**Agent Harness 和推理引擎终于要互相听懂：HEAR 协议在解决哪一层的浪费？**

### 文章梗概

一个多 Agent 研究任务在高并发下越跑越慢：Harness 反复创建相似上下文，推理引擎却把刚用过的 KV cache 淘汰；调度器知道谁在等待，却不知道哪条前缀值得保留。HEAR 论文把两层之间的通信拆成四类消息，并明确区分意图和控制、偏好和要求、观察和保证、接受和完成。文章会画出一次请求从工作流就绪到缓存准备再到执行结果回传的时序，复算论文的调度对照，最后讨论协议能否落进现有 LangGraph、vLLM 或自研 serving，以及哪些策略仍然需要业务自己承担。

### 结构提纲

1. **先定位性能断点**：同一个 Agent 任务里，工作流排队、模型排队、KV cache 和工具等待分别消耗什么时间。
2. **HEAR 的四类消息**：解释 Harness 和 Engine 各自应该知道什么，以及为什么不能把状态报告当成命令。
3. **Cache-Aware + Guard 的执行链**：逐步拆解优先级、缓存准备、等待保护和实际完成回执。
4. **论文实验能证明什么**：核对模型、硬件、负载、任务质量和失败重试，区分可迁移结论与特定配置结果。
5. **接入边界**：哪些现有调度器可以通过适配器接入，哪些需要改变 serving 引擎或工作流协议。

### 写作所需证据

- **已有资料**：arXiv 摘要、HTML 全文、协议消息表、SCBench/Mooncake 的公开对照表和实验设置。
- **需要补做的源码阅读或实验**：查看论文是否提供实现仓库；在一个简化的 LangGraph + vLLM mock 中模拟缓存驻留和队列反馈，比较 FCFS、只看缓存和带等待保护三种策略；若可获得代码，再按论文负载复跑。
- **适合的图**：左右两列画 Harness 与 Inference Engine，中间是 HEAR 双向消息；下方配一条包含“就绪→缓存状态→调度→接受→完成”的时序图。
- **关键未验证点**：论文代码和协议实现是否公开、不同推理引擎的字段映射、缓存估计错误时的退化、策略在工具等待占主导的任务上是否仍有收益。

## 4. Agent 最危险的不是答错，而是读多了：AgentPrivArena 怎样审计完整轨迹？

### 热点是什么

论文《AgentPrivArena: Evaluating and Auditing Real-world AI Agent Privacy》于 2026 年 10 月 5 日提交 arXiv。它把真实开源服务放进可复现的 Docker 网络，用 MCP 服务器暴露 BookStack、Mattermost、Rocket.Chat、Mailpit、GoToSocial 和 Radicale 等工具，要求 Agent 在多步任务中搜索、读取、写入并提交最终动作。论文提出轨迹级隐私指标，关注不必要的信息访问、抽取和处置，并给出运行时 AgentPrivAudit。作者强调，仅看最终答案泄露会漏掉“读过但没说出来”的越权访问。

原始资料：

- [AgentPrivArena 论文摘要](https://arxiv.org/abs/2610.06454)
- [AgentPrivArena HTML 全文与实验细节](https://arxiv.org/html/2610.06454v1)
- [项目主页](https://shouju-wang.github.io/agentprivarena/)

### 为什么值得写

企业 Agent 一旦接上邮箱、群聊、知识库和日历，权限问题就不再是“最后有没有把秘密写进回复”。它可能为了确认一个订单，先把无关邮件、隐藏频道和历史附件读进上下文；最终回答看起来正常，轨迹却已经违反最小必要原则。AgentPrivArena 给出了一个工程上可落地的审计思路：把服务状态真实地放进容器，让 MCP 调用产生可记录的观察，再在每一步判断信息流是否合理。论文使用的是种子数据和开源服务，不能直接当成生产隐私风险比例，但它能帮助团队把审计点从结果扩展到执行过程。

### 建议标题

**Agent 最危险的不是答错，而是读多了：AgentPrivArena 怎样审计完整轨迹？**

### 文章梗概

客服 Agent 只需要查一笔订单，却顺手读取了同事私聊、内部知识库和旧邮件；最后回复没有泄露任何敏感字段，审计系统于是判定“没有问题”。AgentPrivArena 把这个盲点变成可执行实验：服务真的跑在容器里，MCP 工具真的被调用，敏感记录只有在 Agent 主动读取后才进入上下文，再按轨迹统计暴露、抽取和处置。文章会拆开环境、工具层、沙箱和审计器的接口，设计一个奶茶 SaaS 工单场景的最小复现，并说明为什么“任务完成率高”与“权限使用合理”必须分别验收。

### 结构提纲

1. **从结果隐私转向轨迹隐私**：一个没有泄露字段的最终答案，为什么仍可能已经越权。
2. **把服务变成实验环境**：Docker 中的真实应用、种子数据、MCP discovery/access/write 三类工具如何组成任务。
3. **三类轨迹级指标**：暴露了哪些数据、抽取了多少、最后如何处置，以及指标如何受策略定义影响。
4. **AgentPrivAudit 放在执行链哪里**：审计器读取什么事件，怎样做在线拦截、告警或脱敏，如何避免阻塞所有正常调用。
5. **从论文到生产的边界**：合成数据、OpenHands harness、服务版本和任务分布会怎样改变风险结论。

### 写作所需证据

- **已有资料**：论文的系统架构图、六个自托管服务、MCP 工具分类、Docker 重置流程和轨迹级指标定义。
- **需要补做的源码阅读或实验**：检查项目主页是否提供容器和任务配置；搭建一个只含工单、知识库和群聊的最小服务集，记录 Agent 每次 read/write 的数据标签；比较只做最终答案审计与轨迹审计的漏报差异。
- **适合的图**：`服务容器 → MCP 工具层 → Agent sandbox → 轨迹事件流 → AgentPrivAudit → 放行/脱敏/告警`，用颜色区分任务相关数据和受保护数据。
- **关键未验证点**：项目代码和镜像是否可直接运行、审计器对跨工具数据拼接的覆盖、指标阈值是否需要业务策略、真实企业权限模型与论文种子服务的差距。

## 5. 工具已经连续返回无效结果，Agent 为什么还不停止？

### 热点是什么

论文《Judged Useless, Queried Anyway》于 2026 年 10 月 5 日提交 arXiv，并公开了 [代码和数据仓库](https://github.com/bennidict23/judged-useless-queried-anyway)。研究在可控的检索源故障环境中，把 Agent 对结果的判断和它是否停止分开测量：七个 Agent 对失败源的结果有 97%—100% 的概率判断为无用，但多数并不会据此停止。只有 Harness 强制加入“连续五次判断无用后只保留回答动作”的集成步骤，停止才真正跟随证据；作者在 300 个新问题上做了预注册复现。

原始资料：

- [论文摘要](https://arxiv.org/abs/2610.06191)
- [论文代码与数据仓库](https://github.com/bennidict23/judged-useless-queried-anyway)

### 为什么值得写

这项研究击中了 Agent 里很常见的假象：日志里有“这个结果没用”，但下一步仍然继续调用同一个工具。加预算、提醒成本、允许凭记忆回答，可能只会改变停止的时间，不会让停止真正依赖证据。对搜索、RAG、工单定位和代码 Agent 来说，这会直接放大延迟和费用，还可能让错误来源不断污染上下文。论文把问题拆成判断通道和行动通道，并提供 CPU 可运行的复现脚本，适合做一次小而扎实的本地实验，同时讨论“连续 N 次失败”这种硬规则在真实系统里会不会误杀短暂故障恢复。

### 建议标题

**工具已经连续返回无效结果，Agent 为什么还不停止？**

### 文章梗概

值班工程师盯着日志：Agent 已经连续四次写下“这条结果和问题无关”，下一步却又查询了同一个知识库。论文的关键发现不是模型不会判断，而是判断没有进入行动选择。文章先用公开仓库复现失败源、时间匹配对照和停止差异 Δ，再解释提示词、预算和“每次调用有成本”为什么只能部分改变行为，最后把连续无效结果后的动作收敛交给 Harness，并讨论超时、备用工具和短暂故障恢复时应该怎样改成状态机。

### 结构提纲

1. **把“看懂结果”和“决定停止”拆开**：为什么成功率相同的两个 Agent，可靠性可能完全不同。
2. **复现失败源实验**：介绍 HotpotQA、三种动作、八步预算和可控故障注入，说明时间匹配对照 Δ 怎么算。
3. **提示词为什么不够**：比较允许凭记忆、写出成本、设置步数和显式停止规则，区分停止时机与停止依据。
4. **Harness 集成步骤**：把连续无用判断写入状态机，只留下回答或切换备用工具的动作，并处理恢复窗口。
5. **工程取舍**：如何选择 N、怎样避免把暂时性服务故障误判为永久无效，以及哪些任务不适合硬性停止。

### 写作所需证据

- **已有资料**：论文摘要、公开仓库、复现实验脚本、300+300 条 episode 数据、失败源环境说明和停止差异定义。
- **需要补做的源码阅读或实验**：先在 CPU 上运行仓库的 `reproduce_paper.py`，核对论文图表；再把集成步骤接到一个本地 RAG demo，比较 N=3/5/8、备用检索源和恢复窗口的成功率、调用次数和延迟。
- **适合的图**：`工具结果 → 有用/无用判断 → 计数器 → 继续查询/切备用源/强制回答` 的状态机，并标出模型判断通道与 Harness 控制通道。
- **关键未验证点**：公开 episode 与当前依赖能否直接运行、不同模型的失败模式是否一致、连续失败阈值是否随工具类型变化、硬规则对需要多次探索的任务是否有副作用。
