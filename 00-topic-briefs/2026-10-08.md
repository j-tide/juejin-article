## 1. Agent 会不会先把能力装进一个便宜的“瓶子”？拆 BOTTLED 的成本摊销实验

### 热点是什么

论文《Agent in a Bottle》于 2026-10-06 提交，提出 **bottling**：让 Agent 看到一整批没有标签的重复任务，在固定时间、算力和模型 API 预算内，自己选择训练小模型、写程序、做检索或组合路由，把一次次昂贵调用换成可复用的产物。作者在 10 个模型、3 个任务上测试，报告 48/60 次 bottling 低于对应 zero-shot 的 95% 置信区间，31/60 次还不如同预算的朴素蒸馏基线；在 ESCI 上，Opus 5 保留约 82% 的 zero-shot macro-F1，报告成本约低 657 倍。以上数字来自论文实验，尚未由我们独立复现。

原始资料：

- [论文摘要](https://arxiv.org/abs/2610.08775)
- [论文 HTML（含公式、实验设置和附录）](https://arxiv.org/html/2610.08775v1)
- [作者发布的 bottled 代码](https://github.com/aktsonthalia/bottled)

### 为什么值得写

很多 Agent 项目只算“每次请求用了多少 Token”，却没有问过同一类任务会不会重复出现几百万次。BOTTLED 把问题改成一次投资和后续执行的总账：构建产物的成本，加上对整批数据的运行成本，再和逐条调用、固定蒸馏基线比较。它还给了一个反直觉结果：零样本答题强，不等于能把能力封装成便宜产物。这个角度适合写给做客服工单分类、商品属性抽取、内容审核和批量数据处理的工程师，能把“自我优化”落到一个可计算的决策。

### 建议标题

**Agent 不该每次都重新思考：BOTTLED 如何把一次能力变成百万次低成本执行**

### 文章梗概

某个奶茶 SaaS 每天要给几百万条商品和工单打标签，如果每条都调用大模型，账单会随数据量线性增长。文章从 BOTTLED 的定义开始，解释 Agent 怎样在没有标签时抽样、写规则、训练小模型或把难例回流大模型，再用“构建成本 + 执行成本 + 质量”重算是否值得投资。接着拆论文的预算、zero-shot 与蒸馏对照，说明强模型也可能做不好 bottling。最后用小规模实验给出何时做产物、何时直接调用、何时保留大模型兜底的判断，并说明数据漂移、污染和价格会怎样改变结论。
### 结构提纲

1. **先算总账：逐条调用为什么会把重复任务变成线性成本**——用公式区分构建成本、执行成本和质量损失，说明“省 Token”不是唯一目标。
2. **BOTTLED 的执行链**——从读取整批无标签输入，到选择程序、小模型、检索或混合路由，再到写出最终预测文件，逐步对应 harness 提供的工具。
3. **论文结果到底说明了什么**——对照 zero-shot、蒸馏和 Jev，解释 48/60 低于置信区间与 31/60 输给朴素基线的含义，避免把作者实验写成普遍成功率。
4. **做一个小型复现**——选小规模商品属性或工单分类数据，固定 Token/时间预算，分别跑直接调用、蒸馏和 Agent 产物，记录质量、构建时间和单条成本。
5. **落到生产决策**——根据批量规模、标签漂移、难例比例和回滚要求，决定规则、小模型、混合路由和大模型兜底的边界。

### 写作所需证据

- 已有：论文的形式化定义、三个任务（MAVE、ESCI、RAID）、成本权重、OpenCode harness、A100/8 CPU/64GB/10 小时/500 万 Token 设置，以及公开代码仓库。
- 需要补做：阅读仓库的运行入口和产物格式；在小数据上复现一次直接调用、固定蒸馏和 Agent 产物；记录构建 Token、预测覆盖率、质量和回滚方式。
- 适合配图：`逐条调用 → 构建可复用产物 → 批量执行` 的成本对照图；Agent 在“规则 / 小模型 / 难例回流”之间选择的流程图。
- 未验证点：论文报告的模型和价格是特定实验环境下的结果；大规模数据的标签分布、污染审计和 API 价格变化，能否迁移到工单场景需要另测。

## 2. 代码 Agent 太谨慎也会坏：ParanoiaEval 怎样测“防御动作是否有必要”

### 热点是什么

论文《ParanoiaEval》于 2026-10-06 提交，发布了 [代码和数据](https://github.com/ZhuoningXu/ParanoiaEval_release)。基准包含来自 50 个仓库的 200 对证据控制任务，每对只改变一条决定风险处理方式的证据；四类处理是 Avoidance、Transfer、Mitigation、Acceptance。作者用风险处理违规率（VR）和证据响应率（ER）评估 8 组 Agent 配置，并做了人类校准的 Agentic Judge。论文报告在证据已经明确时，仍有 11.2%—58.7% 的运行执行了不必要的防御动作，违规会让开发者满意度下降 1.27/5 分。

原始资料：

- [论文摘要](https://arxiv.org/abs/2610.08662)
- [论文 HTML（任务构造、Judge 和统计细节）](https://arxiv.org/html/2610.08662v1)
- [ParanoiaEval 代码与数据](https://github.com/ZhuoningXu/ParanoiaEval_release)

### 为什么值得写

工程团队通常只给 Agent 两个指标：任务是否完成、测试是否通过。但 Agent 也可能因为过度防御而扩大改动范围、重复备份、无休止地验证，甚至把已经明确的用户决定重新拦回去。ParanoiaEval 的价值在于把“谨慎”拆成可观察的风险处理动作，并用成对任务隔离因果变量。它适合连接代码 Agent 的真实痛点：安全策略不能只有拒绝率，还要知道什么时候该停止加戏、什么时候必须升级给人。

### 建议标题

**代码 Agent 不是越谨慎越好：用 ParanoiaEval 测出它什么时候在“安全地添乱”**

### 文章梗概

下午的修复任务写着“只改展示层，数据库无需迁移”，Agent 却加备份、跑全量检查，还要求人工重新确认。文章从这个场景进入 ParanoiaEval，把 Avoidance、Transfer、Mitigation、Acceptance 翻译成代码动作，再解释 E+/E− 成对任务如何隔离一条证据变量。随后拆 Judge 怎样区分必要动作和多余动作，核对 11.2%—58.7% 的论文结果。最后给出工程落地方案：把证据、允许范围、风险处理和停止条件写进任务卡，分别评估完成率、违规率和证据响应率，而不是只换更强模型。
### 结构提纲

1. **“谨慎”到底是什么动作**——用四种风险处理方式区分拒绝、转交、缓解和接受，避免把所有额外工作都叫安全。
2. **成对任务怎样隔离证据变量**——解释 200 对任务、50 个仓库、E+/E− 变体和可执行性/证据有效性检查。
3. **Judge 如何看一条 Agent 轨迹**——跟踪任务要求、额外命令、验证范围和用户决定，说明 VR、ER 与人类校准的关系。
4. **结果为什么和模型能力分离**——对比不同模型/配置的任务成功率与违规率，讨论“答得对”与“处理得对”是两件事。
5. **把测评变成运行时策略**——设计证据卡、风险预算、停止条件和人工升级点，并列出误报、漏报与体验成本。

### 写作所需证据

- 已有：论文全文、公开任务构造规则、四类风险处理、200 对/400 变体、Judge 验证准确率 0.965、8 组 Agent 配置和资源统计。
- 需要补做：查看仓库 README 与任务格式；抽取一对 E+/E− 任务，运行一个本地或兼容 API 的 Agent，手工标注多余动作，再和 Judge 输出对照。
- 适合配图：同一任务在 E+ / E− 下的证据分叉图；`任务卡 → Agent 轨迹 → Judge → VR/ER/人工升级` 的评测流程图。
- 未验证点：论文的 Judge 和模型版本会影响结果；11.2%—58.7% 不能直接当成所有代码 Agent 的普遍比例，真实仓库中的风险类别和外部有效性仍需验证。

## 3. 一份对话，几台设备：nanoMuse 如何把个人 Agent 的权限做成 Sentinel

### 热点是什么

论文《nanoMuse》于 2026-10-06 提交，项目页面记录其首个版本在 2026-09-25 发布，代码采用 GPL-3.0。它把 Android、桌面、Web 和可选 relay 组成一个跨设备 Agent：每台设备保留完整 Agent 和自己的 Sentinel，记忆用用户可读文件保存，模型由用户选择。论文描述的 Sentinel 采用固定顺序判断：拒绝工具、用户规则、允许/询问列表、私密数据 taint、工具风险与模式、最后的危险命令警告；审批是有范围的 grant，并写入可查看日志。论文也明确列出目前没有独立模型、权限边界仍在同一进程族、relay 会保留文本等限制。

原始资料：

- [论文摘要](https://arxiv.org/abs/2610.08699)
- [nanoMuse 源码](https://github.com/nano-muse/nanoMuse)
- [自部署说明](https://github.com/nano-muse/nanoMuse/blob/main/docs/self-hosting.md)
- [隐私说明](https://github.com/nano-muse/nanoMuse/blob/main/docs/privacy.md)

### 为什么值得写

个人 Agent 的难点不是再接一个模型，而是同一段对话怎样安全地触碰手机、电脑、文件和账号。nanoMuse 把“一个 Agent、多只手”拆成设备拓扑、工具阶梯、审批范围、taint 传播和可读记忆，提供了可以直接读代码的开源样本。它也很适合写边界：论文是项目报告和路线图，不代表每个安全承诺已经经过独立审计，relay、同进程策略和移动端限制都需要读源码和实测。

### 建议标题

**把 Agent 放进手机和电脑之后，谁来拦住它？拆 nanoMuse 的 Sentinel 与跨设备记忆**

### 文章梗概

如果同事只说“把昨天的会议纪要发给客户”，个人 Agent 可能要读文件、找联系人、打开邮件并发送。文章以此拆 nanoMuse：每台设备运行完整 Agent，relay 负责连接，工具调用先过 Sentinel，再按 skill、命令、MCP、浏览器和屏幕逐级降级。重点解释 taint 如何在读到私密数据后提高外发审批级别，以及“只允许这次/这次对话/这个收件人”的 grant 为什么更可撤销。随后对照源码和隐私文档，核实记忆文件、日志、relay 留存和 iOS 限制，并写出跨设备权限测试清单，标出仍是设计主张的部分。
### 结构提纲

1. **从一个发送动作开始画拓扑**——说明设备内 Agent、relay、模型提供商和目标应用各自持有什么数据。
2. **Sentinel 的固定决策顺序**——逐项跟踪拒绝列表、规则、审批、taint、风险模式和危险命令警告，找出顺序对权限的影响。
3. **工具阶梯与屏幕操作**——比较 skill/CLI/MCP/浏览器/屏幕五层手段，解释为什么“越靠近屏幕越难验证”。
4. **记忆和 relay 的数据边界**——阅读文件格式、来源记录、同步协议与隐私文档，区分可读性、可撤回性和实际留存。
5. **做一次跨设备复现与攻击清单**——运行自部署版本，测试私密数据 taint、一次性审批、撤销和离线设备，记录与论文描述的差异。

### 写作所需证据

- 已有：论文的架构图、Sentinel 决策顺序、工具阶梯、设备支持范围、GPL-3.0 仓库及自部署/隐私文档。
- 需要补做：锁定仓库版本，运行桌面或 Web 最小路径；跟踪一次读私密文件后外发的审批日志；确认 relay 是否保存正文、设备离线时会话如何恢复。
- 适合配图：`设备 Agent → Sentinel → 工具阶梯 → relay/模型/外部应用` 架构图；taint 从读取到外发的状态流转图。
- 未验证点：论文版本和仓库主分支会继续变化；同进程策略是否能抵抗恶意插件、移动端限制和 relay 留存，需要源码审计与实际测试，不能只依据项目自述。

## 4. 从文本到界面：GPT-6 Intelligent UI 到底新增了哪一层

### 热点是什么

OpenAI 于 2026-10-07 发布《GPT-6 and Intelligent UI for everyone》，ChatGPT 可以根据问题组合文字、图形、按钮、表单、图表和交互体验。官方描述的实现包括一套原生、可流式输出的组件库，以及在模型生成过程中编译界面的 compiler；模型会学习决定布局、内容、视觉和交互，回答也可以边思考/使用工具边逐步出现。发布说明还明确了 ChatGPT 各套餐的滚动范围，以及 Work/Codex 模型不随本次 ChatGPT 更新变化。页面里的延迟和内部评测均为 OpenAI 自报。

原始资料：

- [OpenAI 产品公告](https://openai.com/index/gpt-6-for-everyone/)
- [ChatGPT 发布说明（2026-10-07）](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)
- [GPT-6 Deployment Safety Hub](https://deploymentsafety.openai.com/gpt-6-october/model-data-and-training)

### 为什么值得写

这次更新最值得拆的不是“模型更强”，而是回答的运行时边界变了：模型不只吐文本，还要选择组件、生成状态、处理用户输入并逐步渲染。对做 AI 产品的工程师来说，难点会从提示词扩展到组件白名单、流式协议、状态恢复、错误降级、无障碍和权限控制。官方公告给出了组件库与 compiler 的方向，但没有公开协议和 API 细节，正好可以把已知事实、合理推导和待验证实验分开写。

### 建议标题

**当模型开始写界面：GPT-6 Intelligent UI 把 Agent 产品的边界推到了哪里**

### 文章梗概

用户问“帮我安排一顿聚餐”，得到的不再只是文字，而是能改人数、复制清单、继续计算的界面。文章先把 OpenAI 公告中的组件库、compiler、流式生成和模型决策拆成响应流水线，再讨论这和“模型返回 JSON、前端自己渲染”有何不同。接着做一个本地最小实现：模型生成受限组件树，编译器增量校验并渲染，非法组件或中断回退到文本。文章还会检查安全卡的工具与限制边界，最后给出 schema、权限、回放、无障碍和跨端一致性的取舍。官方内部延迟数字只作为公告事实。
### 结构提纲

1. **回答为什么需要运行时**——从文本、结构化 JSON 到可交互组件，列出状态和事件多出来的部分。
2. **官方描述的组件库 + compiler 链路**——按“模型选择 → 增量编译 → 渲染 → 用户事件回传”画出可验证的架构。
3. **流式 UI 的失败模式**——处理中断、半棵组件树、非法属性、工具超时和移动端降级如何影响状态一致性。
4. **安全与产品边界**——把组件白名单、工具权限、数据来源和用户确认放进同一条执行链，避免让 UI 生成绕过原有控制。
5. **做一个可回放的最小实现**——用固定 schema 和模拟模型记录增量 patch，测试回滚、重放、无障碍文本和纯文本 fallback。

### 写作所需证据

- 已有：OpenAI 官方公告、发布说明、组件库/compiler/训练目标的公开描述，以及 GPT-6 安全中心的评测边界。
- 需要补做：确认开发者 API 是否公开 Intelligent UI 的组件协议；在本地用 JSON Schema/增量 patch 做一个等价的受限演示，测断流、非法组件、权限拒绝和重放。
- 适合配图：文本回答与“组件树 + compiler + 事件回传”的对照架构图；一棵组件树从生成、校验、渲染到回滚的时序图。
- 未验证点：官方没有公布完整组件 schema、compiler 实现、端到端延迟数据和第三方可用性；产品公告中的内部评测不能直接外推到自建应用。

## 5. 聊天工具为什么要让 Agent 进群？Webex 的共享上下文、MCP 与 Dialog

### 热点是什么

Cisco 于 2026-10-07 的 WebexOne 公告和同日 Webex 官方博客，介绍面向企业协作的 AI-native Webex：Agent 可以被邀请到空间、会议和通话中，读取共享上下文并执行多步工作；官方示例是先在空间里 @mention 分析 Agent 拉取使用统计，再让演示文稿 Agent 更新 PowerPoint。公告还提到 Webex Suite 的 MCP 集成可把会议、通话、消息和对话上下文带入 OpenAI dots，Dialog 被称为 Webex AI Agent 平台的 agentic harness，用于把零散互动串成持续的客户关系。部分能力使用 “soon/future” 表述，当前更接近产品路线和架构宣言。

原始资料：

- [Cisco 新闻稿（2026-10-07）](https://newsroom.cisco.com/c/r/newsroom/en/us/a/y2026/m10/cisco-unveils-new-agentic-collaboration-experiences.html)
- [Webex 官方博客：AI-Native Collaboration](https://blog.webex.com/collaboration/webex-ai-native-collaboration-context-agents-trust/)

### 为什么值得写

企业工单往往横跨群聊、会议、通话和外部系统，单个聊天窗口里的 Bot 无法知道前后发生了什么。Webex 的切口适合写“共享上下文如何变成 Agent 的工作空间”：哪些事件进入上下文、谁有权读取、Agent 如何被 @mention 或自动触发、外部动作怎样审批并留下审计。它也提醒读者区分产品演示和可用接口：新闻稿给了场景和治理方向，尚未给出完整的 MCP schema、租户隔离和上线时间。

### 建议标题

**让 Agent 进群以后，谁负责记住上下文？拆 Webex 的协作 Agent 架构**

### 文章梗概

客户在群里发故障截图，值班同事在会议里讨论，第二天又有人要求把结论写进演示文稿；如果每步都靠人复制粘贴，Agent 只是另一个窗口。文章按 Webex 材料重建共享上下文链：消息、会议、通话和外部应用如何进入上下文，Agent 如何被邀请或由 harness 编排，MCP 怎样交付边界明确的资料。随后把上下文拆成事件账本、权限过滤、租户隔离、审批和审计五层，并用本地模拟器演示跨群聊与工单流程。对 Claude Managed Agents、dots 和 Dialog 的“即将支持”，只写公开承诺和待验证问题。
### 结构提纲

1. **为什么单个聊天 Bot 不够**——把一次客户问题在群、会、呼叫和外部系统间的流转画出来，找出上下文断点。
2. **共享上下文的最小数据模型**——定义事件、参与者、租户、来源和可见范围，说明摘要不能代替原始证据。
3. **Agent 的进入方式与 MCP 边界**——比较 @mention、会议内 Agent、外部 dots 和 Dialog harness，追踪一次跨应用动作的授权链。
4. **治理不是页面上的一个开关**——讨论身份、最小权限、审批、脱敏、租户隔离和审计日志如何共同约束共享上下文。
5. **用模拟器验证产品承诺**——构造群聊事件→上下文检索→Agent 调用→人工确认→更新文档的流程，标记与官方接口仍有差距的地方。
