## 1. Agent 能不能按约定工作一小时？AgentTime 把“时间感”变成可测能力

### 热点是什么

《AgentTime: Can Agents Estimate and Control Their Own Runtime?》于 2026-10-07 提交，2026-10-08 更新到 v2，并公开了 [网站](https://agenttimebench.com/) 和 [实验代码](https://github.com/michaelofengenden/agenttimebench)。基准包含来自 18 个来源的 222 个任务，分别测试按要求持续工作多久、事前预测耗时、事后回忆耗时。论文报告 GPT-6 Astra 在 Codex 中的典型时长偏差约 1.2 倍，Fable 5.1 在 Claude Code 中约 2.9 倍；在 1,991 次 duration-following 运行中，Astra 有 63% 落在请求时长的 5% 范围内。论文还发现，完成任务不等于会控制时间，部分运行只是提前睡眠等待。

原始资料：

- [论文（v2）](https://arxiv.org/abs/2610.09944)
- [AgentTime 网站、方法与结果](https://agenttimebench.com/)
- [实验代码（MIT）](https://github.com/michaelofengenden/agenttimebench)

### 为什么值得写

长任务 Agent 常被当成“给它更多时间就会更可靠”，但调度器真正需要的是三个能力：知道已经花了多久、知道还剩多少预算、在时间到点前选择继续、收尾或求助。AgentTime 把这件事和任务是否完成分开测，并公开数据和脚本，适合讨论值班工单、代码迁移、研究任务里的截止时间控制。它还暴露出一个工程问题：模型自己说“我还要十分钟”并不等于运行时真的会在十分钟后停下。

### 建议标题

**Agent 不是跑得越久越好：AgentTime 怎样测它会不会按时间交付**

### 文章梗概

晚上值班时，Agent 被要求“先查半小时，拿到证据就汇报”，结果十分钟就停了，或者找到答案后继续空转。文章从 AgentTime 的三个测试开始，区分按时工作、事前预测和事后回忆，再拆 222 个任务和原生 Harness 的计时方式。随后用公开代码复现一个小任务，比较只加提示词、时间工具和外部 supervisor 三种控制。最后讨论时间预算如何和重试、人工升级、并发队列绑定，并说明论文数字只代表指定模型和环境。
### 结构提纲

1. **完成和按时是两种能力**——给出任务完成、持续工作、时间预测和事后回忆的区分。
2. **AgentTime 怎样计时**——拆 222 个任务、18 个基准、三种测试、原生 Harness 和请求时长范围。
3. **论文结果如何读**——比较 Astra、Sol、Fable 的时长偏差、5% 命中率和休眠案例，说明“更强模型”不是充分条件。
4. **做一个可控的最小 Agent**——用 supervisor、剩余预算工具和结束状态复现短任务，并记录提前结束、超时和空转。
5. **把时间接入生产调度**——讨论截止时间、成本上限、心跳、重规划和人工升级之间的状态机。

### 写作所需证据

- 已有：论文 v2、结果网站、公开运行数据下载说明、MIT 代码、任务/请求时长定义和 supervisor 计时方式。
- 需要补做：先运行 `python -m agenttime suite/plan` 和测试；选一个本地工具任务，对比提示词、时间工具和外部进程终止；记录时间误差和最终状态。
- 适合配图：`任务预算 → Agent 循环 → 时间观测 → 继续/收尾/求助` 状态图；AgentTime 的 duration-following、forecasting、retrospection 三路流程图。
- 未验证点：完整实验依赖原生 Codex/Claude Code 版本和部分基准；网站结果及厂商模型名称不能替代同环境复现，公开 transcript 也不是全部运行记录。

## 2. 工具返回 200，但结果是错的：为什么 Agent 更容易被“安静故障”骗过

### 热点是什么

《Loud Failures, Quiet Failures》于 2026-10-07 提交，公开了 [论文](https://arxiv.org/abs/2610.10062) 和 [brittle-agents 代码、轨迹与分析脚本](https://github.com/obadaKraishan/brittle-agents)。作者在可执行的多轮工具基准上注入四类故障，使用 6 个模型、24 个任务和 1,920 次试验，分别记录 Agent 是否发现故障、是否改计划、是否恢复到无故障状态、是否重复调用。论文报告：显式错误时 91.3% 的试验会把结果当问题，返回格式正常但内容错误时只有 58.8%；无故障时仍有 26.8% 的运行报告问题。推理模型相比配对 instruct 模型发现更少、改计划更多，恢复率没有显著提升。

原始资料：

- [论文摘要](https://arxiv.org/abs/2610.10062)
- [论文 HTML（故障注入与统计方法）](https://arxiv.org/html/2610.10062v1)
- [brittle-agents 代码与数据](https://github.com/obadaKraishan/brittle-agents)

### 为什么值得写

很多工具协议只区分成功和异常，却没有表达“成功返回了错误事实”。这篇论文把故障检测、重规划、恢复和重复调用分开测，说明 Agent 主要在响应错误通道，而不是检查返回内容。对真实工单系统来说，错误订单号、旧库存、过期配置和被缓存的错误结果，比一次明确的 500 更危险。这个题目能直接落到工具契约、结果校验、独立观测和幂等重试，而不是再加一句“请仔细检查”。

### 建议标题

**工具返回成功不代表事情成功：拆开 Agent 对“静默错误”的盲区**

### 文章梗概

客服 Agent 查询订单时，接口返回结构完整的 JSON，只是状态来自旧缓存；模型看到没有报错，就把错误信息发给了客户。文章从这个“安静故障”开始，按论文的注入层重建超时、工具消失、schema 变化和内容损坏，区分发现、改计划、恢复和重复调用。接着解释无故障基线为何只有 63.3% 的运行一致性。最后用本地工具模拟器比较结果不变量、二次读取和状态对账，说明为什么一句“请检查结果”不够。
### 结构提纲

1. **四类故障如何进入工具层**——画出显式错误、超时、schema 漂移和格式正确但内容错误的注入点。
2. **四个指标不是一个成功率**——解释 detection、replanning、recovery、repetition 及无故障基线的计算。
3. **为什么推理模型没有自动解决问题**——结合论文的配对模型与统计设计，区分“多想几步”和“能校验外部事实”。
4. **把结果校验放到协议里**——设计范围、版本、交叉查询、状态快照和幂等键，让工具输出带可验证条件。
5. **做一次故障注入实验**——对同一工单任务注入一次静默错误，比较不同防线的恢复率、额外步骤和误报。

### 写作所需证据

- 已有：论文的 1,920 次试验、24 个任务、6 个模型、故障注入层、状态一致性公式和公开仓库。
- 需要补做：阅读仓库的 fault adapter 与分析脚本；在本地工具服务中注入一次内容损坏和一次 schema 漂移，保存完整轨迹。
- 适合配图：`工具调用 → 故障注入 → Agent 观察 → 重规划/重试/错误上报` 流程图；显式错误与静默错误的对照图。
- 未验证点：论文使用的模型、温度和任务集与生产工具不同；模型自报的“发现问题”由 Judge 编码，需关注编码误差和业务不变量的覆盖范围。

## 3. RAG 找不到答案时，先别急着换模型：RECAST 让 Agent 主动构造证据

### 热点是什么

《RECAST: Learning to Compute the Right Context through Adaptive Evidence Routing》于 2026-10-07 提交。它把上下文构造视为连续决策：RouterLM 在词法检索、语义检索、只读 SQL 和自定义代码之间选择，CompilerLM 把合成操作编译为 Python，直到 RouterLM 接受证据，再交给 AnswerLM 回答。论文在 6 类异构基准上报告平均成功率 75.6%，比最强大模型基线高 15.9%；在 3 个留出基准上平均提高 15.0%。这些结果来自论文的 SFT+GRPO 训练和固定的 CompilerLM/AnswerLM 配置。

原始资料：

- [论文摘要](https://arxiv.org/abs/2610.10507)
- [论文 HTML（操作空间、训练和消融）](https://arxiv.org/html/2610.10507v1)
- [论文 TeX 源码入口](https://arxiv.org/src/2610.10507)

### 为什么值得写

传统 RAG 默认证据已经存在，只需把相似片段找出来；但工单、数据分析和跨文档问答常常需要过滤、连接、聚合或计算才能得到证据。RECAST 的切口是“上下文不是字符串，而是一组带来源的中间产物”，这和用户的工单系统很接近：历史工单、订单表、日志和代码各自能回答一半，Agent 必须先做证据工程。文章可以把 Router/Compiler/Answer 三个角色拆开，讨论什么时候 SQL 足够、什么时候应该生成代码，以及如何限制合成操作的权限。

### 建议标题

**RAG 不是把片段塞进提示词：RECAST 如何让 Agent 先算出需要的证据**

### 文章梗概

一个客户问“这次团餐活动为什么只有部分门店少算了优惠”，答案不在任何一段文档里，而要把活动规则、门店配置和订单数据连起来算。文章先解释 RECAST 为什么把 RAG 改写成证据构造循环，再跟踪 RouterLM 选择检索、SQL 或合成代码，CompilerLM 执行并返回来源，直到 ACCEPT_CONTEXT。随后对比固定检索和传统 Agentic RAG，做一个小型工单数据实验，记录证据数量、查询成本和错误传播。论文的 75.6% 只按作者配置解读。
### 结构提纲

1. **“相关片段”为什么不等于答案证据**——用跨文档、表格和日志的工单示例说明过滤、连接和聚合的缺口。
2. **RECAST 的三模型执行链**——拆 RouterLM、CompilerLM、AnswerLM 的输入输出和终止条件。
3. **三个操作空间**——比较 BM25、Embedding、只读 SQL 和合成 Python 的能力、成本与权限风险。
4. **结果和训练如何产生**——解释 SFT+GRPO、6 类基准、留出集和论文的对照，不把成功率当作单次调用命中率。
5. **在工单场景做最小实现**——给结构化数据和文档设置证据 ID、查询白名单、代码沙箱和可回放轨迹。

### 写作所需证据

- 已有：论文公式、RouterLM 动作空间、三种 primitive、CompilerLM 一次编译、ACCEPT_CONTEXT 终止、训练数据规模和公开 HTML/TeX。
- 需要补做：按论文附录重写一个不训练的 Router；在本地订单/活动/工单数据上对比固定检索、SQL 路由和合成代码，记录证据来源和 Token。
- 适合配图：`问题 → RouterLM → 检索/SQL/编译 → 证据集 → AnswerLM` 的循环架构图；单次操作失败后重新路由的状态图。
- 未验证点：论文未提供可直接运行的完整仓库入口；CompilerLM 生成代码的安全隔离、数据泄漏、复杂任务成本和中文工单迁移效果都需要自行验证。

## 4. AI 找到漏洞以后，谁来确认它真的值得修？Anthropic OSS Scanner 的快车道

### 热点是什么

Anthropic 于 2026-10-08 发布 [Anthropic Cyber Mission](https://www.anthropic.com/news/anthropic-cyber-mission) 和 [OSS Scanner](https://red.anthropic.com/oss-scanner)，为自愿加入的关键开源项目提供定期模型扫描。扫描报告会包含复现器、漏洞解释、引入版本二分和候选补丁；快车道报告不经过人工复核，项目可以通过 PR 提交仓库、Dockerfile、联系人和威胁模型配置。Anthropic 的启动说明称早期验证中 97 个高/严重报告有 85 个达到 CVD 标准，另有 12 个中 11 个是真问题但重复或来自同一轮扫描；这些数字是 Anthropic 自报，且服务明确承认报告可能错误或严重性估计偏高。

原始资料：

- [Anthropic Cyber Mission 公告](https://www.anthropic.com/news/anthropic-cyber-mission)
- [OSS Scanner 说明与 FAQ](https://red.anthropic.com/oss-scanner/)
- [OSS Scanner 启动研究文章](https://www.anthropic.com/research/launching-opt-in-vulnerability-finding-service-for-open-source)

### 为什么值得写

安全 Agent 的难点不是“能否找到更多漏洞”，而是怎样把未验证发现送进一个不会淹没维护者的修复流程。OSS Scanner 公开了项目准入、离线 Docker 环境、威胁模型、PGP、报告频率、退出方式和无人工复核的风险边界，适合写成一条真实供应链：扫描、复现、去重、严重性、维护者确认、修复和披露。它也提供了一个重要对照：模型发现速度上来以后，验证和修复仍可能是瓶颈。

### 建议标题

**漏洞扫描 Agent 的最后一公里：拆 Anthropic OSS Scanner 怎样把发现交给维护者**

### 文章梗概

开源维护者收到一封报告：里面有漏洞、复现步骤和候选补丁，但报告没有人工复核，项目还要判断是否重复、是否符合自己的威胁模型。文章按 OSS Scanner FAQ 还原仓库配置、Dockerfile 离线审计、威胁模型、模型报告、反馈和后续扫描各自负责什么。然后搭一个隔离的“扫描→复现→去重→人工确认→补丁”沙盒，比较只给结论和附带可运行 PoC 的报告。Anthropic 自报的 85/97 只作为发布方证据，并列出误报、留存和披露边界。
### 结构提纲

1. **从发现到修复的链路缺了哪一步**——区分候选漏洞、已复现漏洞、已确认漏洞和已发布修复。
2. **OSS Scanner 的准入与运行环境**——拆项目 PR 配置、Dockerfile、离线沙箱、威胁模型和 GPG 报告。
3. **为什么快车道不等于自动披露**——说明无人工复核报告的退出、重复、严重性和披露规则。
4. **PoC、根因和补丁如何进入评审**——设计维护者可执行的验证清单，避免把模型解释当成证据。
5. **做一个安全的最小复现**——用故意存在的低风险漏洞测试报告结构、复现器、去重和人工 gate，不连接真实生产仓库。

### 写作所需证据

- 已有：Anthropic 公告、OSS Scanner FAQ、项目配置字段、离线扫描要求、退出和披露政策、自报早期验证数据。
- 需要补做：阅读公开 `anthropics/oss-scanner` 模板和 `tools/validate.py`；在隔离测试仓库中构造 Dockerfile、威胁模型和一个可复现缺陷，记录报告与人工 gate。
- 适合配图：`项目准入 → 离线扫描 Agent → PoC/根因/补丁 → 维护者复核 → CVD/修复` 流程图；快车道与人工复核两条路径的对照图。
- 未验证点：服务仍是 opt-in 和早期项目；自报准确率不是独立评测，报告留存、模型版本、跨项目去重和真实维护者负担需要后续观察。

## 5. 一个 Gemini Agent 负责整家公司：Google 把模型、技能、记忆和治理放进同一层

### 热点是什么

Google Cloud 于 2026-10-08 发布 Gemini at Work 2026，介绍 Gemini agent 作为统一工作 Agent。官方描述它能从单一入口规划任务、调用技能和工具、连接 Workspace/CRM/数据库/MCP，选择不同模型，并运行持久任务和临时子 Agent。公告还提出四类记忆（session、semantic、procedural、episodic）、每个 Agent 独立身份、Agent Sandbox、Agent Gateway、审计日志、实时 spend cap 和 Smart Routing。客户数量、效率和准确率均来自 Google 的发布材料；其中多项能力仍处于预览或后续推出阶段。

原始资料：

- [Google Cloud：Gemini agent 公告](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026)
- [Google Cloud：Gemini at Work 简介](https://blog.google/innovation-and-ai/infrastructure-and-cloud/google-cloud/gemini-at-work/)
- [官方安全、治理与成本章节](https://cloud.google.com/blog/products/ai-machine-learning/welcome-to-gemini-at-work-2026#securing-and-governing-agents)

### 为什么值得写

这不是又一个聊天机器人发布，而是一种企业 Agent 平台的架构宣言：模型可以替换，技能和数据留在企业控制面；Agent 有自己的身份、持久存储和审计记录，任务还能跨天运行。对工程团队来说，真正要拆的是“统一 Agent”背后的多模型路由、技能注册、记忆分层、权限传播、沙箱和费用暂停。文章应把官方产品描述与可验证接口分开，特别是“持续学习”“所有业务上下文”和客户效果数字，不能直接当成已证实能力。

### 建议标题

**企业 Agent 的核心不是一个大模型：拆 Gemini agent 的技能、记忆、身份和费用闸门**

### 文章梗概

一个客服主管说“把本周退款异常查清楚并给出行动计划”，企业 Agent 需要访问工单、邮件、数据库和文档，还要隔天继续工作。文章以此拆 Google 公布的 Gemini agent：统一入口如何规划目标，多模型路由如何控制成本，技能和工具注册表如何连接系统，四类记忆怎样支持跨天执行，身份、Sandbox、Gateway 和审计如何形成边界。随后用本地 mock 模拟子 Agent 越权、预算触顶和记忆过期，并把客户数字与“持续学习”标为待验证声明。
### 结构提纲

1. **从一个跨系统目标开始**——把“提问”改成目标、计划、工具调用、持久执行和交付物。
2. **模型为什么要和 Agent 分离**——解释 Smart Routing、多模型编排、技能注册表和工具/MCP 的关系。
3. **四类记忆与跨天任务**——比较 session、semantic、procedural、episodic 的写入者、读取范围、过期和撤销策略。
4. **身份、Gateway 与费用闸门**——跟踪 Agent 身份、OAuth、Sandbox、审计、网络策略和 spend cap 的控制顺序。
