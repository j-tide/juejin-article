> 检索范围：优先查看 2026-10-10 至 2026-10-13 的一手发布；这几天没有找到足够具体、且明显优于既有选题的官方新材料，因此扩展到 2026-10-06 至 2026-10-08。下列四项都在近 7 天内，但对厂商自报、论文实验和仓库自述分别标注，不把它们混写成独立实测。

## 1. AgentHorizon：长轨迹结果评测

**事件日期：** 2026-10-08  
**材料状态：** 论文与代码已公开；论文中的结果属于作者实验，尚非独立复核

### 热点是什么

AgentHorizon 论文（2026-10-08 发布，页面版本 v1）发布了面向计算机使用 Agent 的长轨迹评测集。作者从 166 小时人工操作记录中整理出 1,373 条指令—轨迹对，覆盖 3 种操作系统；通过交换相近指令构造正负样本，人工复核后保留 523 条正例与 850 条负例。评测包含 11 个 judge、最长 300 张截图和动作记录，并把错误分成 Critical Mistake、Bad Side Effect、Misunderstanding 等类型。论文报告 GPT-5.5 作为工具型 judge 在 AH 集上的 balanced accuracy 为 80.9%，同时观察到工具使用会让部分模型变好、部分开放权重模型变差。

**原始材料：** [论文摘要（arXiv）](https://arxiv.org/abs/2610.11050)；[论文正文（HTML）](https://arxiv.org/html/2610.11050v1)；[配套代码仓库](https://github.com/ServiceNow/agenthorizon)

### 为什么值得写

这件事的事实价值在于它把“任务完成”从最后一张截图，推进到完整执行证据：中间有没有改错对象、是否产生未要求的副作用、是否漏掉隐藏条件。论文还给了长轨迹、负例配对和 judge 行为差异，足以做源码/数据格式阅读与小型复现实验。我的判断是，当前 Agent 评测最容易漏掉的不是点击失败，而是看起来成功、实际违反指令的结果；这个切口能连接评测、训练和上线监控，而不是再写一个“自动化办公”功能清单。

### 建议标题

**Agent 说“完成了”不等于真的完成：拆 AgentHorizon 的长轨迹评测**

### 文章梗概

一个桌面 Agent 打开软件、填完表单、导出文件，最后截图看起来一切正常，却可能混入未要求的字段，或把关键动作做在了错误对象上。文章从 AgentHorizon 的配对轨迹构造入手，解释为什么“换一条指令、复用同一段执行记录”能制造高质量负例。随后拆 300 张截图、工具型 judge、Bad Side Effect 与 hidden evidence，做一个只检查关键事件的本地评测器。最后讨论自动评分进入训练闭环后，误收失败轨迹和误删成功轨迹各自会造成什么后果。

### 结构提纲

1. 从一段“看起来成功”的桌面操作开始，区分最终画面、动作序列和用户真正要求的结果。
2. 阅读 AgentHorizon 的配对构造与标注字段，说明交换指令为什么能暴露隐藏错误。
3. 拆解长轨迹 judge 如何定位关键截图、工具调用和副作用，并对比整段输入与证据抽取。
4. 做一个本地 toy evaluator：先检查必须发生的事件，再检查禁止发生的对象或字段。
5. 讨论 judge 偏差进入训练、回归测试和线上告警后的成本，以及哪些结果仍需人工复核。

### 写作所需证据

已有：arXiv 论文、正文中的数据规模/任务划分/错误类型、ServiceNow 代码入口。需要补做：阅读仓库的数据 schema 和 judge prompt，抽取一条正负配对轨迹；在本地构造 20—30 条带副作用的 toy 轨迹，比较规则检查、模型 judge 与人工标签。适合配图：指令→截图/动作流→证据定位→错误分类→评分与不确定性。关键未验证点：论文数据能否跨领域泛化，工具型 judge 的收益是否依赖模型，负例比例和标注标准对分数的影响。

## 2. Ironclad：合同软件工作流评测

**事件日期：** 2026-10-06  
**材料状态：** OpenAI 与 Ironclad 官方案例；指标为厂商披露，时间为模拟估算，不是客户实测节省

### 热点是什么

OpenAI 于 2026-10-06 发布与 Ironclad 的联合案例，描述用复杂合同、商业和采购流程训练与评测 Agent。公开任务集包含 11 个任务，每个任务有 8—50 条评分标准；任务来自 SEC EDGAR 公开合同，经过隐私处理，不含客户或 Ironclad 内部数据。官方披露 GPT-6 Astra 平均得分 55.0%，GPT-5.6 Sol 为 41.6%；按案例设定估算的每次尝试时间分别为 19.2 和 37.0 分钟。文中明确说明这些时间是模拟估算，不代表真实客户节省。

**原始材料：** [OpenAI 官方案例](https://openai.com/index/advancing-computer-use-with-ironclad/)

### 为什么值得写

这个案例适合写企业 Agent 的“最后一公里”：会打开页面、填表、点击审批并不代表业务结果正确，真正难的是把金额阈值、审批条件、模板字段和例外情况拆成可检查的规则。11 个任务、8—50 条 criteria 和托管软件环境提供了具体分析对象，也能展示厂商指标的边界。我的判断是，企业 Agent 的核心交付物应是一张可追溯的业务规则—测试矩阵，而不是一句“自动完成合同”；同时必须把自报成绩和真实生产收益分开。

### 建议标题

**企业 Agent 为什么总在最后一步失分？拆 OpenAI 与 Ironclad 的 11 个合同流程评测**

### 文章梗概

合同流程 Agent 会填表、建模板、点审批，却可能把金额阈值配错，导致只有部分请求走了安全路径。文章按 OpenAI 与 Ironclad 的 11 个任务重建“业务规则→软件配置→跨场景验证”的执行链，拆 8—50 条评分标准怎样把一句需求变成可检查结果。再比较规则检查、浏览器回放和模型自评，讨论训练任务、托管环境与强化学习如何接上真实软件。最后明确 55.0% 对 41.6% 和“估算时间”各自能证明什么、不能证明什么。

### 结构提纲

1. 用一个合同审批误配的场景开场，说明页面操作成功与业务规则满足是两件事。
2. 根据官方案例还原 11 个任务、评分标准和托管环境，建立从需求到检查项的映射。
3. 对照规则引擎、浏览器回放和模型自评，分析各自能抓到的错误与漏报。
4. 设计一个小型采购审批应用，验证配置、例外分支和跨场景回归如何影响结果。
5. 解释 55.0%、41.6% 与模拟时间的统计边界，给企业落地列出数据、权限和人工验收条件。

### 写作所需证据

已有：OpenAI 官方案例、任务数量与评分范围、SEC EDGAR 数据来源、指标脚注。需要补做：检查页面是否公开更多任务标准；搭建一个带金额阈值和审批分支的 toy procurement app，写 10 个场景和回放脚本。适合配图：需求→配置→场景矩阵→执行回放→规则校验→人工验收。关键未验证点：11 个任务对其他合同流程的代表性、模拟时间与生产耗时的差距、厂商选择任务和评分标准的偏差。

## 3. OpenAI 数学仓库：研究交付协议

**事件日期：** 2026-10-06  
**材料状态：** 官方研究说明与 GitHub 仓库已公开；仓库明确并非全部结果都已形式化或核验

### 热点是什么

OpenAI 于 2026-10-06 公开一批数学研究结果，并同步发布 GitHub 仓库和修订/引用协议。官方说明提到模型尝试约 4,000 道问题、公开 10 份精简推理摘要，并为许多结果提供 Lean 形式化；仓库 README 当前列出 719 份 manuscript、372 个 family，约 42% 的顶层结果已形式化，同时明确并非所有结果都已核验，未形式化结果可能存在问题。仓库保留目录、引用和版本历史，使读者能把论文文本、形式证明和后续修订放在同一条链上。

**原始材料：** [OpenAI 官方研究说明](https://openai.com/index/sharing-ai-progress-in-mathematics/)；[公开数学仓库](https://github.com/openai/math)

### 为什么值得写

这里值得写的不是“模型会不会做数学”，而是研究 Agent 交付一个可审查结果时要带哪些证据：自然语言命题、Lean 文件、引用、推理摘要、目录元数据和版本变更。形式化系统能确认某个形式命题通过检查，却不能自动保证论文表述、动机和引用没有问题。这个项目同时给出公开材料和明确限制，适合做一次小规模 Lean 复核，再把交付协议映射到代码 Agent 和实验复现。

### 建议标题

**AI 说自己证明了，工程上还要交什么？拆 OpenAI 数学仓库的论文、Lean 与版本链**

### 文章梗概

一个研究 Agent 交付了漂亮的证明，审查者仍要问：命题是否写对、证明是否真的编译、引用是否完整、后来改动能否追溯。文章从 OpenAI 10 月 6 日公开的数学仓库出发，拆 manuscript、Lean formalization、reasoning summary、目录和版本历史如何组成证据链。随后选一份公开结果跑 Lean 检查，比较“形式系统接受”与“自然语言论文可信”之间的空白。最后把这套交付协议映射到代码 Agent 和实验复现，给出可自动化与必须人工复核的边界。

### 结构提纲

1. 从一条看似完整的数学结论开始，区分发现、写作、形式化和审查四种工作。
2. 阅读仓库目录、manuscript、family、Lean 文件与引用协议，画出证据链和版本关系。
3. 选择一个公开结果执行 Lean 检查，记录依赖、编译状态和形式命题与自然语言之间的差异。
4. 对照代码 Agent 的测试、实验 Agent 的数据与研究稿件，抽象可复用的交付字段。
5. 列出自动化检查、同行复核和领域专家判断的边界，避免把形式通过当成全部可信。

### 写作所需证据

已有：OpenAI 官方说明、GitHub README 的 719/372/约 42% 统计、版本与引用约定。需要补做：选取仓库中一份公开 manuscript，按其说明安装 Lean/依赖并记录实际编译结果；核对形式命题与正文叙述是否一一对应。适合配图：研究想法→manuscript→Lean proof→引用/版本→机器检查→人工审阅。关键未验证点：仓库后续更新会改变统计，形式化覆盖率不等于结论正确率，依赖公理和人工定义仍需单独说明。

## 4. Jump Trading：长周期 autoresearch 工作流

**事件日期：** 2026-10-06  
**材料状态：** OpenAI 客户案例自报；未见独立基准或可复现实验数据

### 热点是什么

OpenAI 于 2026-10-06 发布 Jump Trading 客户案例，描述使用 GPT-6 Astra、Agent harness 和基础设施做长周期量化研究。案例给出的工作方式是：人类提出问题并定义环境和评价标准，多个 Agent 在受控环境中探索、协作和提交改进，再由人类审查。页面强调安全监控、权限隔离和清晰目标，但没有给出独立验证的收益、成功率或可复现实验数据，因此不能把它当成通用性能基准。

**原始材料：** [OpenAI 官方客户案例](https://openai.com/index/jump-trading/)

### 为什么值得写

它有意思的地方在于把“让 Agent 自己研究几天”还原成一条工程流水线：问题定义、数据权限、沙箱、实验队列、指标、回滚和人工合并缺一不可。案例本身是厂商与客户的自报材料，反而适合拿来练习证据分层：哪些是流程描述，哪些是结果主张，哪些需要自己做实验。我的判断是，多 Agent 协作只有在评价函数稳定、失败可回滚时才扩大搜索覆盖，否则只是并行制造更多噪声。

### 建议标题

**Agent 可以自己做几天研究吗？拆 Jump Trading 的 autoresearch 工作流**

### 文章梗概

量化研究员把一个开放问题交给 Agent，让它拉数据、跑实验、合并改进，听起来像“自动研究员”，但没有明确评价函数，长任务只会变成昂贵的试错。文章以 Jump Trading 分享的 GPT-6 Astra 工作流为例，拆问题定义、隔离环境、数据权限、实验队列、结果评审和人类验收六个环节。随后做一个小型 autoresearch toy loop，演示指标漂移、过拟合和失败回滚。最后把客户自报案例与可复现实验分开，讨论多 Agent 协作何时提高搜索覆盖，何时只是放大噪声。

### 结构提纲

1. 用一个研究指标连续变好却无法出样本外结果的场景，说明长任务首先需要可判定的进步。
2. 按客户案例拆问题、环境、数据权限、实验队列、评价和人工合并六个环节。
3. 实现一个最小 autoresearch toy loop，加入指标漂移、预算上限和失败回滚。
4. 比较单 Agent、并行 Agent 和带审查队列的协作，观察覆盖率、重复实验和噪声。
5. 把客户自报、内部日志和独立复现分层，给金融等高风险场景列出权限与审计边界。

### 写作所需证据

已有：OpenAI 客户案例中的流程描述、环境/评价/人类审查与安全监控表述。需要补做：写一个公开数据集上的 toy research loop，记录每轮实验、指标、回滚和预算；不能把 toy 结果外推到真实量化收益。适合配图：研究问题→沙箱→实验队列→评价函数→候选合并→人工发布。关键未验证点：案例使用的真实数据、评价函数和基础设施细节未公开，多 Agent 协作收益缺少独立数字，金融数据与权限边界需要另行审查。

## 今日优先推荐

优先写第 1 题《Agent 说“完成了”不等于真的完成：拆 AgentHorizon 的长轨迹评测》。它是本期最接近 10 月 10—13 日窗口的实质材料（论文发表于 10 月 8 日），同时给出数据构造、错误分类、长轨迹和可下载代码，能支撑一篇有图、有小实验、有边界讨论的文章。它与前几天的运行监控话题能接上，但切口转向“如何审判最终轨迹”，不会重复写告警或安全政策。
