## 1. 长任务为什么越跑越笨？拆 Deep Agents 的五种上下文工程

**事件日期：** 2026-10-14（原文发布日期）

**材料状态：** LangChain 官方设计说明，含中间件挂载点、约 20,000/50,000 token 外置阈值、85% 摘要阈值和可恢复文件路径；没有独立基准，不能把“防止 context rot”写成已验证的成功率。

### 热点是什么

LangChain 在 10 月 14 日发布 Deep Agents 上下文工程说明，把长任务的上下文管理拆成五个可组合机制：大工具结果和长用户消息先写入文件、接近窗口上限时做可恢复摘要、按需加载 skills、用子 Agent 隔离噪声、把长期记忆放在用户控制的文件存储里。文章还说明这些能力通过 middleware 接在 Agent 循环的启动、模型调用和工具调用前后。

原始材料：
- [https://www.langchain.com/blog/context-engineering-deep-agents-remember](https://www.langchain.com/blog/context-engineering-deep-agents-remember)

### 为什么值得写

这不是又一篇“上下文窗口越大越好”的介绍，而是一套可以画出执行链、逐个替换的工程方案。读者可以拿它对照自己的长任务 Agent：哪些数据应该留在窗口，哪些应该外置，摘要丢失细节后如何回读，以及子 Agent 的隔离到底换来了什么。需要明确的是，来源是框架方的实现说明，尚未给出跨任务的质量、延迟或成本对照。

### 建议标题

长任务为什么越跑越笨？拆 Deep Agents 的五种上下文工程

### 文章梗概

长任务 Agent 变慢、答非所问，往往不是模型突然变差，而是历史、工具输出和中间草稿一起挤进了上下文。本文从 Deep Agents 的实现说明出发，沿着 middleware 的执行位置，拆解外置大结果、可恢复摘要、按需技能、子 Agent 隔离和文件记忆五条路径，再用一个持续调研任务对比“截断、摘要、回读”的差别。文章会把官方阈值和机制与尚未验证的质量收益分开，最后给出何时该外置、何时该回读的判断表。

### 结构提纲

1. 从一次跨多家公司调研任务开始，画出消息、工具结果和草稿不断增长的上下文曲线。
2. 跟进 middleware 挂载点，解释外置文件、预览和后续分页读取怎样改变一次模型调用的输入。
3. 比较 85% 阈值摘要、保留最近消息和把旧历史写入文件的可恢复链路，指出摘要失败时的退化路径。
4. 拆解 skills 的渐进式披露与子 Agent 独立窗口，说明“少放进主上下文”分别解决什么噪声。
5. 用文件记忆收尾，讨论跨模型迁移、权限隔离、清理策略和不适合外置的短上下文任务。

### 写作所需证据

已掌握：官方文章中的五种机制、阈值、文件路径和 middleware 生命周期。
需要补做：阅读 Deep Agents 对应 middleware 源码，确认阈值配置、异常处理和并发读写语义；用固定的调研假数据做“全量历史 / 截断 / 可恢复摘要”三组本地 token 与回读实验，未执行前不写模型质量结论。
配图：Agent 循环与 middleware 挂载图、上下文 token 曲线、主 Agent/子 Agent/文件存储的时序图。
未验证点：摘要模型选择、回读触发条件和文件存储在多租户环境的权限边界。

## 2. 别再给 Agent 日志打标签了：LangSmith 如何按行为搜索整条轨迹

**事件日期：** 2026-10-13（原文发布日期）

**材料状态：** LangChain 官方产品与架构说明，AI Search 处于 LangSmith Cloud 公测；轨迹归一化、8K token 预算、过滤后并行判定和流式返回是厂商披露的设计，暂无独立延迟或精度数据。

### 热点是什么

LangChain 在 10 月 13 日介绍 LangSmith AI Search：用户可以用“Agent 说完成了但其实没有”“用户是否泄露了 PII”这类自然语言搜索行为。系统先用结构化过滤缩小候选，再让快速决策模型读取每条轨迹；SmithDB 会把不同 SDK 的 trace 归一化为 trajectory，去掉重复的历史消息，按优先级填充 8K token，再并行检查并流式返回结果。

原始材料：
- [https://www.langchain.com/blog/agent-traces-ai-search-langsmith](https://www.langchain.com/blog/agent-traces-ai-search-langsmith)

### 为什么值得写

Agent 的故障经常跨越用户输入、工具调用和最终回答，单个标签或向量很难保留“做过什么”和“说过什么”的差别。这个切口适合写成一篇可落地的可观测性文章：先解释为什么向量召回会把“完成”和“声称完成”混在一起，再讨论轨迹规范化、预算裁剪和模型判定的成本边界。文中应把 LangSmith 的产品实现和可迁移到自建系统的抽象分开，不把其百万 token 样本当成普遍分布。

### 建议标题

别再给 Agent 日志打标签了：LangSmith 如何按行为搜索整条轨迹

### 文章梗概

当用户问“哪些会话泄露了 PII”或“哪些 Agent 说完成却没交付”时，关键词、标签和单向量召回都不够。本文沿着 LangSmith AI Search 的执行链，解释 trace 为什么要先归一化为 trajectory，为什么先做结构化过滤，再让决策模型读取候选轨迹，以及 8K token 预算怎样优先保留用户和 Agent 的关键话轮。最后用一组本地模拟轨迹对比关键词、向量和逐轨迹判定，明确延迟、召回和证据完整性之间的取舍。

### 结构提纲

1. 从“说完成但没有工件”的真实故障出发，列出传统标签、全文检索和向量检索各自看不到的证据。
2. 拆解多 SDK trace 到统一 trajectory 的归一化过程，说明去重历史消息为何能降低上下文膨胀。
3. 沿着查询路径分析结构化过滤、8K token 优先级裁剪、决策模型判定和批量流式返回。
4. 用模拟数据做三种检索基线，观察行为问题下的误召回、漏召回和单条轨迹读取成本。
5. 讨论工具结果被裁掉、模型不确定和多模态输入出现时，系统应该怎样二次取证或升级人工复核。

### 写作所需证据

已掌握：官方文章的轨迹模型、8K token 预算、候选过滤、并行扫描和公测范围。
需要补做：构造包含重复历史、工具报错、PII 和“声称完成”的 JSONL 轨迹；本地实现关键词/TF-IDF 或向量基线与逐轨迹规则判定，记录可复现的时间和召回差异，不能把模拟结果外推到 LangSmith。
配图：trace→trajectory 归一化图、查询过滤到决策模型的流水线图、token 预算裁剪优先级图。
未验证点：真实决策模型的误报率、不同问题所需的证据范围，以及跨供应商 trace 的字段兼容性。

## 3. Agent 用得越多就越聪明吗？拆 OpenAI 欧盟 Agentic 用量报告的指标陷阱

**事件日期：** 2026-10-14（原文发布日期）

**材料状态：** OpenAI Economic Research 官方报告；样本只包含 ChatGPT Enterprise/Business，SMB 的“200 个关联用户以内”和 frontier firm 的“按每活跃用户输出 token 前 10%”定义已公开。token 占比和活跃用户增长不是任务成功率、生产率或自动化率。

### 热点是什么

OpenAI 在 10 月 14 日发布欧盟 Agentic 使用报告，称其样本中 Codex 与 ChatGPT Work 已占企业输出 token 的一半以上，欧盟 SMB 的相关周活跃用户自 5 月增长超过 8 倍；不同国家的 agentic token 占比从斯洛文尼亚 22% 到立陶宛 85%。报告还用每活跃用户输出 token 将企业分成 typical 与 frontier，并指出欧盟 frontier 企业与全球 frontier 仍有差距。

原始材料：
- [https://openai.com/index/the-eus-next-chapter-in-ai-is-agentic/](https://openai.com/index/the-eus-next-chapter-in-ai-is-agentic/)
- [https://cdn.openai.com/pdf/europes-agentic-opportunity.pdf](https://cdn.openai.com/pdf/europes-agentic-opportunity.pdf)

### 为什么值得写

这些数字很容易被转述成“Agent 已经替代工作”，但报告真正测量的是特定产品、特定账户样本里的输出 token 和活跃用户。文章可以把它当成一堂指标审计课：拆清 token share、WAU、每用户输出量与任务成功率的关系，解释为什么使用深度不等于交付价值，并给工程团队一套自己的 adoption/quality/impact 三层指标。这样既能回应热点，也能避免把厂商自报数据当成行业普查。

### 建议标题

Agent 用得越多就越聪明吗？拆 OpenAI 欧盟 Agentic 用量报告的指标陷阱

### 文章梗概

OpenAI 的欧盟报告给出一组很抓眼的数字：Agentic 工具占企业输出 token 过半，SMB 周活跃用户数月增长超过 8 倍，不同国家占比从 22% 到 85%。但 token share 不是任务成功率，活跃用户也不是流程自动化率。本文逐项拆解报告的样本、定义和计算口径，再把它们映射到工程团队可落地的 adoption、quality、impact 三层指标，最后用一个客服工单 Agent 例子说明如何避免“用得多”被误读成“交付得好”。

### 结构提纲

1. 先读报告脚注，厘清 Enterprise/Business 样本、SMB 定义、frontier 分组和 28 天输出窗口。
2. 把 agentic token share、WAU、输出 token/活跃用户与任务成功率画成不同指标，说明它们不能互相替代。
3. 构造客服工单 Agent 的指标账本，分别记录调用深度、人工接管、工单一次解决和返工成本。
4. 讨论厂商自报数据的选择偏差、产品变化和地区差异，给出阅读这类报告时的核对清单。
5. 收束到组织落地：先建立可审计的事件与结果字段，再决定是否扩大 Agent 使用范围。

### 写作所需证据

已掌握：OpenAI 官方文章和 PDF 的样本边界、国家差异、SMB 增长、frontier 定义及图表口径。
需要补做：按报告定义复算 PDF 中的关键比例，设计一份不依赖厂商产品的 Agent 事件表；用合成工单演示 token、调用次数、人工接管和最终解决率出现分歧的情况，明确这是示例而非真实业务结果。
配图：指标口径关系图、客服工单从调用到交付的漏斗图、adoption/quality/impact 三层仪表板草图。
未验证点：报告样本的行业分布、输出 token 与真实工作量的相关性，以及不同 Agent 产品之间的可比性。

## 4. AI 集群为什么开始重写以太网传输？拆 MetaRoCE 与 OCP 的开放路线

**事件日期：** 2026-10-12（原文发布日期）

**材料状态：** Meta 工程博客与 OCP 相关公告；MetaRoCE 的规范、参考实现和合规测试套件由 Meta 宣布开放，64 节点 AMD 集群对比和 1%/10% 丢包数据是官方实测，尚无独立硬件复测。

### 热点是什么

Meta 在 10 月 12 日 OCP Summit 文章中宣布 MetaRoCE 的开源实现，并把它放进更大的 AI 网络开放路线：FPF 多平面 scale-out、IcePack/IceCube 液冷交换设备、OSPA 交换机平台，以及 scale-across 的 BAG 超级脊。MetaRoCE 的设计把多路径、乱序到达、丢包恢复和拥塞控制更多放到 NIC 端，官方 8 月说明还提到会提供规范、Linux 参考实现和合规测试套件。

原始材料：
- [https://engineering.fb.com/2026/10/12/open-source/ocp-summit-2026-powering-ai-with-open-innovations-in-scale-up-scale-out-and-scale-across-networks/](https://engineering.fb.com/2026/10/12/open-source/ocp-summit-2026-powering-ai-with-open-innovations-in-scale-up-scale-out-and-scale-across-networks/)
- [https://engineering.fb.com/2026/08/24/networking-traffic/metaroce-rdma-transport-ai-ethernet/](https://engineering.fb.com/2026/08/24/networking-traffic/metaroce-rdma-transport-ai-ethernet/)

### 为什么值得写

模型和 Agent 的上层代码看不见 RDMA，但训练 all-reduce、推理分片和 KV cache 传输都会被最慢的一条网络路径拖住。这个热点的价值在于能把“AI 基础设施开放”落到协议执行：为什么允许乱序，为什么不依赖 PFC，NIC 如何按路径维护 RTT/ECN，软件栈怎样在不改动 RDMA Verbs 的情况下接入。要同时标出官方测得的吞吐与丢包结果、规范是否已可下载、以及普通开发者无法在本地复现硬件级结论的边界。

### 建议标题

AI 集群为什么开始重写以太网传输？拆 MetaRoCE 与 OCP 的开放路线

### 文章梗概

训练和推理的瓶颈不只在 GPU，也在成千上万张卡之间的网络。Meta 近期把 MetaRoCE、FPF 和交换机平台一起带到 OCP，试图用开放的以太网传输承受多平面、丢包和跨机房距离。本文从一个 all-reduce 数据包出发，解释 MetaRoCE 为什么允许乱序、怎样在 NIC 侧做多路径和拥塞控制，再对照传统 RoCE 的 PFC 与顺序假设。最后把官方 64 节点测试和普通团队可复现的 Linux/UDP 实验分开，说明协议开放、硬件可用和生产收益之间还差哪些验证。

### 结构提纲

1. 从 all-reduce 和推理分片的“最慢链路决定整体速度”开始，定位网络协议而非 GPU 算力的约束。
2. 逐包解释 MetaRoCE 的目标地址、乱序写入、每路径 RTT/ECN 和选择性重传机制。
3. 对照 RoCEv2 的 PFC、顺序交付和交换机侧假设，说明为什么多平面网络会放大旧模型的代价。
4. 把 Meta 的 FPF、BAG、FBOSS 与 MetaRoCE 放到同一张 scale-up/scale-out/scale-across 架构图中。
5. 区分官方硬件实测、Linux 参考实现和读者可做的 UDP 丢包实验，列出从规范到生产部署的验证门槛。

### 写作所需证据

已掌握：Meta 10 月 OCP 文章、8 月 MetaRoCE 设计说明、开放规范/参考实现/合规套件计划，以及官方 64 节点与丢包结果。
需要补做：核对 OCP 提交的规范和参考实现当前可下载状态；若代码可得，运行 Linux UDP 参考实验，注入乱序、丢包和多路径，记录协议行为，不能将软件模拟结果等同于 NIC 硬件性能。
配图：GPU/NIC/交换机的 scale-up 与 scale-out 图、MetaRoCE 单连接多路径时序图、丢包重传状态机。
未验证点：规范版本、跨厂商互操作性、真实集群的尾延迟收益和运营复杂度。
