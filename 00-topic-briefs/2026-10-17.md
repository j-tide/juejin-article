## 1. 1M Token 不是长任务答案：拆 Gemini 4 Argon 的续跑协议和 Agent 监控

**事件日期：** 2026-10-13（原文发布日期）

**材料状态：** Google 官方发布与模型卡；1M 输入输出窗口、续跑协议、监控器和安全数字均为厂商说明或厂商评测，尚无独立复测，不能把内部工程案例写成普遍收益。

### 热点是什么

Google 在 10 月 13 日开放 Gemini 4 Argon，面向 API、AI Studio、企业产品和 Antigravity。官方给出的工程切口不只是“更强模型”：它提供最高 1M token 的输入输出合计窗口和 continuation protocol，模型卡明确为原生多模态稀疏 MoE；Google 还介绍了实时 misalignment monitor、不可逆操作前暂停、间接提示注入测试，以及在 Chrome、ADK 和 Gemma 推理优化中的内部案例。

原始材料：
- [https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-argon/](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-argon/)
- [https://storage.googleapis.com/deepmind-media/Model-Cards/Gemini-4-Argon-Model-Card.pdf](https://storage.googleapis.com/deepmind-media/Model-Cards/Gemini-4-Argon-Model-Card.pdf)

### 为什么值得写

长上下文、续跑和动作监控其实是三层不同问题：上下文能不能放下，任务能不能跨请求接着跑，Agent 是否会在遇到权限或测试失败时走捷径。把它们混成“1M token 就能解决长任务”会掩盖状态持久化、费用、超时和人工确认的设计。这个题目可以沿 API 请求、上下文续接和动作拦截画出完整链路，同时把 Google 的内部数据与尚未独立验证的模型能力分开。

### 建议标题

1M Token 不是长任务答案：拆 Gemini 4 Argon 的续跑协议和 Agent 监控

### 文章梗概

Gemini 4 Argon 把 1M 输入输出窗口、续跑协议和 Agent 动作监控一起推到开发者面前，但这三件事解决的不是同一个问题。本文从一次跨多文件的长任务开始，拆解上下文窗口、跨请求状态、工具调用和人工确认如何串起来，再对照模型卡中的安全边界与官方内部案例。重点会放在协议与状态机，而不是复述“更强模型”的宣传；没有独立复测的数字只作为待验证假设。

### 结构提纲

1. 用一个跨多文件重构任务区分“单次上下文够大”和“任务可以跨请求继续”两个状态。
2. 沿着输入、输出、续跑 token 与工具结果，画出 1M 窗口在 Agent 循环里的真实成本。
3. 拆 continuation protocol 需要保存哪些会话状态、怎样处理超时、重试和重复工具调用。
4. 对照 Google 描述的 misalignment monitor、失败测试和不可逆操作确认，说明监控器应该站在模型前后哪一层。
5. 设计本地长任务回放与提示注入实验，列出采用 Argon 前必须补齐的审计字段和人工接管点。

### 写作所需证据

已掌握：Google 发布文章与 Gemini 4 Argon Model Card，包含输入输出窗口、原生多模态、续跑协议入口、监控和安全评估边界。
需要补做：核对 Gemini API 续跑协议的公开文档；若没有可用模型额度，则用假的 tool-call 状态机验证断点续跑、重复提交和人工确认，不把状态机测试当成模型能力结果。
配图：一次长任务的请求/续跑时序图、模型—工具—监控器三层架构图、不可逆动作的审批状态机。
未验证点：续跑状态是否包含完整工具回执、1M 窗口的真实计费与延迟、监控器在生产误报时的降级路径。

## 2. 本地 Agent 开始验证“做没做”：拆 GAIA v0.25.0-rc17 的权限、记忆与交付确认

**事件日期：** 2026-10-16（原文发布日期）

**材料状态：** AMD GAIA 官方 GitHub 预发布说明与仓库；v0.25.0-rc17 是 release candidate，不是最终稳定版。首响应约 43 秒降到 21 秒等数字是项目方本地测试，需在相同硬件、模型和缓存条件下复核。

### 热点是什么

AMD 的 GAIA 仓库在 10 月 16 日发布 v0.25.0-rc17。变更集中在 Agent harness：Agent UI 统一到旗舰 GAIA Agent，首次启动可配置模型和权限并支持可撤销的 always allow；拒绝动作不会偷偷换工具重试；回答会对照工具实际结果，未确认时才提示；记忆按请求相关性加载、在回答后保存；长任务按“有进展”而不是固定时长决定是否继续。

原始材料：
- [https://github.com/amd/gaia/releases](https://github.com/amd/gaia/releases)
- [https://github.com/amd/gaia](https://github.com/amd/gaia)

### 为什么值得写

这是少见的“把 Agent 做没做”直接写进本地产品的版本说明。它没有只强调模型大小，而是把权限、工具回执、记忆写入时机、MCP 故障、停止和超时都变成用户能看到的状态。读者可以顺着开源代码验证这些承诺，比较云端 Agent 常见的黑盒回执和本地可审计状态；同时要把 release candidate 的行为与稳定版兼容性分开。

### 建议标题

本地 Agent 开始验证“做没做”：拆 GAIA v0.25.0-rc17 的权限、记忆与交付确认

### 文章梗概

一个本地 Agent 真正难的地方，不是把模型下载下来，而是用户拒绝后它会不会换条路偷偷重试，工具失败后回答会不会仍说“完成了”。GAIA v0.25.0-rc17 把权限、工具回执、记忆保存、长任务超时和模型来源都写进版本变更。本文沿开源代码追踪一次命令执行，验证“允许、拒绝、失败、停止、未确认”如何落到状态与 UI，再讨论本地模型、云模型和 release candidate 的边界。

### 结构提纲

1. 从一次需要审批的 shell 命令开始，记录 Agent 请求、用户拒绝、工具回执和最终回答的状态转换。
2. 阅读权限层和 persistent shell，解释“拒绝后不换工具重试”怎样防止语义绕过。
3. 跟进“回答与工具结果对照”的实现，区分工具执行成功、输出存在和业务目标完成。
4. 拆记忆按相关性加载、回答后保存与模型重嵌入，说明失败经验为什么不能在回答前写入。
5. 复现长任务进展超时、MCP 不可达和停止后继续提问，给出本地 Agent 的验收清单。

### 写作所需证据

已掌握：GAIA v0.25.0-rc17 的官方 release notes、仓库入口、权限/记忆/工具验证/长任务行为说明。
需要补做：固定到 release commit，阅读 Agent UI、tool approval、memory 和 stream timeout 相关代码；在本机可用环境中跑一次拒绝、工具报错、停止和云模型标识实验，记录实际日志。
配图：本地 Agent 的 UI—harness—工具—模型分层图、审批状态机、工具结果到最终回答的校验时序图。
未验证点：rc17 到最终版的差异、不同 GPU/模型下首响应数据、长期记忆重嵌入的耗时和失败恢复。

## 3. 从告警到可合并 PR：GitHub Agentic Autofix 如何把安全修复接进 CodeQL

**事件日期：** 2026-10-15（原文发布日期）

**材料状态：** GitHub 官方 Changelog 与 Enterprise Cloud 文档；Agentic Autofix 和 AI Scan 已 GA，但官方明确是 best-effort、需人工审查，AI Scan 发现不会阻塞合并，也没有公开修复成功率或误报率。

### 热点是什么

GitHub 在 10 月 15 日同时推进两条应用安全 Agent 链路：AI Scan for pull requests GA，为 CodeQL 尚未覆盖的 PHP、Shell、Terraform、Dockerfile 等变更提供 advisory findings；Agentic Autofix GA，则从告警出发跨文件探索、生成修复、重新运行 CodeQL，必要时迭代，最后打开 draft PR。一次安全活动最多可批量处理 25 个告警，还能通过 REST API 指派给 Copilot。

原始材料：
- [https://github.blog/changelog/2026-10-15-agentic-autofix-for-code-scanning-alerts-general-availability/](https://github.blog/changelog/2026-10-15-agentic-autofix-for-code-scanning-alerts-general-availability/)
- [https://github.blog/changelog/2026-10-15-ai-scan-for-pull-requests-generally-available/](https://github.blog/changelog/2026-10-15-ai-scan-for-pull-requests-generally-available/)
- [https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/code-scanning/autofix-for-code-scanning](https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/code-scanning/autofix-for-code-scanning)
- [https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/code-scanning/ai-powered-security-detections](https://docs.github.com/en/enterprise-cloud@latest/code-security/concepts/code-scanning/ai-powered-security-detections)

### 为什么值得写

亮点不在“模型会改代码”，而在修复必须回到独立的 CodeQL 检查，且系统把扫描、Agent、Actions、AI credits 和人工 review 串成一条可审计流水线。文章可以拆清 AI Scan、Copilot Autofix 和 Agentic Autofix 三个边界，讨论为什么 advisory finding 不能直接变成 merge gate，以及如何为安全 Agent 设计回滚、预算和证据字段。

### 建议标题

从告警到可合并 PR：GitHub Agentic Autofix 如何把安全修复接进 CodeQL

### 文章梗概

安全 Agent 最怕的是“改完看起来对，但漏洞并没有消失”。GitHub 最近把 AI Scan 和 Agentic Autofix 接成一条从 PR 检测、跨文件探索、生成修改到重新运行 CodeQL 的流水线。本文拆解两种能力与传统 Copilot Autofix 的边界，解释为什么 AI Scan 只能提供 advisory signal、为什么 CodeQL 重跑仍不是完整验证，再用一个模拟漏洞修复流程设计预算、回滚和人工合并门槛。

### 结构提纲

1. 从一个 CodeQL 未覆盖语言的 PR 开始，区分“发现风险”和“证明修复有效”两种任务。
2. 拆 AI Scan 的触发条件、代码搜索上下文、advisory 结果和 AI credits 计费边界。
3. 跟进 Agentic Autofix 的跨文件探索、修改、CodeQL 重跑、迭代和 draft PR 产物。
4. 对照单次 Copilot Autofix，说明何时需要 Agent session，何时只要一个建议补丁。
5. 设计安全流水线的 merge gate、人工复核、Actions 预算、失败回滚和审计字段。

### 写作所需证据

已掌握：GitHub Changelog、官方文档中 AI Scan 的触发与限制、Agentic Autofix 的验证和权限/计费边界。
需要补做：用一个公开易复现的漏洞仓库构造 PR，分别跑 CodeQL、AI Scan（若账号可用）和本地模拟 Agent 修复；若无法调用 GitHub 服务，只保留 API/状态机设计，不能声称跑过官方功能。
配图：检测→Agent 修复→CodeQL 重跑→draft PR 的流程图、三种 Autofix 能力对照表、预算与人工门槛状态机。
未验证点：不同语言的覆盖差异、CodeQL 重跑对真实修复的漏检、批量 25 告警的并发和失败隔离。

## 4. 模型会退役，Agent 不能跟着失忆：GitHub Copilot 下线公告后的兼容层设计

**事件日期：** 2026-10-15（原文发布日期）

**材料状态：** GitHub 官方下线公告与模型支持文档；11 月 16 日下线日期和建议替代模型已明确，但替代模型的工具调用、输出格式、速度、价格与原模型的任务等价性没有由公告保证。

### 热点是什么

GitHub 在 10 月 15 日宣布，Copilot Chat、inline edits、ask/agent modes 和 code completions 将于 11 月 16 日下线 Claude Opus 4.8、Claude Opus 5 和 GPT-5.6 Terra，并建议迁移到 Claude Opus 5.5、GPT-6.1 Sol 或 GPT-6 Luna。支持模型文档同时提醒可用性会变化，并列出 fallback/LTS、客户端版本和不同能力窗口。

原始材料：
- [https://github.blog/changelog/2026-10-15-upcoming-deprecation-of-selected-github-copilot-models-in-mid-november/](https://github.blog/changelog/2026-10-15-upcoming-deprecation-of-selected-github-copilot-models-in-mid-november/)
- [https://docs.github.com/en/copilot/reference/ai-models/supported-models](https://docs.github.com/en/copilot/reference/ai-models/supported-models)

### 为什么值得写

模型下线对 Agent 团队的影响不是换一个下拉选项，而是工具调用协议、上下文长度、推理级别、延迟、成本和拒答行为都会改变。这个题目适合从“模型是基础设施依赖”切入，给出模型别名、能力合同、回归样本、fallback 和灰度切换的工程方案。文章不判断替代模型一定更好，而是把迁移风险拆成可测试的接口和行为。

### 建议标题

模型会退役，Agent 不能跟着失忆：GitHub Copilot 下线公告后的兼容层设计

### 文章梗概

当模型在 Agent 运行中被下线，真正坏掉的可能不是回答质量，而是工具参数、上下文预算、推理级别、延迟和拒答行为。GitHub 已通知 11 月 16 日退役三款 Copilot 模型，并给出替代项。本文把公告还原成一次工程迁移：如何定义模型能力合同、建立工具调用回归集、用 fallback 和灰度流量控制风险，再说明哪些差异必须由业务结果验证，不能只看模型名称。

### 结构提纲

1. 列出一个编码 Agent 对模型的隐含依赖：工具 schema、上下文、终止条件、成本和人工接管。
2. 从 GitHub 的退役与建议替代表出发，区分模型可用性、客户端版本和企业策略三种变更。
3. 设计模型能力合同与回归集，覆盖 JSON 参数、工具选择、长上下文、失败重试和安全拒答。
4. 比较 fallback、双跑、灰度切换和硬切换的风险，说明如何用任务结果而非主观体感判定迁移。
5. 收尾到组织流程：把模型生命周期、预算、审计和回滚写进 Agent 的发布检查单。

### 写作所需证据

已掌握：GitHub 下线 Changelog、支持模型表、fallback/LTS、客户端和能力窗口说明。
需要补做：从现有 Agent 代码中抽取模型能力合同，准备一组工具调用、结构化输出、长上下文和拒答回归样本；真实替代模型调用条件不足时，先做协议级 mock，不能伪造迁移成功率。
配图：模型路由与 fallback 架构图、一次迁移的双跑/灰度时序图、能力合同到回归结果的矩阵。
未验证点：替代模型在真实仓库任务上的行为差异、Copilot 各客户端切换时间、模型下线后历史会话的可重放性。
