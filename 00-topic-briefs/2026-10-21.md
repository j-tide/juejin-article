## 选题一：只看最后答案会漏掉什么？拆 FairStress 如何测量大模型的“决策抗压性”

### 热点是什么

Allen Institute 在 2026-10-20 发布 FairStress，目标是把 LLM 的公平性评测从“最后选了谁”推进到“证据相同、身份线索变化或受到同类劝说时，模型会不会对不同群体表现出不同的坚持程度”。项目提供技术报告、数据和代码，并计划接入 Olmo-eval。完整基准包含 300 个双候选决策场景、29 个高风险领域、33 组身份对比和 78 组对抗性前缀，组合后超过 1300 万个测试样例；另有约 5 万条的 FairStress-Core 供低成本评测。

官方报告考察了输出、抗对抗前缀、解释和激活四个层次。其作者在 15 个模型上的结果显示，身份线索变得更明显后，模型在“被一句话说服而放弃原本有充分证据的选择”上出现不对称；这属于作者自己的实验发现，尚无独立复测。FairStress 采用的是强调对称性的公平定义，也不等同于所有政策或伦理语境下的公平。

原始资料：

- [FairStress 官方介绍（2026-10-20）](https://huggingface.co/blog/allenai/fairstress)
- [技术报告：Asymmetrically Unfair Decision Making and Reasoning in LLMs](https://allenai.org/papers/fairstress)
- [FairStress 数据集](https://huggingface.co/datasets/allenai/fairstress) · [评测代码](https://github.com/pardissz/fairstress)

### 为什么值得写

很多团队的离线评测只比较最终标签或选择率，但客服、信贷、招聘和审核类 Agent 还会经历追问、申诉和工具调用。一个模型可能在第一轮给出相同答案，却在“领导更看好候选人 B”“这个群体过去被忽视”等相同结构的说服语句下，对不同身份的候选人表现出不同的翻转概率。这个切口能把公平性变成可观测的决策过程：不仅测结果，还测鲁棒性、提示敏感度和解释是否跟着身份线索变化。工程上可以把它接到回归集和发布门禁里，但需要先确认场景、身份定义和公平指标是否适合自己的业务。

### 建议标题

**只看最后答案会漏掉什么？拆 FairStress 如何测量大模型的“决策抗压性”**

### 文章梗概（约 200 字）

某个客服 Agent 给两位客户同样的退款结论，看起来已经“公平”；但只要换一种身份线索，再加一句同样强度的劝说，它可能更容易推翻其中一人的结论。文章从 FairStress 的 300 个场景、身份信号和成对对抗前缀入手，复算 Accuracy Gap、Robustness Gap、Tie-Break Lean 与 Tie-Break Shift 四类指标，再对照只看最终答案的传统评测。重点解释“公平”到底被定义成什么、哪些指标能进入 CI、哪些结果仍只是项目方实验，并给出一套小规模回归集和人工复核流程。

### 结构提纲

1. **从相同答案到相同坚持程度**：用一个两候选人的决策例子说明输出公平为什么遮住过程差异。
2. **FairStress 怎样造出可对照的样例**：拆解身份信号、明确优势/模糊场景、成对对抗前缀和四个维度。
3. **四个指标分别在测什么**：把准确率差、抗压差、平局偏好和翻转差写成可执行的评分函数。
4. **作者的结果与方法边界**：核对模型、领域和数据规模，区分报告结果、规范性选择与独立验证缺口。
5. **落到工程流水线**：设计 50K 子集的抽样、模型版本固定、拒答/翻转率记录、阈值告警和人工复核。

### 写作所需证据

- 已有：官方博客、70 页技术报告、数据集卡和 MIT 代码仓库；仓库还给出四个指标的定义和运行目录。
- 需要补做：先在 FairStress-Core 上跑一个开源模型，固定温度、解码、提示模板和随机种子，再对比没有身份线索、隐含线索、显式标签三组结果；不要把一次本地跑分写成普遍结论。
- 配图建议：一张“四层公平性”矩阵（输出、抗压、解释、激活），一张成对样例的翻转流程图，以及一张从数据生成到 CI 阈值告警的评测流水线图。
- 关键未验证点：中文场景和本地模型是否复现同样的方向；对抗前缀是否代表真实客服对话；指标变化和真实人工决策质量之间的相关性如何。

## 选题二：Agent 变聪明，先别急着微调：拆 ALTK-Evolve 的轨迹记忆与 Pass^4

### 热点是什么

IBM Research 在 2026-10-20 发布 ALTK-Evolve 的客服实验，展示一种不更新模型权重的“在岗学习”：先让基础 ReAct Agent 在 τ²-bench 的训练任务里工作，再用同一个模型把成功和失败轨迹提炼成带支持次数的行为准则，最后把准则追加到系统提示词里。τ²-bench 的任务包含客户、工具、业务政策和最终数据库状态，退款、改地址等副作用必须真正落到正确的状态。

在作者的实验设置中，Agent 用 GPT-4.1，客户模拟器用 GPT-5.5，每个任务跑 4 次；零记忆基线、支持数至少为 3 的 `sup3`、以及保留全部准则的 `lossless` 分开评估。作者报告的零记忆零售测试集 Pass^4 为 57.5%，`lossless` 为 67.5%；航空测试集则是 35.0% 对 40.0%，说明“记得越多越好”并不成立。报告还测了 GPT-5.5、提示词成本和对话轮数。这些数字来自 IBM 的自有运行和 2026-10-12 的排行榜快照，不是独立复测。

原始资料：

- [ALTK-Evolve 客服实验（2026-10-20）](https://huggingface.co/blog/ibm-research/altk-evolve-bc)
- [ALTK-Evolve 开源仓库](https://github.com/AgentToolkit/altk-evolve)
- [τ²-bench 基准与工具环境](https://github.com/sierra-research/tau2-bench)

### 为什么值得写

很多“记忆”实现只是把旧对话重新塞回上下文，Agent 读过一遍，下一次仍然会犯同样的错。ALTK-Evolve 把轨迹改写成可检索的操作准则，并用支持次数控制哪些规则更可信，正好对应工单系统里“成功处理过的案例如何变成下一次的排查习惯”。这个方案的价值不在一个榜单数字，而在于它把自进化拆成可审计的回路：轨迹、规则、检索、注入和回滚都能单独观察。文章还可以讨论为什么零售适合全量准则、航空却更适合小核心，以及提示成本、规则污染和测试集泄漏如何控制。

### 建议标题

**Agent 变聪明，先别急着微调：拆 ALTK-Evolve 的轨迹记忆与 Pass^4**

### 文章梗概（约 210 字）

客服 Agent 第一次把退货流程走通，并不代表下一位客户也能稳定成功。文章把 ALTK-Evolve 放回 τ²-bench 的真实约束里，沿着“轨迹采集—规则提炼—支持次数—检索注入—四次重复执行”的链路，解释为什么 Pass^4 比平均成功率更接近用户感受。重点复核零售和航空两个域的差异：全量准则在零售更有效，小核心在航空更稳；收益来自输入提示变长，而不是对话轮数增加。最后把这种回路映射到工单 Agent，补上规则版本、来源任务、冲突解决、灰度启用和错误经验撤销，并明确作者自测与本地复现实验的边界。

### 结构提纲

1. **“成功一次”为什么不等于可靠**：用四次独立执行区分 Mean Accuracy、Pass^4 和偶然成功。
2. **一条轨迹怎样变成行为准则**：跟读 ALTK-Evolve 的提炼、支持计数和冲突合并流程。
3. **准则放多少才合适**：对照 `sup3`、`lossless` 在零售和航空上的表现、成本与轮数。
4. **它真的在学习吗**：区分提示层记忆、权重更新、训练/测试隔离和项目方排行榜对比。
5. **迁移到工单系统的安全回路**：设计规则 provenance、有效期、冲突检测、灰度和一键回滚。

### 写作所需证据

- 已有：Hugging Face/IBM 实验文章、开源仓库、τ²-bench 仓库及可读的指标表；仓库 README 还给出 MCP、向量存储、冲突解决和 OpenTelemetry 接口。
- 需要补做：在不调用外部模型的情况下先阅读 `save_trajectory`、规则检索和支持计数实现；有模型条件后再固定同一任务集跑基线、`sup3`、`lossless`，报告 Mean Accuracy、Pass^4、输入 token 和回合数。
- 配图建议：轨迹到规则的反馈环、规则支持次数与检索剂量的决策图、工单 Agent 的“经验候选—审核—灰度—回滚”状态图。
- 关键未验证点：规则提炼是否会把偶然成功固化成错误经验；不同模型、语言和业务政策下的最优支持阈值；提示缓存能否抵消生产输入成本。

## 选题三：Mac 上的本地推理为什么突然快了？读 PyTorch 2.15 MPS 的 Metal 内核迁移

### 热点是什么

Hugging Face 的 PyTorch 团队在 2026-10-20 发布《MPS in PyTorch 2.15》，总结他们用真实语言、图像和视频模型寻找 MPS 短板，并将越来越多算子从 MPSGraph 迁移到专用 Metal kernel 的工作。文章目前仍以 release candidate 形式邀请试用，要求 macOS 15+、Python 3.11+，不能当成已经完成的最终版本。

项目方给出的变化包括：MPS 支持 FP8；在 M3 Ultra、`torch.compile` 和指定模型上，Qwen3.6-35B-A3B 的解码从 9.4 提升到 61.3 tokens/s；词表维度的 softmax 约快 8 倍；Wan2.2 视频 VAE 解码的驱动内存峰值从约 270 GiB 降到约 8 GiB；同时增加 MPS stream 和更多线性代数/卷积算子。数字都是团队自己的硬件和模型组合测试，文章没有承诺每个模型都会得到相同增益。

原始资料：

- [MPS in PyTorch 2.15（2026-10-20）](https://huggingface.co/blog/mps-pytorch-2-15)
- [PyTorch MPS backend 源码](https://github.com/pytorch/pytorch/tree/main/aten/src/ATen/mps)
- [PyTorch MPS 使用说明](https://pytorch.org/docs/stable/notes/mps.html)

### 为什么值得写

“Mac 能不能跑本地模型”常被简化成显存和参数量问题，实际瓶颈经常出现在一个算子走了错误后端、CPU/GPU 同步过多或内存分配路径失控。MPS 2.15 的材料恰好能从一个真实 decode step 追到 `F.linear`、grouped matmul、softmax、padding 和 stream，解释为什么“同一个模型、同一块芯片”会因为后端实现变化而出现数量级差异。文章也能给本地开发者一套判断方法：看算子覆盖、graph break、driver memory 和端到端 token/s，而不是只看单个 kernel。

### 建议标题

**Mac 上的本地推理为什么突然快了？读 PyTorch 2.15 MPS 的 Metal 内核迁移**

### 文章梗概（约 200 字）

同一台 Mac、同一个模型，升级 PyTorch 后速度可能从“能跑”变成“值得跑”，原因往往是关键算子终于绕开了 MPSGraph。文章从 decode 的 `F.linear`、MoE grouped matmul 追到 softmax、padding、FP8 和 MPS stream，再用 Wan2.2 的内存案例解释驱动分配。文中标出 2.15 仍是 release candidate，不把官方 M3 Ultra 数据当成普遍收益，最后给出包含模型、上下文、编译方式、吞吐和峰值内存的复测清单。

### 结构提纲

1. **先拆 decode 的真实热路径**：说明 prefill 与 decode 的形状差异，为什么单行矩阵乘法决定每个 token 的延迟。
2. **从 MPSGraph 到 Metal kernel**：对比 `F.linear`、grouped matmul 和 softmax 的旧路径、新路径与同步点。
3. **性能之外的内存与正确性**：解释 padding 导致的 driver-memory 峰值，以及 Qwen-Image 编解码修复如何被 PSNR 发现。
4. **把官方数字变成可复验实验**：固定硬件、版本、模型、上下文、`torch.compile` 和采样策略，分别测 token/s、首 token、峰值内存和 graph break。
5. **适用边界**：列出 MPS 仍可能回退、算子覆盖不完整和 release candidate 变化的地方。

### 写作所需证据

- 已有：官方团队文章给出算子级解释、版本要求、示例代码和具体测量；PyTorch 源码与 MPS 文档可用于追实现。
- 需要补做：在可用的 Apple Silicon 机器上跑一个小模型和一个 MoE 模型的 2.14/2.15 对照；若没有同型号硬件，文章只能保留实验计划，不能声称复现 5—6.5 倍。
- 配图建议：一张 token decode 的调用链（Python → ATen → MPSGraph/Metal → GPU），一张 MPSGraph 到 Metal 的迁移前后时序图，以及一张 driver memory 峰值对比图。
- 关键未验证点：不同 macOS、芯片和 nightly/RC 版本的差异；`torch.compile` 的 graph break 对端到端结果的影响；FP8 的精度/兼容性在常用模型上的实际收益。

## 选题四：大模型 API 统一之后，iPhone 上的 Agent 真能随时换模型吗？拆 AnyLanguageModel 1.0

### 热点是什么

Hugging Face 在 2026-10-20 发布 AnyLanguageModel 1.0 的年度更新；GitHub 的 1.0.0 release tag 建立于 2026-10-13。它把 Apple Foundation Models 风格的会话 API扩展到本地和托管模型：同一套 Swift 会话代码可以切换系统模型、llama.cpp、MLX、Core ML，以及 OpenAI、Anthropic、Gemini、Ollama、Private Cloud Compute 和 Hugging Face Inference Providers。文章称 tool calling、guided generation（含嵌套 `@Generable`）和图像输入已对所有 provider 提供统一接口，并配套发布 `swift-huggingface` 与 `swift-xet` 1.0。

这不是“所有模型行为完全一致”的承诺。不同 provider 的上下文限制、工具协议、结构化输出约束、推理块和流式语义仍可能不同；1.0 release notes 也列出 `JSONValue` 和 `@Generable` 枚举编码等 breaking changes。文章给出的能力矩阵和迁移指南比单纯 SDK 宣传更适合拿来拆抽象边界。

原始资料：

- [AnyLanguageModel 1.0 官方介绍（2026-10-20）](https://huggingface.co/blog/anylanguagemodel-1-0)
- [AnyLanguageModel 1.0.0 Release Notes（2026-10-13）](https://github.com/huggingface/AnyLanguageModel/releases/tag/1.0.0)
- [AnyLanguageModel 源码仓库](https://github.com/huggingface/AnyLanguageModel)

### 为什么值得写

端侧 Agent 真正难的不是“把请求发出去”，而是让工具调用、结构化结果、流式输出、图片输入和凭证轮换在本地与云端之间保持可控。AnyLanguageModel 把 provider 差异压进适配层，为离线优先、隐私敏感和成本敏感的产品提供了切换空间，但也把“接口兼容”和“语义等价”分开了。这个题目适合从源码协议层读到应用层，提醒开发者把能力矩阵、失败降级和密钥生命周期写进产品设计，而不是只换一个 import。

### 建议标题

**大模型 API 统一之后，iPhone 上的 Agent 真能随时换模型吗？拆 AnyLanguageModel 1.0**

### 文章梗概（约 200 字）

把 `import FoundationModels` 换成 `import AnyLanguageModel`，端侧 Agent 就能在系统、本地开源和云端模型间切换。文章沿一段带工具调用和结构化输出的 Swift 会话，拆 1.0 如何做协议适配、流式转译、图片输入和 provider 选择，再用 release notes 的 breaking changes 说明兼容 API 不等于兼容行为。最后给出端侧—云端降级策略：会话状态、reasoning block、短期 token 和能力矩阵怎样设计，才能验证切换没有改变业务语义。

### 结构提纲

1. **一个 import 后面藏了多少协议**：从会话、消息、工具和生成约束四个接口看抽象边界。
2. **本地与云端怎样被适配到同一条链**：沿 provider adapter、流式事件和结构化输出解析追调用路径。
3. **工具调用兼容不等于结果兼容**：对比 schema、错误、重试、推理块、图像输入和上下文限制。
4. **端侧—云端切换的状态与凭证**：设计短期令牌、会话恢复、脱网缓存和降级时的幂等边界。
5. **用能力矩阵而不是口号验收**：为每个 provider 建立工具、结构化输出、图片、流式和取消操作的回归用例。

### 写作所需证据

- 已有：HF 1.0 介绍、GitHub release notes、源码仓库和 Foundation Models 风格的公开 API 形态。
- 需要补做：读 provider adapter 和 `LanguageModel` 协议，写一个最小 Swift sample，至少在一个本地 provider 与一个 OpenAI-compatible provider 上验证工具调用和 structured output；没有可用 Apple 环境时只写代码阅读与实验计划。
- 配图建议：provider 适配层架构图、一次工具调用的跨 provider 事件时序图、离线/在线切换的状态机图。
- 关键未验证点：各 provider 的 JSON schema 约束是否真的等价；reasoning blocks 在切换时丢弃后的上下文影响；短期 token、代理转发和本地模型下载的安全成本。

## 选题五：看起来像手术，能拿来训练机器人吗？拆 Cosmos3-H-Dreams 的动作条件生成与闭环验证

### 热点是什么

NVIDIA 在 Hugging Face 于 2026-10-20 发布 Cosmos3-H-Dreams，目标是把临床胆囊切除手术中的视频和机器人运动轨迹变成可交互的生成式仿真器。项目以 Cosmos3-H-Embodied-Nano（16B）为基础，使用 832×480、10 Hz 的视频与动作对齐数据，支持 28 个动作维度；通过双向 teacher、因果 student、Self-Forcing 和 FlashDreams 流式推理，提供四步和两步去噪 checkpoint，并声称可在单张 RTX PRO 6000 上交互运行。

这类系统的关键不只是生成“像真的”画面。动作必须改变器械、组织和遮挡的后续状态，长时间 rollout 还要处理误差累积与 KV cache 增长。项目明确把自己定位为研究模拟器，尚未通过临床验证，也不能用于患者护理。

### 为什么值得写

生成式世界模型从桌面缝合任务走到真实临床视频，最值得讨论的不是“画面更逼真”，而是它把 Agent/机器人训练中的环境建模改成了动作条件的视频预测。开发者可以借这个案例看清 teacher-to-student 蒸馏、Self-Forcing、两步/四步采样和缓存压缩各自解决什么问题，也能看到验证标准必须从视觉相似度扩展到动作响应、时序一致性和控制闭环。它适合写成一篇有技术细节、又能明确告诉读者哪些结论尚未成立的多模态工程分析。

### 建议标题

**看起来像手术，能拿来训练机器人吗？拆 Cosmos3-H-Dreams 的动作条件生成与闭环验证**

### 文章梗概（约 210 字）

如果模拟器只会生成逼真的手术画面，却不响应夹持器指令，它就不能训练机器人。文章从 Cosmos3-H-Dreams 的 28 维动作、832×480/10 Hz 数据和胆囊切除场景开始，沿 teacher、causal student、Self-Forcing 与 FlashDreams 的闭环，解释速度、画质和长程稳定性的取舍。随后设计动作响应、器械/组织时序、长 rollout 漂移和跨轨迹泛化测试，而不是只看截图，并明确单卡交互是项目方披露，系统仍不是临床能力。

### 结构提纲

1. **从桌面任务到体内场景**：说明遮挡、组织变形和烟雾为什么让动作条件生成更难。
2. **数据与动作接口**：拆 28 维动作、视频—运动对齐、10 Hz 采样和只保留两件器械的取舍。
3. **Teacher、Student 与 Self-Forcing**：解释长视野训练、因果生成和自生成上下文如何应对误差累积。
4. **两步/四步与 FlashDreams**：把去噪步数、质量、延迟和 KV cache 合并到一张运行时图里。
5. **怎样验证它真的“受控”**：给出动作跟随、时序一致性、长 rollout 和专家评审的实验矩阵，说明临床边界。

### 写作所需证据

- 已有：NVIDIA/HF 官方文章、GitHub 代码、模型卡、Open-H-Embodiment 数据入口和 FlashDreams 仓库。
- 需要补做：先读 teacher fine-tuning 与 Self-Forcing recipe，再用公开 checkpoint 做短 rollout，记录显存、延迟和动作改变前后的视频差异；没有 RTX PRO 6000 时只能引用官方环境并说明未复跑。
- 配图建议：视频帧+动作向量进入模型的闭环架构图，teacher→student→Self-Forcing 的训练流程图，以及“生成质量—控制响应—长程漂移”的三轴验证图。
- 关键未验证点：对未见器械/轨迹的泛化；生成画面与真实组织动力学的偏差；两步模型在控制精度上的具体损失；专家评分与机器人策略成功率的关系。
