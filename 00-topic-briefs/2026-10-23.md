## 1. Agent 不该每一步都用完整模型：拆 OpenAI Decisions API 的“窄决策”路径

### 热点是什么

OpenAI 在 **2026 年 10 月 22 日**发布《Build more responsive apps with the Decisions API》，宣布 Decisions API 正式 GA。它把 Agent 流程中大量“答案范围有限”的判断单独抽出来：开发者给出问题、上下文和允许的答案，服务返回 predicate probability、choice 或 score，而不是生成一段完整文本。官方文章称它基于 GPT-6 Luna，相比通过 Responses API 使用 GPT-6 Luna “最高可快 10 倍”；这是厂商自己的性能表述，不能替代同任务、同区域、同并发的独立压测。

当前 API 支持文本、图片和原生 JSON 输入，单次请求最多 400 个问题，可使用提示缓存，并能通过 GPT-Live 在通话过程中触发决策。官方给出的价格是每百万输入 token 0.10 美元，缓存输入每百万 0.01 美元，且不收输出 token 费用。开发者文档的请求入口是 `POST /v1/decisions`。

原始材料：

- [OpenAI：Build more responsive apps with the Decisions API（2026-10-22）](https://openai.com/index/decisions-api/)
- [OpenAI API 文档：Decisions](https://developers.openai.com/api/docs/guides/decisions)
- [OpenAI API Changelog：2026-10-22 GA 更新](https://developers.openai.com/api/docs/changelog)

### 为什么值得写

事实层面，OpenAI 把“调用模型后再解析文本”改成了有边界的决策接口，给了 Agent 一个更明确的控制点：继续、重试、追问、升级人工、选择工具都可以先变成 `choice`，而不是依赖字符串解析。价格也把“短输出的固定决策”从普通文本生成账单里单独拿出来。

我的判断是，真正值得拆的不是“一个新 endpoint”，而是决策边界的重新划分。把步骤改成 choice 并不会自动提高准确率，反而会把问题暴露为：选项是否穷尽？低置信度怎么处理？同一上下文是否会因缓存失效出现分叉？如果企业 Agent 把所有中间判断都改成窄接口，观测、回放和降级会更清晰；但如果把开放式调查误塞进固定选项，模型只是更快地做出一个错误选择。

### 建议标题

**Agent 不该每一步都用完整模型：拆 OpenAI Decisions API 的“窄决策”路径**

### 文章梗概

一个客服 Agent 判断“继续查订单、追问门店，还是转人工”，真的需要生成一段完整回答吗？OpenAI 的 Decisions API 把这类判断压成概率、枚举选择和有序评分，试图让 Agent 的控制流变得更快、更便宜，也更容易观测。文章从一个工单路由流程开始，对照 Responses API 的文本解析和 Decisions API 的结构化返回，拆解 predicate、choice、score 三种语义，说明置信度、提示缓存、400 问题批量请求如何影响延迟和成本。最后给出哪些判断适合窄化、哪些仍应交给完整模型，以及低置信度时如何回退到追问或人工。

### 结构提纲

1. **先把“模型回答”拆成“程序要做的选择”**：以客服工单路由为例，画出完整生成、文本解析和窄决策三条执行链，明确每一步的输入、输出和失败方式。
2. **predicate、choice、score 分别承诺了什么**：从返回结构和概率含义出发，区分真假判断、互斥选项和有序等级，避免把概率误当成校准后的置信度。
3. **速度和价格从哪里来**：按输入 token、缓存命中、问题数量和并发量建立成本模型，并设计同任务对照来验证“10 倍更快”是否适用于自己的区域和负载。
4. **固定选项会不会把未知强行塞进已知**：讨论开放世界问题、选项覆盖率、低置信度和 `other`/`ask` 分支，给出安全的回退策略。
5. **把窄决策接回 Agent Harness**：展示如何记录 question id、模型版本、概率、实际动作和后续结果，让决策可以回放、评测和审计。

### 写作所需证据

- **已有材料**：OpenAI 官方发布、开发者文档和 API Changelog 已说明 GA 状态、输入类型、问题上限、三类 answer type、缓存和价格；官方客户案例中的 40 倍、3 倍和 90% 等数字属于客户/厂商自报，正文需要单独标记。
- **需要补做的源码或接口阅读**：阅读 Decisions 的请求/响应 schema、错误码、流式事件和 GPT-Live 集成；重点确认概率字段是否有校准保证、批量问题之间是否共享上下文以及超限时的错误语义。
- **建议实验与图**：用同一批客服路由样本分别调用 Responses 和 Decisions，记录 p50/p95、token、缓存命中和低置信度回退；配一张“完整生成→解析”和“窄决策→控制流”的架构对照图。
- **未验证点**：官方“最高 10 倍”是上限表述，尚无本地环境的独立结果；还需确认图片/JSON 输入下的延迟、不同服务区域的差异，以及固定选项改变后是否需要重新建立评测基线。

## 2. 几千个 Agent 一起读生物数据，为什么单 Agent 做不到？拆分布式科学推理

### 热点是什么

OpenAI 在 **2026 年 10 月 21 日**发布《Using thousands of AI agents to uncover new leads in biological data》，介绍 OpenAI、PerturbAI 和 Scripps Research 用 GPT-Rosalind Agent 并行分析数百万小鼠脑细胞的全脑 CRISPR atlas。流程把每个基因扰动分配给独立 Agent：阅读细胞反应、检索文献、提出解释，再把报告合并为 reasoning atlas。项目方称整个分析在 32 分钟内完成，并发现了可供后续实验验证的生物学线索。

文章还报告了一个很适合工程分析的对照：在模型和资源固定的条件下，单 Agent 在最大工作量下引用 11 篇文献，分布式 Agent 汇总后超过 700 篇；盲评中人类专家 75% 的时间更偏好分布式报告。这些数字来自项目方与合作研究者的实验，不是独立第三方复测，也不能直接推出“Agent 越多越聪明”。

原始材料：

- [OpenAI：Using thousands of AI agents to uncover new leads in biological data（2026-10-21）](https://openai.com/index/scaling-ai-research-for-complex-biological-data/)
- [GitHub：Distributed Agents 代码与数据处理框架](https://github.com/jinlabneurogenomics/distributed_agent)
- [项目仓库中引用的 bioRxiv 预印本信息](https://doi.org/10.64898/2026.10.15.759436)

### 为什么值得写

事实层面，这个项目把“多 Agent”落成了一个可读的分工协议：任务按扰动切片，单个 Agent 负责局部证据，汇总层负责跨报告的关联和排序，最后把候选机制交给人类实验者。公开仓库还包含运行时、语料库工具、结果和论文分析脚本，读者可以从目录结构而不是宣传图开始读。

我的判断是，单 Agent 和分布式 Agent 的差别不只是并发数。单 Agent 面对大数据集时必须决定先看什么，容易在一个叙事里过早收敛；分布式方案把“覆盖面”交给调度器，把“相关性”交给汇总器，但也新增了重复检索、证据冲突、引用质量和预算失控的问题。文章最值得回答的是：哪些维度适合切片，怎样定义报告契约，汇总层如何防止多数 Agent 一起复读同一个错误。

### 建议标题

**几千个 Agent 一起读生物数据，为什么单 Agent 做不到？拆分布式科学推理**

### 文章梗概

在一个包含数千个基因扰动、数百万细胞和大量论文的实验里，把全部数据塞给一个 Agent，问题不是上下文够不够长，而是它必须自己决定先看哪些线索。OpenAI、PerturbAI 和 Scripps Research 的分布式生物推理项目把任务按扰动拆开，让多个 Agent 分头查文献、解释细胞变化，再由汇总层建立 reasoning atlas。文章沿公开仓库追踪任务切片、工具调用、报告格式和跨报告合并，解释为什么分布式方法扩大了检索覆盖，也带来重复、冲突和成本控制问题。最后把这种架构映射到代码审查、工单排查等场景，给出何时并行、何时保持单 Agent 的边界。

### 结构提纲

1. **数据大不等于上下文要更长**：用“基因扰动→细胞反应→文献证据”的任务图说明单 Agent 在覆盖面和早期收敛上的瓶颈。
2. **公开仓库里如何切片与派工**：沿 `src/`、脚本和运行目录追踪一个扰动从输入到报告的生命周期，列出 Agent 的最小任务契约。
3. **报告怎样从“文字”变成“可合并证据”**：设计引用、实体、假设、置信度和待验证实验字段，说明汇总层如何处理重复和矛盾。
4. **并行度的收益与账单**：对照单 Agent、固定并发和按难度自适应并发，分别统计覆盖率、引用去重率、延迟、模型调用量和失败重试。
5. **从科学发现迁移到工程排查**：把同样的分工映射到工单、代码和日志调查，明确哪些任务可独立、哪些必须共享状态或串行确认。

### 写作所需证据

- **已有材料**：OpenAI 文章、公开 GitHub 仓库、MIT 许可和仓库中的本地运行说明；文章给出 32 分钟、700 对 11 篇引用和 75% 偏好等结果，但这些均应标为项目方实验。
- **需要补做的源码阅读**：阅读任务分发、文献检索、报告 schema、汇总/排名脚本和 `runs/` 里的保存产物；核对 hosted MCP 与本地运行的能力差异。
- **建议实验与图**：用公开仓库的小型 corpus 做 1/4/16 个 Agent 的固定预算回放，画“调度器—局部 Agent—证据报告—汇总器—人类复核”的泳道图，并增加证据冲突和重复引用的故障样本。
- **未验证点**：完整论文数据和模型调用成本较大，不能承诺本地复现 32 分钟；还需确认分布式报告的优势来自覆盖、并行还是提示/检索差异，避免把项目方的相关性结果写成因果结论。

## 3. 语音 Agent 听错一个名字就全盘失败：拆 τ-Entity 与 τ-i18n 的评测设计

### 热点是什么

Sierra 在 **2026 年 10 月 21 日**发布 τ-i18n，在 **10 月 22 日**发布 τ-Entity。τ-i18n 把原有语音 Agent 任务扩展到西班牙语、巴西葡萄牙语、印地语、韩语和普通话，保持航空、零售、电信任务、工具和成功标准不变，同时增加交互质量和生成质量指标。项目方称 2,700 次主调用覆盖了六种语言，并把轮次响应、selectivity、工具效率、自然度和 speech fidelity 分开报告。

τ-Entity 则把一个更容易被忽略的细节单独拿出来测：Agent 是否能正确记录姓名、电话、地址和邮箱。基准有 200 个任务、10 类实体，变量包括值本身的难度、用户修正/重启和音频环境；Pass³ 要求同一任务在普通、噪声和 speech-heavy 三种条件都成功。Sierra 的文章报告，GPT Live 1 在普通条件下 60.3%，Pass³ 34.0%；强制“询问—拼写/复述—确认—提交”流程能提高 14—31 个百分点，但多花 21—28 秒。数字来自 Sierra 的 benchmark 与论文，需保留其项目方来源属性。

原始材料：

- [Sierra：τ-i18n（2026-10-21）](https://sierra.ai/blog/tau-i18n)
- [Sierra：τ-Entity（2026-10-22）](https://sierra.ai/blog/tau-entity-can-voice-agents-get-the-details-right)
- [τ-Entity / τ-i18n 排行榜](https://taubench.com)

### 为什么值得写

事实层面，这组评测把“Agent 完成了任务”拆成了多个可追责的结果：最终状态是否正确、是否在恰当时间让出话轮、是否对嗯哼和背景声过度响应、工具参数是否正确、说出来的名字和数字是否保真。Pass³ 还把一次偶然成功与跨环境稳定成功区分开来。

我的判断是，语音 Agent 的难点已经从“能不能说话”转向“什么时候该停、是否听对、错了能否修复”。一个 75% 的单字段准确率，组合三个字段后可能只剩 53% 成功；验证流程提高成功率，却增加通话时长，不能简单地把“多问一次”当作万能方案。这个题目适合写成工程决策：哪些字段需要强验证，怎样根据噪声、实体难度和语言选择性触发校验，怎么把延迟预算和风险一起算进去。

### 建议标题

**语音 Agent 听错一个名字就全盘失败：拆 τ-Entity 与 τ-i18n 的评测设计**

### 文章梗概

“好的，我已经帮你改好了”并不代表电话 Agent 做对了：如果姓名、手机号或地址有一个字符错了，后续身份校验和订单操作都可能失败。Sierra 最近发布的 τ-Entity 和 τ-i18n，分别把实体捕获、跨噪声稳定性、多语言本地化和交互质量拆成独立指标。文章从一个客服录入电话的场景开始，重建 200 个实体任务、Pass³、三种音频条件和六语言评测，解释为什么单字段准确率会在多字段流程中快速下降。再对照强制复述策略带来的成功率和额外时长，给出“何时验证、验证什么、错了如何重试”的 Agent 设计，并说明排行榜数据仍需结合自己的通话、语言和工具链复测。

### 结构提纲

1. **先把“说得像人”换成“写入状态正确”**：从姓名、电话、地址字段进入业务数据库的链路出发，区分语音自然度、工具调用和最终状态。
2. **τ-Entity 如何构造可重复的失败**：解释 200 个任务、10 类实体、难度/修正/音频变量和 Pass³，说明为什么三条件交集比平均成功率更有工程价值。
3. **τ-i18n 测的不是翻译**：比较任务完成、话轮交互、工具效率、自然度和 speech fidelity，讨论姓氏顺序、敬语、数字读法等本地化规则如何影响 Agent。
4. **验证流程为什么有效又为什么慢**：复现“询问—拼写或复述—确认—提交”的状态机，计算 14—31 个百分点收益与 21—28 秒成本，分析哪些字段应强制验证。
5. **把评测接进生产回放**：设计通话转录、实体真值、工具参数、重试次数和人工接管的指标，制定语言/噪声/字段变化后的回归门槛。

### 写作所需证据

- **已有材料**：Sierra 两篇官方文章、公开排行榜和 τ-Voice/τ-Elicitation 论文入口；文章中的模型分数、验证收益、校正成功率和多字段结果都需标注为 Sierra/合作论文结果。
- **需要补做的源码或论文阅读**：打开 τ-Entity 关联的 τ-Elicitation 论文与排行榜配置，核对任务生成、音频扰动、实体真值比较、重试统计和模型版本；阅读 τ-i18n 的 LanguageFactory 代码，确认语言包到底覆盖哪些规则。
- **建议实验与图**：做一个本地文字/音频简化版状态机，分别模拟无校验、按难度校验和每字段校验，画“听取→规范化→复述→确认→提交→回滚”的流程图，并用三字段乘法展示误差累积。
- **未验证点**：项目方数字不等于特定企业电话链路的上线表现；需要补测中文方言、真实线路抖动、ASR 与 TTS 组合、工具超时和用户不合作时的策略，不能只根据排行榜选择模型。

## 4. Token 少了不等于便宜：拆 VocabX 如何把小模型推理成本降 77%

### 热点是什么

Dharma-AI 在 **2026 年 10 月 21 日**发布 VocabX 论文预览，文章明确说明论文仍在审稿中。团队以 Qwen3-4B 的葡萄牙语作文评分器为例，不改变基础模型、数据和训练配方，只改词表：一方面重建领域子词切分，另一方面把经常重复的长表达、JSON 结构和整行文本做成 macro token。它不是按出现频率选择 token，而是按输入/输出字段的成本加权；文章称在同一测试机、vLLM 和 RTX 5090 上，平均输出从 350 降到 101 token，测得推理成本下降 77.0%，bench score 从 0.703 升到 0.810，词表从约 152k 缩到 65k。

团队还披露，在其设置里，生成 token 的成本约是输入 token 的 7.4 倍；这解释了为什么同样节省一个 token，压缩输出比压缩输入更划算。文中结果来自 7 个模型版本和 500 次请求，作者明确写了“under review”“may change before publication”，不能把它当成已审论文或通用成本保证。

原始材料：

- [Dharma-AI：How Specializing the Vocabulary of SLMs Can Cut Inference Cost by 77%（2026-10-21）](https://huggingface.co/blog/Dharma-AI/vocabx-vocabulary-specialization)
- [In-Place Tokenizer Expansion（论文预印本）](https://arxiv.org/abs/2607.15232)
- [Hugging Face：VocabX 论文预览与方法对比](https://huggingface.co/blog/Dharma-AI/vocabx-vocabulary-specialization#why-existing-solutions-fell-short)

### 为什么值得写

事实层面，VocabX 把 tokenizer、输出格式和推理成本放到同一条优化链里：减少 token 数只是一部分，缩小输出层的候选词表也可能改变每一步 logits 计算；但宏 token 也可能把“结构”和“模型要做的判断”绑在一起，损害质量。团队自己给出了一个有意思的反例：把评分和周围 JSON 一起融合，分数下降到 0.689；把评分保留为独立 token，虽然多 2 个 token，bench score 反而升到 0.810。

我的判断是，文章最有价值的切口不是复述“77%”，而是讨论 Agent/小模型在固定输出 schema 下是否值得做词表专门化。优化目标应同时包含 token 数、解码吞吐、显存、质量和回滚成本；如果生产格式或领域发生变化，专门词表可能变成新的兼容性负担。

### 建议标题

**Token 少了不等于便宜：拆 VocabX 如何把小模型推理成本降 77%**

### 文章梗概

很多团队优化小模型时只看参数量和量化，却忽略了模型每次生成要切多少 token、每一步要在多大的词表上算 logits。Dharma-AI 的 VocabX 针对葡萄牙语作文评分器同时改造子词和重复 JSON 结构，并按输入/输出成本选择候选 token；项目方报告输出从 350 降到 101 token，推理成本下降 77%，质量分数反而提高。文章从 tokenizer、输出层和 vLLM 解码路径出发，解释为什么减少 token 不必然等于加速，也拆开“把评分和 JSON 绑成宏 token”导致质量下降的反例。最后给出在工单分类、结构化抽取和 Agent 工具回执中评估词表专门化的指标与边界。

### 结构提纲

1. **一次生成到底为哪些 token 付费**：画出输入切分、KV cache、logits 计算和采样路径，区分减少序列长度与缩小词表的收益。
2. **VocabX 的成本加权选择**：解释为什么输出 token 权重更高，子词 token 与 macro token 两层如何共享预算，避免把“高频”当成“高价值”。
3. **宏 token 绑错了决策会伤质量**：复述项目方融合评分与 JSON 的失败对照，说明压缩结构时必须保留模型需要决定的变量。
4. **从 500 次请求到生产指标**：设计同模型、同数据、同 seed 的质量/延迟/显存/成本实验，区分项目方测得成本与云端账单价格。
5. **什么时候值得专门化词表**：讨论单语言、固定 schema、高输出占比和稳定领域的适用范围，以及词表版本升级、回退和多语言输入的兼容成本。

### 写作所需证据

- **已有材料**：Dharma-AI 官方预览、引用的 FVT/MWT/in-place BPE 论文和文章中的七版本/500 请求设置；所有 77%、7.4 倍和 bench score 数字均为团队运行结果，且论文尚未正式发表。
- **需要补做的源码或论文阅读**：等待/查找 VocabX 完整论文和代码，核对 tokenizer 构建、macro token miner、词表裁剪、模型 embedding/lm_head 映射以及 vLLM 是否做了专门优化。
- **建议实验与图**：在一个固定 JSON 输出的小模型上比较原词表、仅子词、仅 macro token、两层同时改造，画“tokenizer→模型输入→logits→schema 校验”的流程图，记录 tok/s、显存、首 token 延迟和质量。
- **未验证点**：文章暂时只有作者预览，没有独立复现；需要确认缩小词表对不同硬件、batch、量化和流式输出的影响，也要测试领域词表失配时的降级行为。

## 5. 数据库不用先展平，也能直接做预测？拆 Kumo Relational 的表间推理

### 热点是什么

NVIDIA 在 **2026 年 10 月 21 日**通过 Hugging Face 发布 Kumo Relational 介绍和配套资料。它把关系数据库的表、外键和时间戳直接作为推理输入：开发者用 Predictive Query Language 描述要预测的对象，系统从历史状态生成最多 10,000 个上下文样本，再由预训练 Relational Foundation Model 做一次前向预测。项目方主张不需要任务特定训练、手工特征工程或先把多张表展平成一张宽表。

官方文章覆盖 41 个任务、15 个数据库，称模型在常见关系数据基准上超过监督式关系深度学习和人工设计的 GBDT 管线，在 SAP SALT 企业基准上比 AutoGluon 集成高 8% MRR；这些是 NVIDIA 项目评测。架构上，模型分别处理表内列/行、跨表图注意力和样本间注意力；上下文生成通过历史时间点回放避免目标泄漏。项目同时公开 `structured-data-models` 代码、模型权重和文档，宣称通过 mmap 支持 500B+ 行、最高 5 GB/s 的读取，这些吞吐数字也需要独立环境验证。

原始材料：

- [NVIDIA：Kumo Relational（2026-10-21）](https://huggingface.co/blog/nvidia/kumo-relational)
- [论文：Kumo Relational（arXiv:2604.12596）](https://arxiv.org/abs/2604.12596)
- [GitHub：NVIDIA structured-data-models](https://github.com/NVIDIA/structured-data-models)
- [官方文档：Relational Foundation Model](https://docs.nvidia.com/sdgm/rfm/overview)

### 为什么值得写

事实层面，Kumo Relational 把“让 Agent 查数据库”与“让模型直接预测关系数据”分开：前者解决查询和证据获取，后者尝试在表关系和时间变化上做 few-shot 预测。它没有要求读者先写一套用户、订单、商品的聚合特征，接口也能被 Agent 通过 PQL 调用。

我的判断是，真正的难点在于数据泄漏和上下文采样，而不是“模型能看表”。如果历史状态回放、目标时间点、外键跳数或样本边界处理错了，模型可能只是在读取未来信息；如果预测信号跨越太多表，few-shot 上下文也未必足够。项目方已经承认训练数据量很大时任务特定监督模型可能更强、有效信号需要限制在少量 hop 内，这正好提供了文章的适用边界。

### 建议标题

**数据库不用先展平，也能直接做预测？拆 Kumo Relational 的表间推理**

### 文章梗概

当订单、用户、商品和营销活动分散在多张表里时，传统机器学习通常先做一轮手工聚合，再训练一个任务模型；Kumo Relational 试图把这一步交给关系基础模型。NVIDIA 的方案直接读取表、外键和时间戳，用 PQL 描述预测问题，再从历史状态抽取最多 10,000 个上下文样本做一次前向推理。文章沿公开论文、代码和文档拆解上下文生成、表内注意力、跨表图注意力和时间防泄漏，重点分析它为什么适合被 Agent 调用，以及为何大规模监督数据、长 hop 关系和错误时间切片会改变结论。最后给出接入真实业务数据库前必须验证的泄漏、采样、延迟和可解释性清单。

### 结构提纲

1. **先看业务表为什么不能随手展平**：用用户—订单—商品—营销活动案例说明手工聚合丢失哪些关系和时间信息。
2. **一次 PQL 预测经过哪些步骤**：从预测实体、目标时间点、历史上下文采样到模型输入，画出数据不应穿越的时间边界。
3. **模型如何同时处理列、行、表和样本**：结合论文和代码解释表内注意力、跨表图注意力与 context-example attention 的分工。
4. **few-shot 关系推理与监督模型如何比较**：复核 41 个任务/15 个数据库的评测协议，区分项目方的 leaderboard 结果和自己能做的最小回放。
5. **接入生产数据库前的边界**：检查外键跳数、历史快照、隐私、连接器吞吐、预测延迟和模型版本，并设计 Agent 调用后的人工/规则兜底。

### 写作所需证据

- **已有材料**：NVIDIA 官方文章、论文、Apache 2 代码、OpenMDW 权重和文档；41/15、SAP SALT +8% MRR、500B 行和 5 GB/s 都应标为项目方材料。
- **需要补做的源码阅读**：阅读 PQL 解析、context generator、时间切片/防泄漏逻辑、不同 connector、mmap 读取和模型输入 schema；确认示例是否包含真实外键边界和缺失值处理。
- **建议实验与图**：用一个小型订单数据库构造“未来泄漏”和“正确历史回放”两种 pipeline，比较 PQL、手工聚合 GBDT 和固定上下文预测；配一张表关系→上下文子图→模型层→预测结果的架构图。
- **未验证点**：当前没有本地 GPU/大数据库条件，不能声称复现项目吞吐；需要核对训练数据规模、企业表结构变化、长 hop 关系和少数类/回归任务上的稳定性，也要评估 Agent 生成 PQL 时的权限边界。
