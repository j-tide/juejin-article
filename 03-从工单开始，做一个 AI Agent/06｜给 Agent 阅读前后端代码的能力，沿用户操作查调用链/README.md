# 给 Agent 阅读前后端代码的能力，沿用户操作查调用链

*开头与结尾草稿。人物、工单及 Demo 情节为虚构示例；结尾待实现验证后定稿。*

## 开头

阿杰把录屏停在“价格已更新”出现的那一刻。

“这个提示我见过，结算页处理报价变化的时候会弹。”

他找到一段前端代码，贴进话题。老周顺着接口名查后端，又问了一句：“门店现在用的是哪个版本？”

品牌运营给出的信息是，部分门店刚参加一轮功能灰度。阿杰打开的主分支已经改过一次结算逻辑，而录屏里的页面是否用了这段实现，还没有确认。

这时候，只让 Agent 总结视频和搜索知识库，已经回答不了下一步该查哪里。它需要阅读代码，但也不能搜到一处相同文案，就宣布找到了故障位置。

页面提示在哪个条件下出现，调用了哪个接口，返回值经过什么转换，后端怎样计算活动价格，这些问题要沿着代码关系追下去。更早的一步，是确认当前读的代码与这家门店当时运行的版本相符。

我们这一篇给 Demo 增加代码检索和受限读取能力，先接入配套的前后端示例仓库。从页面、请求、接口到业务函数，逐步找到相关实现，并把文件位置和提交版本留在证据里。工具接口也在这里讨论如何通过 MCP 适配。

最终要得到的是可以继续验证的调用路径。代码里存在一种可能，并不说明这张工单真的走过它。这个区分会决定 Agent 接下来是继续取证，还是过早写下一句“原因已经找到了”。

## 结尾

阿杰核对了 Agent 找到的文件和接口位置。记录里保留了代码提交和版本线索，哪些分支可能触发提示也分别列了出来。

“这次知道它看的是什么版本。”他说，“我们可以从这里继续查，不用再问它这段代码从哪来的。”

老周指着其中一条路径：“这个分支确实可能返回价格变化，但这笔订单是不是走到这里，还得看请求记录。”

于是给小林的进展里，写的是已经定位到需要检查的实现，没有写“故障原因已确认”。

小林点头：“那我先告诉门店查到哪了，别让大家以为已经修好。”

代码把调查范围缩小了。下一篇用受限的数据库与日志工具，核验这张工单实际发生过什么。
