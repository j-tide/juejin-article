# 接上只读数据库和日志，让代码推断得到验证

*开头与结尾草稿。人物、工单及 Demo 情节为虚构示例；结尾待实现验证后定稿。*

## 开头

老周贴出查询结果：“订单支付状态是成功。”

店长回了张打印机旁边的照片：“钱肯定付了，我现在是没找到小票。”

又一条记录被贴进来，出单任务显示发送成功。小林看了一会儿，问：“这个成功，是发出去了，还是店里已经打出来了？”

话题里出现了两个“成功”，柜台那边却还在等。支付记录、订单状态、任务发送和设备实际打印，说的是不同阶段。把其中一个状态当成整笔交易已经完成，就会把后面的调查跳过去。

代码阅读能帮助我们知道这些阶段如何连接，但这笔订单当时经过了哪一步，还得看对应记录。查询发生得太晚，现场已经恢复；读到的是副本，状态还没追上；设备回执缺失，这些情况都可能让证据不完整。

这一篇把 Demo 最初的合成查询接口扩展成受限的数据库和日志工具，按品牌、门店、业务对象与时间窗口取证，再把结果放到同一条时间线上。

查询范围和预算由执行端控制。Agent 需要哪个对象，就请求哪一段资料，不能因为“还没找到”而不断扩大扫描。记录只证明发送成功时，回复也只能说到发送成功；现场是否打印，要有相应回执或门店确认。

我们会沿这张工单继续查，也会准备一个最终状态相同、事件顺序不同的例子，看看它能不能分清“现在是什么样”和“之前发生了什么”。

## 结尾

给店长的回复里，三个状态终于各自有了含义：支付记录支持什么，订单流转到哪里，出单任务留下了哪些记录。没有设备回执的部分，也明确列成需要现场继续确认的事项。

“这下我知道问店里什么了。”小林说，“不能再把‘任务发出去了’转成‘已经打印了’。”

老周带着时间窗口和任务标识继续核对设备侧，门店按对应单号确认现场情况。还没取得的证据，留在未完成检查里。

到了交接时间，接班的人问：“这些记录对应的是哪一次补充？前面那个页面问题排除了吗？”

查到的资料多了，话题也更长了。下一版需要把事实、假设、纠正与待办整理清楚，让后来加入的人能从当前进度继续，而不是重新猜一遍。
