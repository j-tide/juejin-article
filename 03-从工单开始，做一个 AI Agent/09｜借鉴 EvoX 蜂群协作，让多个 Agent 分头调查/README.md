# 借鉴 EvoX 蜂群协作，让多个 Agent 分头调查

*开头与结尾草稿。人物、工单及 Demo 情节为虚构示例；结尾待实现验证后定稿。*

## 开头

老周在群里发了一句：“我查活动服务，先别催。”

这次是几家门店反馈同一张活动券无法使用。阿杰已经在看结算页，品牌运营在核对门店名单，小林还要分辨反馈里哪些来自当前活动。

大家有各自能做的事，彼此之间也有依赖：门店名单没确定，查询范围就可能错；前端拿到的报价版本，还需要后端记录来对照。

把同样的工单交给我们现有的单 Agent，它也能调用这些工具，但一些互不依赖的检查可能排成一长串。让几个 Agent 一起做似乎很合适，不过小林提出了另一个问题：

“分出去以后，谁知道有没有漏查？它们结论不一样，我该转哪一个？”

多开几个执行者，增加的不只是并发。任务怎样划分、输入是否一致、结果回到哪里、失败由谁补上，都需要有明确做法。否则几份看起来完整的报告，可能都在重复同一条错误资料，还把真正缺少的检查漏了。

这一篇借鉴 [EvoX 关于任务拆分与结果汇合的讨论](https://evomap.ai/research/self-organizing-ai-swarms)，在现有工具和证据结构上增加协作。能独立取证的分支分别执行，存在依赖的按顺序推进；结果带任务编号与引用，由程序检查覆盖，再处理结论冲突。

我们也会保留单 Agent 的对照。不是每张优惠咨询都需要这么多人——得看拆分之后是否真的更有用，付出的时间与调用成本是否值得。

## 结尾

小林看到的不是几份彼此独立的长报告，而是同一张调查记录：门店范围对应哪项任务，前端取得了什么版本线索，后端还缺哪段记录。未完成的分支仍然可见，没有在汇总时被悄悄略过。

“那条结论有冲突的，怎么处理？”她问。

阿杰点开两边的引用：“先补这项检查。不能因为两份报告都这么写，就当成已经确认。”

这次协作需要交付的是覆盖完整、来源清楚的调查进度；是否比单 Agent 更快、更省或更准确，要看同条件对照的实际结果。

老周接着问：“一张单这么分，活动一开，几十条话题都来呢？”

执行者数量和查询预算不能跟着话题数量无限增加。下一步要把排队、事故聚合和整体运行开销一起考虑。
