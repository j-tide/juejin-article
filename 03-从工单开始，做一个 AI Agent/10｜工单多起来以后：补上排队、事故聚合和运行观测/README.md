# 工单多起来以后：补上排队、事故聚合和运行观测

*开头与结尾草稿。人物、工单及 Demo 情节为虚构示例；结尾待实现验证后定稿。*

## 开头

活动刚开始，小林的飞书未读消息就一直在往上加。

一家店说结算慢，另一家说付款后状态不刷新。还有人只贴了一张加载中的截图。小林刚把几条话题归到一起，第三家店长又催了一句：“我们是团餐，一会儿要统一送走，别跟普通点单混了。”

其中还夹着一条“没出单”。阿杰看了录屏，发现顾客根本还没完成支付，和其他几家不一定是同一件事。

一张复杂工单可以拆开调查，不意味着同时来一批话题就能照样处理。如果每个话题都启动完整调查，甚至再派出几个子 Agent，模型调用、日志查询和数据库读取会一起增加。同一条公共依赖被查很多遍，真正紧急的团餐却可能还在队尾。

小林此时最需要的，也不是十几份完整报告。她要知道哪些门店可能受同一问题影响，谁已经开始查，哪些需要先处理，以及下一条有用进展什么时候能发出来。

这一篇给 Demo 补上持久化排队、优先级和并发预算，聚合可能属于同一事故的工单，同时保留每家店的差异。再把等待时间与实际执行时间分开记录，看看时间究竟花在排队、模型、工具还是人工补充上。

我们会把那张团餐单和混入的独立问题一起放进回放。不能只证明系统最终都回了话，还得检查该先处理的是否被及时处理，聚合有没有把不同的问题混成一个。

## 结尾

活动高峰的回放结束，小林先看的是那张临近交付时间的团餐单：它是否按配置得到及时处理，等待中有没有收到有用进展。

“那条没完成支付的，也别并进去。”阿杰提醒。

调查记录保留了这张单的差异。其他可能共享原因的话题仍需核验，不能仅凭“都很慢”就认定属于同一事故。运行记录则把排队、工具执行和人工等待分开，方便定位真正卡住的位置。

“这次至少能看见谁在等什么。”小林说。

吞吐量和成本还需要拿实际负载继续验证。老周翻着其中一段熟悉的检查过程，提出了另一个问题：“这条路径以前验证过，为什么每次还得重新找？”

排队解决任务怎么安排，经验记录要解决的，是哪些工作值得在下一次复用。
