# 怎样知道 Agent 进步了：建立工单回放评测

*开头与结尾草稿。人物、工单及 Demo 情节为虚构示例；结尾待实现验证后定稿。*

## 开头

小林把新版和旧版的两段回复放在一起。

新版短一些，步骤也少一些。她觉得更好转述，老周却指着第一句话问：“它怎么一上来就知道这个活动范围有问题？”

我们回头检查准备用来回放的资料。里面不仅有客户最初的反馈，还混进了后来运营确认原因的那条回复。那条消息在实际调查开始时，根本还没有出现。

这次对比看起来很顺，输入却不公平。还有几张相似工单，其实来自同一场活动异常：一张进了经验库，另外几张留作测试。如果直接按工单数量计算，很容易把一次事故的重复描述当成多次独立判断。

前面已经做了很多功能，也积累了一些经验。现在需要回答一个更具体的问题：面对当时可获得的信息，新版是不是比旧版更会处理，而不是因为提前看到了结论，或者反复遇到已经记住的样例。

这一篇建立按消息时间推进的工单回放，并按事故与时间隔离开发和测试数据。在固定模型、工具和预算下，分别看定位、错误判断、证据引用、追问、人工接手、耗时与成本。

信息不足、原因未知的工单也要保留。它们不一定有一个能自动评分的根因答案，但我们仍能检查 Agent 有没有胡乱定因、遗漏已知事实，或者把需要转交的工作拖在自己手里。

先把比较方法做对，后面才有依据决定哪些经验和策略值得继续用。

## 结尾

小林再次看新版和旧版的对照时，最后确认原因的那条消息已经从早期输入中拿掉，来自同一事故的重复工单也按组划分。

“现在比较的，才是当时能知道的那些事。”老周说。

结果要按不同类型分别记录：有的工单能确认原因，有的只能检查追问和交接是否合理。原因未知的样例没有被删掉，模型少调用几次工具，也不会自动换成更高的质量评价。

小林把最开始那两段回复收起来：“先别说新版更聪明，把差在哪里写清楚。”

这一篇得到的是可以复查的比较方法，而不是预先承诺某个版本胜出。接下来再从具体失败中提出改动，一次验证一种变化，避免凭总体印象修改整个系统。
