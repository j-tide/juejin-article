# 根据反馈改进策略：检索、排查步骤和蜂群分工怎样更新

*开头与结尾草稿。人物、工单及 Demo 情节为虚构示例；结尾待实现验证后定稿。*

## 开头

回放里有一类问题反复出现：门店说优惠券不能用，Agent 总要先翻一圈历史故障，最后才去核对活动范围。

小林看着这段过程说：“这种是不是先看活动配置就够了？”

老周翻出另一张工单。那张配置本身没有明显问题，最后要对照旧客户端拿到的报价版本。“这张要是看完配置就结束，还是会漏。”

两个人都指出了有用的条件。第一种情况值得提前核对配置，第二种情况需要保留继续调查的出口。把它们压成一句“优惠券问题先查配置”，看着像学到了经验，也可能把策略改得过于简单。

有了上一篇的回放方法，我们可以开始有依据地提出改进。候选变化需要说明它针对什么失败、适用于哪些工单、改变哪一个步骤，以及如何判断没有伤害其他场景。

这一篇尝试把检索条件、追问顺序、技能选择和蜂群分工做成可比较的策略版本。先从一类变化开始，拿失败轨迹提出候选，再用隔离数据对照，不把一段自动复盘直接当成已经可以启用的新规则。

如果候选只对常见问题有效，却让旧版本、团餐或特殊活动的工单更容易被误判，也要在结果里看见。处理过更多工单，应当帮助系统选择更合适的下一步，而不是让它更坚定地套用上一次的方法。

## 结尾

回到“优惠券问题先查什么”的讨论，小林的建议被整理成一项有适用条件的候选；老周提出的旧客户端案例则留在对照里，检查它有没有因为简化流程而漏掉后续调查。

“所以不是把所有优惠问题都改成先看配置。”小林确认了一遍。

“对，先看它在哪些条件下有用。”老周说。

每个候选都需要留下来源、版本、对照结果和准入判断。没有改善、证据不够，或者损害其他场景时，可以不启用；自动提出建议，并不要求系统必须接受。

小林最后问：“如果回放过了，新活动上线后还是出问题呢？”

这就需要下一层能力：把候选放到可控范围里使用，观察新情况，并能明确退回哪个版本。
