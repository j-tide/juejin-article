# 把改进用起来：小范围启用、错误经验撤销与完整回放

*开头与结尾草稿。人物、工单及 Demo 情节为虚构示例；结尾待实现验证后定稿。*

## 开头

小林在一条旧话题下面补了新消息。

“这家店又不行了。上次的办法现在还适用吗？”

这次品牌刚调整过活动范围，一部分门店还没切到新的配置版本。候选策略正在少量话题中试用，仍然优先采用此前整理的检查路径。运营同时补充：这次团餐订单的优惠条件也有变化。

老周没有马上让它继续查，先问：“这张工单用的是哪一版策略？它引用的经验是哪次活动留下的？”

前面已经能提炼经验、比较候选，但系统开始实际使用这些改进以后，还需要回答这些问题。一次离线对照无法覆盖所有新活动和新版本。经验过期、人工反馈错误，或者几个 Agent 反复引用同一个误判，都可能让原本有用的更新变得不合适。

直接覆盖提示词或修改记忆库，会让事情更难判断。正在处理的工单可能前半段用旧规则、后半段用新规则；即使发现问题，也说不清该退回什么状态。

这一篇把经验、技能、检索配置和协作策略绑定成可追踪的版本，先影子对照，再小范围启用。观察到退步时，能够停止继续扩大范围、撤销有问题的经验，并恢复先前可用的版本。

最后回到整个系列的工单：从顾客付款却没出单，到团餐、多店活动和人员交接，检查每次增加能力究竟改变了什么。能留下的改进需要证据，不适用的部分也要有明确的退出办法。

## 结尾

小林重新打开那张复发的工单，先看到当前采用的策略版本，以及被标记为需要复核的旧活动经验。新的配置线索没有被旧结论盖过去。

“这次不能把上次的回复直接转给店长。”她说。

老周确认要停用的候选与受影响范围，再核对正在处理的任务。回滚只恢复调查系统的版本，不表示业务故障已经修复；门店问题仍要沿当前证据继续处理。

阿杰把尚未核验的客户端版本补进待办。小林向门店交代已确认的事实和下一项检查，保留这张工单，没有因为系统完成回滚就将它关闭。

从最初手动复制一条文字，到能追踪材料、协作调查、复用和撤销经验，系列中的每次改动都要回到对应的工单验证。最后留下哪些版本、淘汰哪些策略，以实际回放与使用结果为准。

“没查清的就写没查清。”小林说，“告诉我下一步找谁、还差什么，我才能接着跟。”
